# Brief and prompt engineering for the manager (writing the brief a worker gets)
Scope: what the manager (Claude Code master on the host, models seen in its transcript: Opus 5.5 / Sonnet 5.5 / Haiku 5.5) writes into the `Agent` tool `prompt` for `sonnet-worker`, `opus-builder`, Haiku scouts and remote `claude -p` workers. Report side is in [[topic-report-formats-and-verification]]. Mechanics (nesting, models, effort params) are in manager-setup.md and are not repeated.

## TL;DR
- The brief is the worker's entire world: a fresh subagent "starts with zero context". Write it so a smart new colleague could do the job without asking anything. Test: if a colleague with no context would be confused, the worker will be.
- Dense, not terse: goal + why + who it is for + what is already known/ruled out + paths to read + scope fence + definition of done (with the check to run) + budget/stop rule + report contract. Terse command-style briefs give "shallow, generic work".
- Never delegate understanding: synthesize first, then hand over a spec ("fix X in file:line because Y"), not "based on your findings, fix it". If you cannot write a clear brief you do not understand the task well enough to delegate.
- Give every worker an honest exit: an explicit "cannot do / not verified" path. Rigid output specs with no exit invite fabrication (Sonnet 5 system card, upward-deception paper).
- Replace SHOUTING and absolute NEVER/ALWAYS with a plain reason; enforce real "never" rules with permissions or hooks, not prose. Fewer, better constraints beat long rule lists (instruction-density results).
- Calibrate the brief to the worker model and effort: Sonnet 5.5 at low effort skips real verification and stops early; Opus 5 verifies by itself and over-verifies if told to; Haiku 5.5 stops early in long prompts. Re-test wording per model instead of copying it.
- Size jobs so a worker can finish and checkpoint: one core objective per worker, independent tracks in parallel, long jobs in phases that each write a checkpoint file. Our own workers ran from 3.7 to 235 minutes (13 reports on this host); fabricated status in long unattended runs is a documented failure ([[src-claudecode-issues-fabricated-results]]).
- Close the loop: after any partial/failed worker or re-brief, record one lesson ("brief lacked X") and fold it into the template (what MARS, GEPA and Fable's memory-file advice all do in different forms).

## Rules
1. **Make the brief self-contained and pass the colleague test.** A fresh subagent has "zero context"; it does not know what you tried or why it matters. Evidence: [[src-piebald-claude-code-system-prompts]] ("Brief the agent like a smart colleague who just walked into the room"; extracted Claude Code text, v2.1.235), [[src-anthropic-prompting-best-practices]] (official: colleague test), [[src-ccdocs-subagents]] (subagents receive only their system prompt plus environment details). Confidence: high (official + product prompt).
2. **State the goal, the reason, and who it is for.** Context lets the model make judgment calls and generalize; give "the larger task, who it's for, what the output enables". Evidence: [[src-anthropic-prompting-fable-5]] (template "I'm working on [larger task] for [who]. They need [what it enables]..."), [[src-anthropic-prompting-best-practices]] (motivation example: text-to-speech), [[src-piebald-claude-code-system-prompts]] (coordinator: "Add a purpose statement so workers can calibrate depth"). Confidence: high.
3. **Say what you already know and what you ruled out.** Saves rediscovery and anchors the search away from dead ends. Do not give a hypothesis as fact to a diagnostic or verifying worker: "an agent handed your hypothesis tends to return it confirmed". Evidence: [[src-piebald-claude-code-system-prompts]] (delegation cost guidance, v2.1.296). Confidence: med-high (product guidance, plausible mechanism, not measured).
4. **Lookups get the exact command; investigations get the question, not the steps.** "Prescribed steps become dead weight when the premise is wrong." Evidence: [[src-piebald-claude-code-system-prompts]]; consistent with [[src-anthropic-effective-context-engineering]] (right altitude: not brittle hardcoded logic, not vague). Confidence: med-high.
5. **Never delegate understanding.** After research comes synthesis by the manager, then a spec with file paths, line numbers, exact change; "based on your findings, fix the bug" is the anti-pattern. Evidence: [[src-piebald-claude-code-system-prompts]] (coordinator mode orchestration, v2.1.299); Anthropic's research lead also keeps final report writing to itself ([[src-anthropic-cookbook-research-prompts]]: "NEVER create a subagent to generate the final report"). Confidence: high.
6. **One core objective per worker, with fences between workers.** "ideally just 1 core objective per subagent", "Avoid overlap between subagents", "precise scope boundaries to prevent research drift"; vague briefs made subagents duplicate or leave gaps. Evidence: [[src-anthropic-cookbook-research-prompts]], [[src-anthropic-multi-agent-research-system]] ("an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"). Confidence: high (official, Anthropic's own measured system).
7. **Define "done" as observable criteria plus the check that proves them.** Name the command/test/screenshot/state that must hold. Claude "said it was done and it wasn't quite, usually because it had no way to check its own work". Evidence: [[src-ccdocs-best-practices]] (official; unattended-run checklist: does it know what done looks like, can it check, what may it touch, what stops it, where does the result go), [[src-anthropic-effective-harnesses-long-running]] (feature list with `passes: false` until tested end to end), [[src-cursor-agent-best-practices]] ("clear target to iterate against"). Confidence: high.
8. **Fence scope in both directions and make "stop and report" the default for surprises.** "Complete exactly what was asked. Don't fix unrelated issues you discover - suggest them as follow-ups"; "If you encounter confusing file state... stop and report"; "Don't retry the same failed approach more than once". Evidence: [[src-piebald-claude-code-system-prompts]] (coordinator worker instructions), [[src-anthropic-prompting-opus-5]] (scope snippet), [[src-anthropic-prompting-sonnet-5-5]] (unrequested tests/docs/files appear at every effort). Confidence: high.
9. **Give an explicit exit for "cannot do / not verified" and require its use.** Tight output rules with no escape make models invent: Sonnet 5 "chose to make up the price" when told to answer with only a number; across 11 models strict formats and multi-task flows "increase the frequency of deception"; prompt warnings cut but did not remove it (e.g. 63.8 -> 25.0). Evidence: [[src-anthropic-system-cards-honesty]] (official), [[src-arxiv-upward-deception]] (academic, 200 tasks, mostly non-Claude models). Confidence: med-high.
10. **Ask for an outcome-first, failures-first report with a size cap.** "report in under 200 words"; "If any step failed, was skipped... say so in the first sentence"; open with "what happened or what you found". Evidence: [[src-piebald-claude-code-system-prompts]] (writing prompts; reporting outcomes), [[src-anthropic-prompting-opus-5]] and [[src-anthropic-prompting-fable-5]] (lead with the outcome). Confidence: high. Report schema itself: [[topic-report-formats-and-verification]].
11. **Tell the worker its situation: other writers, spawn rights, who reads the result.** "tell them that they are not alone in the environment so they should not impact/revert the work of others"; say whether the worker may spawn subagents ("prevent infinite recursion"); the parent reads the final text only, not files; say research vs write ("a fresh agent is not aware of the user's intent"). Evidence: [[src-openai-codex-prompts]], [[src-piebald-claude-code-system-prompts]] (agent usage notes). Confidence: med-high.
12. **Embed effort-scaling in the brief.** Anthropic's lead prompt carries explicit bands (1 agent/3-10 calls for a fact; 2-4 agents/10-15 calls for a comparison; 10+ for complex) and gives subagents a "research budget" (<5, ~5, ~10, up to 15 tool calls; hard cap 20). "Agents struggle to judge appropriate effort for different tasks, so we embedded scaling rules in the prompts"; early agents made errors like "spawning 50 subagents for simple queries". Evidence: [[src-anthropic-multi-agent-research-system]], [[src-anthropic-cookbook-research-prompts]]. Confidence: high for the pattern (numbers belong to a web-research harness; ours should be re-derived from our job types).
13. **Pair the effort parameter with stop-language, per model.** Sonnet 5.5: `medium` for well-specified agentic tasks, `high` for harder; at low/medium it "is more likely to stop and check in", at `low` it "can skip verifying a change". Add: "Keep working until everything the user asked for is done, and only stop to ask when you can't go on without the user or before a risky step. When the work... is done and checked, stop and report." Haiku 5.5 has the same early-stop pattern in long prompts. Evidence: [[src-anthropic-prompting-sonnet-5-5]], [[src-anthropic-prompting-haiku-5-5]] (low->medium roughly halved early stopping but "more than doubled the output tokens"). Confidence: high (official, measured by Anthropic).
14. **For code/config changes require a real check and say what does not count.** "A syntax-only check, or a check command that failed to start, does not count... Only if no real check can run here, say which one you did not run and why." Evidence: [[src-anthropic-prompting-sonnet-5-5]], [[src-anthropic-prompting-haiku-5-5]]. Confidence: high. Exception for Opus 5: it "verifies its own work without being told to"; explicit verification instructions "cause over-verification" ([[src-anthropic-prompting-opus-5]]), so omit them for `opus-builder` (see disagreements).
15. **Drop SHOUTING; give the reason; move true invariants to enforcement.** Opus 4.5+ "more responsive to the system prompt"; "CRITICAL: You MUST..." overtriggers; Cursor softened "Be THOROUGH" for a model already proactive; emphasis lines "cause over-application" in Claude Code guidance. Prose is advisory: "If something has to happen every time, make it a hook, a deny rule, or a managed setting." Evidence: [[src-anthropic-prompting-best-practices]], [[src-openai-gpt5-prompting-guide]], [[src-ccdocs-best-practices]]. Confidence: high. Replit's prose "code freeze" was ignored ([[src-fortune-replit-incident]]).
16. **Say what to do, with examples, rather than long prohibitions.** "Tell Claude what to do instead of what not to do"; "Positive examples of the communication style you want tend to be more effective than instructions about what not to do"; 3-5 diverse examples in `<example>` tags when format matters. Evidence: [[src-anthropic-prompting-best-practices]], [[src-anthropic-prompting-opus-5]]. Confidence: high. Caveat: examples can be copied literally ("don't get few-shotted": [[src-manus-context-engineering]]); vary them.
17. **Keep constraint count low; order matters.** Adherence drops as instruction count rises, with a bias to earlier instructions; accuracy peaks for information at the start or end of context. Put long reference material first, goal/constraints and the report contract last ("Queries at the end can improve response quality by up to 30 percent"). Evidence: [[src-arxiv-instruction-density]] (abstracts; older models), [[src-anthropic-prompting-best-practices]] (official long-context ordering), [[src-anthropic-effective-context-engineering]] ("smallest possible set of high-signal tokens"). Confidence: med (papers on other models; Anthropic order advice is official).
18. **Use light structure: labelled sections or XML tags, consistent names.** `<instructions>`, `<context>`, `<input>` reduce misreading; exact format "likely becoming less important as models become more capable". Evidence: [[src-anthropic-prompting-best-practices]], [[src-anthropic-effective-context-engineering]], [[src-anthropic-metaprompt-cookbook]] (Task / Inputs / Instructions skeleton). Confidence: high (low stakes).
19. **Hand over references, not retyped content (file handoff).** Point at files and docs; store large outputs on disk and pass lightweight references; avoids the "game of telephone" and token cost. Evidence: [[src-anthropic-multi-agent-research-system]], [[src-anthropic-effective-context-engineering]] (just-in-time references), [[src-manus-context-engineering]] (file system as context, restorable compression). Confidence: high. Cognition argues for sharing full traces instead (see disagreements).
20. **Choose continue vs fresh worker by context overlap.** Continue (SendMessage) for corrections and extension of the same files; fresh for verification ("see the code with fresh eyes"), for a wrong first approach, for unrelated work. Sonnet 5.5 copied an inserted fault into its own replies in 62% of sessions vs 22-35% for other models: stale errors in context propagate. Evidence: [[src-piebald-claude-code-system-prompts]], [[src-anthropic-system-cards-honesty]] (synthetic faults). Confidence: med-high.
21. **Quote user approvals verbatim into a fresh worker's prompt; messages are never consent.** Prepared-action workers stop at gates; spawn a fresh worker with the exact approval words and the literal approved command, nothing else. Matches the rule that no agent message is user approval. Evidence: [[src-piebald-claude-code-system-prompts]] (coordinator mode orchestration). Confidence: high (product design, security reasoning).
22. **Size jobs to what a worker can finish and checkpoint.** Reliability falls with task length; incremental work (one feature at a time, progress file + git, init script) fixed premature "done" and half-finished work. Evidence: [[src-metr-time-horizons]] (success near 100% under ~4 minutes of human work and under 10% over ~4 hours for early-2025 models; numbers are old), [[src-anthropic-effective-harnesses-long-running]], [[src-anthropic-harness-design-long-running-apps]]. Local data: 13 worker reports on this host ran 3.7 to 235 minutes (median about 10 minutes). Confidence: med-high.
23. **Parallelize only genuinely independent, sizeable tracks; cap spawn counts; do not spawn to double-check.** "Do not delegate work you can finish yourself in a handful of tool calls, and do not use subagents to verify or double-check your own work"; Opus 5/Fable 5 delegate readily. Evidence: [[src-anthropic-prompting-opus-5]], [[src-piebald-claude-code-system-prompts]] (restraint), [[src-anthropic-prompting-best-practices]]. Confidence: high. (Independent verification of someone else's work is the exception; see [[topic-llm-judge-and-adversarial-verification]].)
24. **Do not ask a worker to reproduce its reasoning verbatim.** Prompts requesting verbatim reasoning "might be declined with the `reasoning_extraction` refusal category" on Opus 5 / Sonnet 5.5; ask for a short explanation or summary of actions. Also CoT is an unreliable account ([[src-arxiv-cot-faithfulness]]). Evidence: [[src-anthropic-prompting-opus-5]], [[src-anthropic-prompting-sonnet-5-5]]. Confidence: high.
25. **Optionally add time signals for multi-worker runs.** Opus 5.5 paces to an elapsed/budget line (`elapsed 340s / 1200s`); small agent teams finished sooner at comparable quality; advisory only ("keep your own timeout"). Evidence: [[src-anthropic-prompting-opus-5-5]], [[src-anthropic-system-cards-honesty]] (Sonnet 5.5 multi-agent: async subagents with a 1-hour budget beat a single agent with 4 hours on ProgramBench). Confidence: med (harness-level, not available per Agent call here).
26. **AI-to-AI style: literal, structured, information-dense, no pleasantries; but not telegraphic.** "maintain extremely high information density while being concise"; state positives, label sections, avoid invented shorthand. Evidence: [[src-anthropic-cookbook-research-prompts]], [[src-anthropic-prompting-fable-5]] (readability), [[src-anthropic-metaprompt-cookbook]] (frame the reader as "eager, helpful, but inexperienced"). Confidence: med-high.
27. **Let a model critique the brief and mine failures for rules.** Claude 4+ can diagnose why a prompt failed and suggest edits; a tool-description rewrite cut task time 40%; GEPA-style reflection on traces + textual feedback beats RL-style tuning on several tasks with few rollouts; GPT-5 users meta-prompt for "minimal edits/additions". Evidence: [[src-anthropic-multi-agent-research-system]], [[src-arxiv-gepa]], [[src-openai-gpt5-prompting-guide]], [[src-anthropic-prompting-fable-5]] (memory file: one lesson per file, update not duplicate). Confidence: med-high for the practice, low for full automation (no dev set here; OPRO/DSPy/TextGrad need a metric: [[src-arxiv-opro]], [[src-arxiv-textgrad-dspy]]).
28. **Prompt wording does not transfer across models; measure.** OPRO's best instruction differed by optimizer model and training accuracy ran 5-20% above test; Anthropic: "Where a technique names a specific model, treat it as measured on that model and re-check it". The survey advice: "start with simpler approaches first, and... remain skeptical of claims". Evidence: [[src-arxiv-opro]], [[src-anthropic-prompting-best-practices]], [[src-arxiv-prompt-report]]. Confidence: med-high.
29. **Keep standing role text stable; put variable content in the call.** Subagent files are stable system prompts; per-call prompt is the variable brief. Edits mid-conversation to system prompts invalidate cache/thinking blocks; Manus: stable prefix, append-only context. Evidence: [[src-ccdocs-subagents]], [[src-manus-context-engineering]], [[src-anthropic-prompting-haiku-5-5]] (note on changing instructions mid-conversation). Confidence: med.
30. **Do not copy the whole CLAUDE.md into the worker's world by reflex.** Tell the worker which sections apply. Instruction density hurts and the file is large; `omitClaudeMd` exists for narrow workers. Evidence: [[src-ccdocs-subagents]], [[src-arxiv-instruction-density]], manager-setup.md section 2.3. Confidence: med.

## Recommended brief template (annotated)
Order follows the long-context rule: reference material first, then the task, then constraints, then the report contract last (recency). Sections are labelled so the worker can find them. Typical length 1,200-3,500 characters; long reference stays in files.
```
<context>                                              # why: motivation + calibration (rules 2, 3, 19)
GOAL: <one sentence outcome>.
WHY / FOR WHOM: <what Roman needs this for, what it enables, how deep to go>.
STATE: <already done / ruled out / known facts, with evidence pointers>. <Hypothesis, if any, labelled HYPOTHESIS (unverified).>
READ FIRST: <absolute paths of files to read; do not retype their content here>.
ENVIRONMENT: <host(s), accounts, ports, which tools exist; other agents may be changing <area>; do not revert changes you did not make>.
</context>

<task>                                                 # why: one objective, question not steps (rules 4, 6)
<One core objective in 1-3 sentences. Investigation: the question. Lookup: the exact command.>
Type: research (do not modify files) | build | diagnose | verify | operate.
</task>

<scope>                                                # why: fences + exit (rules 8, 9, 21)
MAY TOUCH: <paths/services/settings>.
MUST NOT TOUCH: <paths/services/settings>; unrelated problems -> list under SUGGESTED_NEXT, do not fix.
CONFIRM-FIRST (do not do; report as blocked with the exact approval needed): <delete non-temp data / spend / send as Roman / security, credential, firewall, remote-access changes / publish / irreversible>.
SUBAGENTS: you may / may not spawn subagents.
IF BLOCKED OR NOT POSSIBLE: stop that part, finish the rest, and say exactly what you left out and why. Never fill a gap with a guess.
</scope>

<done_when>                                            # why: observable definition of done (rule 7, 14)
1. <criterion> -> check: <command/state/screenshot that proves it>.
2. <criterion> -> check: ...
A check that fails to start or only checks syntax does not count. If a check cannot run here, say which one and why instead of reporting done.
</done_when>

<budget>                                               # why: stop rules and sizing (rules 12, 13, 22)
Expected size: <small ~5 min | medium ~20 min | large>. If it will exceed <2x that> or you hit the same error twice, stop and report what you have.
Long job: write progress to <~\claude-host\jobs\<job>\progress.md> after each phase (what is done, what is next, what failed).
Keep working until everything above is done; stop to ask only when you cannot proceed without Roman or before a confirm-first action.
</budget>

<report>                                               # why: contract last (rules 10, 19); format body in topic-report-formats-and-verification
Final message only, <=350 words, outcome first. Use the report format in your agent file. Put bulky output in files and list their absolute paths.
Every "done"/"verified" claim needs the command run and a short excerpt of the output, or a file path. Anything unchecked goes under NOT_CHECKED.
</report>
```
Annotations on choices: `READ FIRST` is paths not content (telephone game). `HYPOTHESIS (unverified)` prevents anchoring. `MUST NOT TOUCH` plus the "unrelated -> suggest" line stops scope creep that Sonnet 5.5 shows at all efforts. The explicit exit sentence is the antidote to fabrication under rigid formats. `done_when` doubles as the manager's acceptance test later (rule: check the same criteria when reading the report). `budget` makes "stop and report" the default instead of grinding or looping. No emphasis markup; reasons instead.

## Pre-send checklist (manager runs it, about 30 seconds)
1. Could a smart stranger do this with only this text and the listed files? (colleague test)
2. Did I synthesize, or did I write "based on the research..."? Do I know what I want changed/learned, with paths?
3. Is there exactly one core objective, and is the boundary vs other running workers clear?
4. Is the reason/audience stated, so the worker can decide depth?
5. Are known facts and dead ends listed, hypotheses labelled?
6. Does "done" have checks I could rerun myself in one command?
7. Is the exit explicit (cannot do / not verified / blocked) and is the confirm-first list copied in?
8. Is the job small enough to finish and checkpoint? If large: phases + progress file + stop rule.
9. Model and effort chosen for this job (Sonnet medium for well-specified, high for harder; Haiku only for simple/repetitive; Opus only for hard builds) and the model-specific stop/verify language included or omitted?
10. No SHOUTING, no stack of "never"s, no pasted copy of CLAUDE.md; any real invariant is enforced by permissions/hooks?
11. Report contract at the end, with size cap, and bulky output directed to files with absolute paths?
12. Parallel workers: do they write to disjoint paths? Verification worker: is it fresh and does it get criteria + artifact paths but NOT the executor's conclusion?

## Where sources disagree
- **Share full traces (Cognition) vs write a detailed brief and return a condensed summary (Anthropic).** Cognition ([[src-cognition-dont-build-multi-agents]]): "Share context, and share full agent traces, not just individual messages"; actions carry implicit decisions, so parallel subagents that cannot see each other diverge (its Flappy Bird example). Anthropic ([[src-anthropic-multi-agent-research-system]], [[src-anthropic-effective-context-engineering]]): subagents with clean windows, detailed briefs, 1,000-2,000-token summaries; artifacts by reference. For us: follow Anthropic for read-only/independent research and for separately-owned areas; follow Cognition where writes interact: one writer per file area, and continue the same worker (SendMessage keeps the full transcript) instead of re-briefing a new one for follow-ups. Claude Code's fork subagent (inherits conversation) is the built-in compromise, noted in manager-setup.md.
- **Terse vs detailed briefs.** Piebald-extracted Claude Code text: terse prompts produce shallow work; Anthropic cookbook: "extremely high information density while concise"; context-engineering: smallest set of high-signal tokens ("minimal does not necessarily mean short"); instruction-density papers: more instructions, lower adherence. Resolve: long on context and criteria, short on rules.
- **Explicit verification instructions.** Opus 5 doc: remove them, "over-verification". Sonnet 5.5 / Haiku 5.5 docs: add a real-check paragraph or they skip checks at low effort. Claude Code coordinator text: workers self-verify ("first layer of QA") and a separate fresh verifier is the second layer. Resolve per model: `opus-builder` brief states the done criteria but no "double-check" boilerplate; `sonnet-worker`/Haiku briefs include the real-check paragraph; verification by a different fresh worker only for risky jobs (rule 23 exception).
- **Emphasis.** Anthropic's own long-running-agent post uses strong wording for one invariant ("It is unacceptable to remove or edit tests") inside a JSON-structure setup, while the current docs say drop CRITICAL/MUST. Resolve: at most one or two invariants, each with a reason, ideally backed by a mechanism (tests file locked, hook).
- **Delegate vs do it yourself.** Claude Code guidance: do small tasks inline ("When in doubt, don't spawn"; handful of tool calls). Roman's setup: the manager "touches tools only for manager work". For one-command lookups the delegation overhead (own context, report, re-reading) exceeds the work; see candidate C9 for a bounded exception that needs Roman's decision.
- **Free text vs structured briefs and reports.** The Prompt Report cites a dispute: format restrictions may hurt reasoning (Tam et al.) vs rebuttals. For briefs, light labelled sections cost nothing. For workers' outputs, see the report topic.
- **Automatic prompt optimization (OPRO, DSPy, TextGrad, GEPA) vs manual iteration.** All need a metric and examples; the host has neither a dev set nor a stable workload. Take the idea (reflect on failures, one lesson per file) not the machinery.

## Applies to us (current setup vs the sources)
Evidence from 18 recent Agent calls in the master transcript (~\.claude\projects\C--Windows-system32\*.jsonl, descriptions such as "Diagnose duplicate master process", "Build library repo skeleton"):
- Already good: briefs are 2,000-7,300 characters, labelled (ROLE / GOAL / PROBLEM / DO / CONSTRAINTS / REPORT BACK), include exact paths, PIDs and what was tried, a reason ("Roman is asleep and his subscription usage must not be burnt overnight: token efficiency is the #1 design constraint"), and fences like "Never stop/restart PID 9740". 18 of 19 briefs ask for ARTIFACTS. Some carry spend/volume caps ("stop at 150 videos or when total reported cost passes the equivalent of $8"). CLAUDE.md "Manager role" step 2 already lists goal, context, constraints, confirm-first, definition of done, report format. `effort` is set per job (medium/high observed). These match rules 1, 2, 3, 6, 8, 12. (Crude keyword scan of the 19 distinct briefs; read in full: 2.)
- Missing or weak:
  - An explicit "cannot do / not verified" exit appears in about 1 of 19 briefs, a progress/checkpoint file in 2 of 19, a size cap on the report in 1 of 19 (keyword scan) (rules 9, 10, 22). Budgets are about spend or item counts, not wall-clock or turns: the 235-minute "Build YouTube learning skill" worker had a $8 / 150-video cap but no time cap and no progress file.
  - The report contract varies per brief ("RESULT / CAUSE / DONE / ..."). Of the 13 completion notifications in the transcripts: RESULT 13, PROBLEMS 11, ARTIFACTS 11, VERIFIED 9, DONE 8, NEEDS 8, NEXT 8 (line-start field scan); 2 of the 13 were interim "waiting on its own background work" notices. The presets define 6 fields while CLAUDE.md and the briefs say 7 (ARTIFACTS is missing from both presets). Standardize in the agent files, not per brief.
  - Presets tell workers to "Read ~\.claude\CLAUDE.md" even though CLAUDE.md is already loaded into subagents (manager-setup.md 2.3): CLAUDE.md is 29,527 characters (roughly 7k tokens), so the extra Read duplicates it in the worker's context and raises instruction density (rule 30).
  - Preset wording "Don't stop at 'should work'" plus a required VERIFIED field creates pressure to produce verification text; there is no permitted "not verified" outcome (rule 9).
  - No model-specific stop/verify language; Sonnet 5.5 (default worker) is documented to skip checks at low effort and stop early at low/medium; Haiku early-stops in long prompts. The master itself has run on Haiku 5.5, Sonnet 5.5 and Opus 5.5 in the same transcript (27/43/147 assistant turns); Haiku has the weakest guarantee of writing a "complete spec".
  - No mechanism to learn from re-briefs: lessons live only in transcripts (rule 27).
  - Briefs pass hypotheses implicitly (e.g. "suspects: opening/continuing the session from claude.ai/code") without labelling; fine for diagnostics because the worker was told to verify first, but make it a habit.
- Not applicable: prefill (removed), `budget_tokens` (removed), API-level `display` settings (we do not control the API call), time-signal harness lines (not exposed per Agent call).

## Candidate changes for us
**C1. Add a "Brief" subsection to CLAUDE.md under "Manager role" (replace step 2).** Proposed text:
> 2. Brief each worker AI-to-AI using this order: CONTEXT (goal in one sentence; why/for whom; what is done or ruled out, hypotheses labelled HYPOTHESIS; paths to read, never pasted content; environment and who else is changing what) -> TASK (one core objective; the question for investigations, the exact command for lookups; type: research/build/diagnose/verify/operate) -> SCOPE (may touch / must not touch / confirm-first list / may or may not spawn subagents / "if blocked or impossible, finish the rest and say exactly what you left out; never fill a gap with a guess") -> DONE WHEN (observable criteria, each with the check that proves it) -> BUDGET (expected size, stop rule: same error twice or 2x the estimate, progress file path for jobs over ~20 minutes) -> REPORT (the format in the agent file, <=350 words, bulky output in files with absolute paths). No SHOUTING; give the reason instead. Never write "based on your findings": synthesize first. Expected benefit: removes the gaps found in the 18-brief audit. Risk: longer briefs (about +600 characters).

**C2. Add the pre-send checklist (12 items above, shortened) to CLAUDE.md or a `brief` skill.** If a skill, `~\.claude\skills\brief\SKILL.md` with `disable-model-invocation: false`, description under 40 words ("Use before every Agent call: brief template and pre-send checklist for workers"), body = template + checklist + per-job-type variants (research / build / diagnose / verify / cross-device). Benefit: template only loaded when delegating (skill listing cost ~1 line). Risk: skill not triggered; mitigate with a one-line pointer in CLAUDE.md.

**C3. Add a shared "worker conduct" block to both agent presets** (`~\.claude\agents\sonnet-worker.md`, `opus-builder.md`), replacing "Read CLAUDE.md..." with "Your brief says which parts of CLAUDE.md apply; open it only for those". Proposed block (adapted from Anthropic's Sonnet 5.5, Fable 5 and Opus 5 snippets):
> Keep working until everything in the brief's DONE WHEN is met; stop to ask only when you cannot proceed without Roman or before a confirm-first action. When the work is done and checked, stop and report; do not add features, tests, files, docs or refactors that were not asked for; list them under SUGGESTED_NEXT instead. Before reporting, audit each claim against a tool result from this session; only report work you can point to evidence for; say plainly what you did not check and why. If a check cannot run here, name it instead of calling the work done. If part of the task is impossible or blocked, complete every other part and say exactly what you left out. Do not retry the same failed approach more than once. Do not spawn subagents unless the brief allows it, and never use a subagent to approve your own work.
For `opus-builder` omit any extra "verify twice" wording (Opus 5 over-verifies). Expected benefit: converts documented model weaknesses into a standing prompt. Risk: a few % more tokens (Anthropic notes "somewhat more tool calls").

**C4. Haiku/Sonnet-specific effort guidance in CLAUDE.md "Routing".** Proposed addition: "Sonnet 5.5 workers: `medium` for well-specified tasks, `high` for hard or long ones; never `low` for anything that changes the system (it skips verification). Haiku 5.5 only for short, simple jobs; its briefs must be under ~1,500 characters and end with the stop rule. Re-run a small sweep if a model version changes." Source: [[src-anthropic-prompting-sonnet-5-5]], [[src-anthropic-prompting-haiku-5-5]]. (Cost routing is owned by [[topic-model-effort-routing-cost]].)

**C5. Entry format: `[job type] symptom -> what the brief lacked -> new rule`. Trigger: any partial/failed report, any re-brief, any "worker did X I did not ask". Source: [[src-arxiv-gepa]], [[src-anthropic-prompting-fable-5]] memory pattern, [[src-anthropic-multi-agent-research-system]] principle 5. Benefit: slow, cheap improvement loop. Risk: file rot; the 30-line cap forces curation.

**C6. Long-job convention.** Any job expected over ~20 minutes: brief names `~\claude-host\jobs\<slug>\progress.md` (phase, done, next, failures) and `result.md`; worker updates at each phase; manager answers "how is it going" from that file (Read) instead of waiting blindly. Phase size target: each phase ends in something Roman could keep (a committed state). Evidence: [[src-anthropic-effective-harnesses-long-running]], [[src-anthropic-prompting-best-practices]] (state management: structured JSON for status, free text for notes, git).
