# Model / effort routing and cost (subscription limits) for the 24/7 manager
Scope: how the manager should pick haiku/sonnet/opus + effort per job, what actually burns the Max-plan 5-hour and weekly windows, and which caps/measurements to add. Companion: [[topic-context-window-management]]. Mechanics already covered in manager-setup.md (subagent frontmatter, `effort` param, `CLAUDE_CODE_SUBAGENT_MODEL`) are not repeated.

## TL;DR
- **Workers, not the manager, are the bill.** In this very session (measured, [[src-local-master-usage-analysis]]) 31 `sonnet-worker` runs used 325.6M cache-read + 15.1M cache-write + 1.94M output tokens (list-price equivalent ~$90) versus the master's 18.5M/0.82M/0.12M (~$7.7): workers = 95% of tokens, ~11.6x the manager's cost. The lever is worker turns x worker context, then model tier, then effort.
- Median worker: 42 turns (p90 105, max 171), 52k-token fixed baseline on turn 1 (26% of all worker cache-read volume), median peak context 186k (max 574k). Heavy tail: the top 5 workers are 48% of worker cost (one 171-turn, 383k-context run cost ~$23.5 list). Cap turns and context for the tail, shrink the baseline, keep tool outputs small.
- Price tiers are lopsided: Opus 5.5 is only 2x Sonnet 5.5, but Haiku 5.5 is 20x cheaper than Sonnet (<=100k prompt) ([[src-claude-api-pricing]]). Savings come from moving routine work Sonnet -> Haiku, not from demoting the Opus manager. Subscription weights are unpublished; plan on "several times" per tier ([[src-claude-support-usage-limits]]) and calibrate with `/usage`.
- Keep a strong manager and decide the model ONCE at launch. Model switches rebuilt 49k-155k tokens of cache each time (6 switches in 40 min measured); boot script forcing `--model haiku` on a resumed 70k+ context contradicts what the session actually runs (Opus 5.5).
- Effort: Anthropic's starting point for Opus/Sonnet/Haiku 5.5 in Claude Code is `medium`; ours is pinned higher (Sonnet `xhigh`, Opus/Haiku `high`, agent files `high`) with no eval behind it. `xhigh` is documented for >30-minute, million-token jobs; `max` "prone to overthinking".
- Effort does not fix a wrong approach (it fixes missed edge cases). On a bad report, re-brief or move up a model tier; do not just re-run at higher effort.
- Parallel fan-out costs ~15x tokens (Anthropic's own number); default to ONE worker per job. Forks inherit the manager's full context and model and are ON by default: avoid for routine jobs.
- Add four cheap controls: `maxTurns` on agents, a job-cost ledger (parse subagent transcripts), a limit-hit protocol (no auto-wait in Remote Control), and `--max-turns/--max-budget-usd` on remote `claude -p` jobs.

## Rules
1. **Optimise worker turns x worker context first.** Every request resends the whole conversation; subagent requests "still draw on your usage"; Anthropic's multi-agent system used ~15x chat tokens and "token usage by itself explains 80% of the variance" in quality. Our measurement: workers 95% of tokens. Evidence: [[src-ccdocs-costs]] (official doc), [[src-anthropic-multi-agent-research-system]] (measured, older models), [[src-local-master-usage-analysis]] (measured, ours). Confidence: high.
2. **Use the real price ratios when tiering.** Opus 5.5 $4/$20, Sonnet 5.5 $2/$10, Haiku 5.5 $0.10/$0.50 per MTok (<=100k prompt), cache read 5% of input on Opus/Sonnet 5.5 and 10% on Haiku. Opus:Sonnet = 2x, Sonnet:Haiku = 20x. Evidence: [[src-claude-api-pricing]] (official, list prices; the ratios are my arithmetic). Confidence: high for API prices; the subscription meter may weight differently (Help Center: "Opus costs several times more per turn than Sonnet", no number: [[src-claude-support-usage-limits]], summary-fetched). Confidence on subscription ratio: low.
3. **Haiku 5.5 has a price cliff at 100k prompt tokens.** Over 100k: $0.50/$2.50, cache reads and writes count toward the 100k, "a request over the threshold pays the higher prices even when part of its prompt is a cache hit". A manager resumed at 70k and growing is on the upper tier within hours (our Haiku turns hit 112-117k). Evidence: [[src-claude-api-pricing]], [[src-ccdocs-model-config]], [[src-local-master-usage-analysis]]. Confidence: high.
4. **Haiku 5.5 is documented as a router/extractor/subagent model, not a long-horizon coordinator.** "built for high-volume, latency-sensitive work such as classification, routing, extraction, and subagent tasks"; in long agent prompts at `low` it is "more likely to skip a search, stop early, or skip a check". Use it for lookups, triage, summaries, file chores. Evidence: [[src-platform-haiku-5-5-overview]], [[src-platform-effort]], [[src-anthropic-prompting-haiku-5-5]] (official). Confidence: high.
5. **Never switch the manager's model mid-session; pick at launch.** Each model has its own cache; switching re-reads the full history uncached. Anthropic's own advice: at 100k context a "fairly easy" question can be cheaper on Opus than switching to Haiku; "If you need to switch models, the best way to do it is with subagents". `opusplan` toggles are model switches too. Measured: Haiku->Sonnet->Opus switches wrote 75k, 49k, 109k, 155k tokens of fresh cache. Evidence: [[src-ccdocs-prompt-caching]], [[src-claude-blog-prompt-caching-lessons]], [[src-local-master-usage-analysis]]. Confidence: high.
6. **Delegate the cheaper model, not switch to it.** A subagent with `model: haiku|sonnet` gets its own small cache and context; the manager's cache stays intact. Evidence: [[src-claude-blog-prompt-caching-lessons]], [[src-ccdocs-sub-agents]]. Confidence: high.
7. **Start effort at the model default (`medium` for Opus/Sonnet/Haiku 5.5 in Claude Code) and move on evidence.** "Opus 5.5 at medium matches or exceeds Opus 5 at high on coding and knowledge-work evaluations"; "start at medium rather than carrying over the level you used on Opus 5"; for Sonnet 5.5 "medium for well-specified tasks and move to high for harder or longer ones". Note the API default for Sonnet 5.5 is `high`, Claude Code's is `medium`: check `/effort status`. Evidence: [[src-ccdocs-model-config]], [[src-platform-effort]] (official). Confidence: high.
8. **`xhigh` only for long-horizon work; `max` almost never.** Effort table: xhigh = "Long-running agentic and coding tasks (over 30 minutes) with token budgets in the millions"; max "may show diminishing returns and is prone to overthinking, so test before adopting it broadly"; "Use xhigh or max only where your evals show a quality gain". Measured by Anthropic on Fable 5.1: low->max = 73k -> 222k median tokens (3x) and 1.5 -> 67 min on an underspecified task. Evidence: [[src-platform-effort]], [[src-ccdocs-model-config]], [[src-claude-dev-spending-your-effort]]. Confidence: high (doc) / med (blog numbers, Fable not our models).
9. **Match effort to verification need, not to "importance".** Anthropic rule of thumb: low = quick in-the-loop/easy changes; medium = regular feature work; high = "work where verification is important or there are edge cases"; max = fully autonomous hard problems. Loop: "Implement it on low effort... Verify and test on high effort." Evidence: [[src-claude-dev-spending-your-effort]], [[src-ccdocs-model-config]]. Confidence: med-high (vendor practitioner post).
10. **Higher effort fixes missed cases, not wrong approaches.** On Terminal-Bench "missed a case" failures fell 59 -> 24 low->max but "made the wrong call" only 133 -> 107; detailed specs made levels behave "much more similarly". So: a better brief beats a higher effort; if a report shows the wrong approach, re-brief or escalate model. Evidence: [[src-claude-dev-spending-your-effort]] (vendor internal runs, model-judge categories flagged approximate). Confidence: med.
11. **Low effort skips checks.** Sonnet 5.5 at low "can skip verifying a change"; Haiku "sometimes reports a code change as done without running a check"; early stopping halves from low to medium but output tokens more than double. So `low` only for read-only, small-scope jobs, or with an explicit checklist and an evidence requirement in the report. Evidence: [[src-anthropic-prompting-sonnet-5-5]], [[src-anthropic-prompting-haiku-5-5]]. Confidence: high.
12. **Control effort with the knob, not with prose.** Telling Sonnet 5.5 to "think less" "doesn't reliably reduce its thinking"; "effort shapes token consumption but doesn't limit it"; thinking cannot be turned off on 5.5 models. `think hard` is plain text; only `ultrathink` (terminal-typed, v2.1.311+) raises a turn to xhigh. Do not paste "ultrathink" into worker briefs and do not set `CLAUDE_CODE_EFFORT_LEVEL` (it overrides per-invocation and frontmatter effort). Evidence: [[src-anthropic-prompting-sonnet-5-5]], [[src-claude-blog-model-and-effort]], [[src-ccdocs-model-config]], manager-setup.md. Confidence: high.
13. **Changing effort on 5.5 models does not break the cache.** In Claude Code, effort changes keep the cache on Opus/Sonnet/Haiku 5.5 and Fable 5.1 (not Bedrock/Vertex). So Roman can nudge the manager's effort from the phone without penalty; model changes are different (rule 5). Evidence: [[src-ccdocs-prompt-caching]], [[src-platform-effort]]. Confidence: high.
14. **Do not build a learned router; use a static table plus evidence-gated escalation.** FrugalGPT (cascade, up to 98% cost cut at GPT-4 quality), RouteLLM (>2x cost cut), Hybrid LLM (up to 40% fewer large-model calls), AutoMix (>50% cheaper) all show most traffic is easy and cheap models suffice when quality can be judged. They are single-turn QA routers trained on data we do not have; our manager has ~10 job types known in advance. Evidence: [[src-arxiv-frugalgpt]], [[src-arxiv-routellm]], [[src-arxiv-hybrid-llm]], [[src-arxiv-automix]] (abstract-level, 2023-24 models). Confidence: med (my inference for applicability).
15. **Give the manager a worker descriptor table (price, strengths, latency).** Router-R1 conditions an LLM router only on "simple model descriptors such as pricing, latency, and example performance" and generalises to unseen models; it also learns a cost reward. Cheap to copy as a prompt table. Evidence: [[src-arxiv-router-r1]] (abstract; QA benchmarks only). Confidence: low-med.
16. **A cascade is only as good as its verifier.** AutoMix's self-verification "can be noisy" so it needs a POMDP router; our analogue is the worker's own RESULT/VERIFIED, which is also self-reported. Escalate on evidence read in VERIFIED/PROBLEMS, and use a different (not higher-effort same) checker for risky jobs. Evidence: [[src-arxiv-automix]]; see [[topic-llm-judge-and-adversarial-verification]]. Confidence: med.
17. **Small executor + large advisor is a real Anthropic pattern, but ours is the inverse shape.** Advisor strategy: "Haiku with an Opus advisor trails Sonnet solo by 29% in score but costs 85% less per task"; Haiku+advisor 41.2% vs 19.7% solo on BrowseComp (older Haiku 4.5/Opus 4.6; footnoted prompt differences); advisor output only 400-700 tokens. Our manager coordinates and workers execute, i.e. `opusplan`-shaped ("plan with Opus, execute with Sonnet"). Evidence: [[src-claude-blog-advisor-strategy]], [[src-ccdocs-advisor]], [[src-claude-support-usage-limits]]. Confidence: med.
18. **If the manager is ever downsized, use the advisor, and watch its cost scale with context.** `/advisor opus` works over Remote Control; each advisor call "processes the full transcript anew" (never cached), so a 150k manager transcript makes every consultation a 150k uncached Opus read; toggling the advisor does not break the main cache. Evidence: [[src-ccdocs-advisor]]. Confidence: high (doc).
19. **Parallelism costs tokens, not just time.** ~15x chat tokens for multi-agent; agent teams ~7x; "Parallel agents buy you wall-clock time. They do not buy you tokens"; a subagent "doesn't make the answer any better... a fresh reviewer does". Use fan-out for independent, high-value work (research waves, audits); effort-scaling rule from Anthropic's prompt: simple = 1 agent / 3-10 calls, comparison = 2-4 agents / 10-15 calls, only complex = >10 agents. Evidence: [[src-anthropic-multi-agent-research-system]], [[src-ccdocs-costs]], [[src-openclawdc-subagents-limits]] (low), [[src-ccdocs-best-practices]]. Confidence: high (15x, 7x are vendor numbers).
20. **Avoid forks for routine jobs.** A fork inherits the manager's system prompt, tools, model and entire history; its first request reads the parent cache, but every fork turn then re-reads the whole manager context at the manager's model price, and fork mode (default since 2.1.302) lets Claude start forks on its own. A fresh `sonnet-worker` with a self-contained brief starts at ~52k and runs on Sonnet. Evidence: [[src-ccdocs-sub-agents]] (existing note) and docs section "Fork the current conversation", [[src-ccdocs-prompt-caching]]. Confidence: high (doc) / med (cost inference).
21. **Cap worker turns and context, and ask for partial reports.** Frontmatter `maxTurns` returns partial output (resumable); `claude -p` has `--max-turns` (errors at limit) and `--max-budget-usd` (client-side estimate, subagent spend counts, can overshoot, subagent spawn then fails with `Budget limit reached`). Measured: median 42 turns, p90 105, max 171; peak context up to 574k. Evidence: [[src-ccdocs-sub-agents]], [[src-ccdocs-settings-idle-compaction-budget]], [[src-local-master-usage-analysis]]. Confidence: high.
22. **Cut the fixed per-worker baseline.** Every request carries system prompt + CLAUDE.md + tool/skill/MCP listings; ours is ~52k on turn 1 and 26% of worker read volume. Levers: `omitClaudeMd: true` on narrow workers (docs: the main conversation keeps full CLAUDE.md anyway), smaller CLAUDE.md (<200 lines target; ours is 143 lines / 29.5 KB), `gh` CLI over MCP, disable unused connectors, and do not tell agents to re-read CLAUDE.md (already loaded). Evidence: [[src-ccdocs-costs]], [[src-ccdocs-memory]], [[src-ccdocs-sub-agents]], [[src-local-master-usage-analysis]]. Confidence: high.
23. **Tool output is paid twice: written once, read every later turn.** In our worker data cache writes ($37.7 list-equivalent) exceeded cache reads ($32.6) because workers are short-lived and each added token (tool result, own text) is written at 1.25x then re-read on every later turn (median 42 turns, tail to 171). Truncate outputs (`| head`, `select -first`), use hooks to pre-filter, fetch pages with a targeted prompt, not the whole file. Evidence: [[src-claude-api-pricing]], [[src-local-master-usage-analysis]], [[src-ccdocs-costs]] (hook example). Confidence: med-high.
24. **Watch the cache hit rate like uptime.** Anthropic alerts on it and declares incidents; `/usage` shows a `Prompt cache (main)` line with misses and a likely cause; statusline exposes `prompt_cache`. Subagents are not covered by that line. Ours (computed from usage fields, one record per message id): master 95.8% read/(read+write), workers 95.6%. Evidence: [[src-claude-blog-prompt-caching-lessons]], [[src-ccdocs-costs]], [[src-local-master-usage-analysis]]. Confidence: high.
25. **Leave TTLs at default unless workers are re-messaged after idle gaps.** Main conversation = 1 h on a subscription within plan usage (falls to 5 min once usage credits are billed); subagents/forks/workflows/compaction = 5 min. 1 h writes cost 2x vs 1.25x, break-even after 2 reads. One-shot workers that run continuously refresh the 5-min cache every turn, so `subagentPromptCacheTtl: "1h"` only pays for long-lived, occasionally re-messaged workers. Measured idle gaps of 88 and 174 min each cost a 52-69k re-write on the manager (about $0.3-0.55 list on Opus 5.5, depending on 5m vs 1h write rate). Evidence: [[src-ccdocs-prompt-caching]], [[src-claude-api-pricing]], [[src-local-master-usage-analysis]]. Confidence: high.
26. **Know what the subscription limit is, and what it is not.** Two windows (5 h session, weekly), shared by claude.ai, Code, Desktop, all models; affected by length, model, effort; "You've hit your session/weekly limit" cannot be dodged by switching models, but a model-family message ("Opus limit") can (switch family). Anthropic publishes no token-to-allowance conversion; whether cache reads count at full rate is unresolved and community reports conflict. So optimise tokens broadly and calibrate with `/usage` attribution and the plan bars. Roman is on Max (`claude auth status` shows `subscriptionType: max`; 5x vs 20x unknown). Evidence: [[src-claude-support-usage-limits]], [[src-ccdocs-costs]], [[src-openclawdc-subagents-limits]], [[src-community-handoff-and-cache-reports]] (low). Confidence: high (windows), low (weights).
27. **Remote Control sessions do not auto-wait for a limit reset.** `autoContinueAtUsageLimit` starts its wait in interactive terminals, not in Remote Control sessions, `-p`, or background sessions; the user must run `/rate-limit-options`. So the manager needs its own limit-hit protocol (stop spawning, report, retry after reset). Evidence: [[src-ccdocs-usage-limit-wait]] (existing note), [[src-ccdocs-costs]]. Confidence: high.
28. **Fallback model chains are for overload, not for limits.** `fallbackModel` (array, max 3) triggers on overloaded/unavailable/non-retryable server errors, lasts one turn, covers subagents and (non-smaller-window) compaction; it does NOT trigger on rate-limit, auth or billing errors. Evidence: [[src-ccdocs-model-config]]. Confidence: high.
29. **Hold usage-heavy background triggers.** Scheduled tasks, cross-session messages and goal check-ins each start a full-context turn while the session is idle; `crossSessionInbound: hold` and `CLAUDE_CODE_GOAL_CHECKIN_MINUTES=0` stop that. Evidence: [[src-ccdocs-costs]]. Confidence: high.
30. **Measure per job, from transcripts.** `/usage` gives local attribution (skills, subagents, MCP) and recommendations; `claude -p --output-format json` gives `total_cost_usd` (list-price estimate, not billing); subagent transcripts under `.../<session>/subagents/agent-*.jsonl` carry per-message `usage` (that is how [[src-local-master-usage-analysis]] was computed). Evidence: [[src-ccdocs-costs]], [[src-local-master-usage-analysis]]. Confidence: high.
31. **Batch and off-peak are not levers on this plan.** Message Batches give 50% off but only via the API; Claude Code subscription use has no documented off-peak discount. Third-party posts about peak-hour reductions being removed (May 2026) are unverified snippets. Time heavy waves after the weekly reset and when the plan bar is low. Evidence: [[src-platform-haiku-5-5-overview]] (batch 50%), [[src-claude-support-usage-limits]]. Confidence: med.
32. **Retries are the silent multiplier.** A failed or partial worker that is simply re-run pays the baseline (52k) + all turns again; `SendMessage` resume of the same worker can read the original cache if within TTL; Explore/Plan agents cannot be resumed. Re-brief with what failed, resume by name if within 5 min, else spawn fresh with a corrected brief. Evidence: [[src-ccdocs-sub-agents]] (resume), [[src-ccdocs-prompt-caching]] ("Resumed subagents"). Confidence: med.

## What changed in 2026 (added 2026-11-01)
- **Reasoning budget is a measured tradeoff, not "more is better".** Same model and harness: always-xhigh 53.9% (timeouts) vs high 63.6% vs "reasoning sandwich" (extra effort on planning and on verification, high in between) 66.5%. [[src-langchain-improving-deep-agents-harness]] (vendor, one benchmark). Supports pinning `effort` per job type and spending the high setting on plan and verify steps; consistent with the existing routing table.
- **Teams and workflows are the new multipliers.** Agent teams ~7x tokens of a standard session when teammates run in plan mode; every active teammate keeps consuming until shut down; docs advise Sonnet for teammates and small teams. [[src-ccdocs-costs-2026-update]], [[src-ccdocs-agent-teams]]. Workflows: warn at >25 agents or 1.5M projected tokens, try a small slice first, choose a smaller model for stages that don't need the strongest. [[src-ccdocs-workflows-usage-and-limits]].
- **Measurement now exists inside the product.** `/usage` attributes plan usage to skills, subagents, plugins and MCP servers and lists recommendations at >=10% share; the cache line reports hit %, misses with likely cause and warm/cold, but covers only the main conversation, not subagents. [[src-ccdocs-costs-2026-update]]. Use it before changing routing; our own digest (see [[topic-observability]]) is still needed for per-job cost.
- **Hidden idle spend** is itemised: scheduled tasks, cross-session messages, goal check-ins (max 3 idle per goal) and cache expiry each re-send full context. For an always-on manager: `crossSessionInbound: hold` if no peer messaging is wanted, keep loops few. [[src-ccdocs-costs-2026-update]], [[src-ccdocs-cross-session-messaging]].
- **Thinking cannot be disabled** on Opus/Sonnet/Haiku 5.5 and Fable models, so `effort` is the only cost lever for them. [[src-ccdocs-costs-2026-update]].
- Fan-out cache sharing: sibling agents with identical model, effort, tools, schema and cwd share a prompt-cache prefix; 5-minute TTL unless `subagentPromptCacheTtl`=1h. Practical: give parallel workers identical presets and differ only in the brief. [[src-ccdocs-workflows-usage-and-limits]].

## Where sources disagree
- **Is Opus expensive?** API price table: Opus 5.5 is 2x Sonnet 5.5 ([[src-claude-api-pricing]]); Zivtech (April 2026, Opus 4.6 era, low reliability) says Opus ~1.7x Sonnet input; Help Center says Opus "several times more per turn" and "Spending Opus on routine work is the fastest way to drain a daily limit" ([[src-claude-support-usage-limits]], summarised, Enterprise-oriented article). I would follow: plan with 2-5x, measure once with `/usage`; our own measurement shows the whole master (mostly Opus) is ~8% of list cost, so tier the workers first.
- **Effort: use defaults vs push higher.** Anthropic model-and-effort blog: "for most tasks you should use the model's default effort level" ([[src-claude-blog-model-and-effort]]); "Spending your effort" shows big pass-rate gains low->max on hard tasks with 3x tokens ([[src-claude-dev-spending-your-effort]]); effort docs: xhigh/max "only where your evals show a quality gain". Both are consistent once you separate routine from hard: default for routine, raise per job with a stated reason. Our static pins at xhigh/high are the outlier.
- **Multi-agent value.** Anthropic: lead Opus + Sonnet subagents beat single Opus by 90.2% at ~15x tokens, for high-value breadth-first research ([[src-anthropic-multi-agent-research-system]]); Cognition argues for single-threaded agents because parallel agents make conflicting implicit decisions ([[src-cognition-dont-build-multi-agents]]); Claude Code best practices: subagents give parallelism or fresh eyes "but not a smarter answer" ([[src-ccdocs-best-practices]]). Follow: fan out only independent read/research/verify tasks; one worker per write task.
- **Small vs large manager.** Anthropic's advisor material argues cheap executor + strong advisor ([[src-claude-blog-advisor-strategy]]); the docs position Haiku 5.5 for routing/subagent tasks ([[src-platform-haiku-5-5-overview]]); `opusplan` and the Help Center say plan with Opus, execute with Sonnet. No source evaluates a Haiku coordinator of Sonnet workers on long-horizon ops. Follow: Opus-class (or Sonnet 5.5) manager, Haiku for leaf tasks; test a Sonnet-manager+Opus-advisor config on real jobs before changing.
- **Do cache reads count against subscription limits?** Unknown. Docs say usage "is affected by... which Claude model... and the effort level" and that long sessions "draw usage for the whole conversation" ([[src-claude-support-usage-limits]], [[src-ccdocs-costs]]); community reports conflict ([[src-openclawdc-subagents-limits]], snippet). Follow the docs: assume cached re-reads are cheaper but not free; verify with a controlled test (see C9).
- **Model switching for cheap questions.** Common advice is "use Haiku for easy questions"; Anthropic's Claude Code team says in a 100k session switching is costlier than asking Opus ([[src-claude-blog-prompt-caching-lessons]]). Follow Anthropic: delegate, do not switch.

## Applies to us
Current setup (CLAUDE.md, soul.md, agents, settings.json, boot-claude.ps1, manager-setup.md) versus the rules:
- **Routing text in CLAUDE.md**: says sonnet-worker default, opus-builder rare, Haiku for simple jobs by passing `model: "haiku"`, effort defaults high, `low/medium` for simple, `xhigh/max` for hard. Already good: tiers exist. Missing: no job-type table, no turn caps, no escalation rule, no statement that `high` is above Anthropic's start, no "one worker per job" or "no forks" rule, no limit-hit protocol. Verdict: right idea, uncalibrated.
- **Effort pins**: settings.json `modelSettings`: sonnet-5-5 `xhigh`, opus-5-5 `high`, haiku-5-5 `high`; both agent files `effort: high`; boot script `--effort high`. Anthropic's starting point is `medium`; `xhigh` is for >30-min jobs. The agent frontmatter overrides the session level for workers (so workers run at `high`, not `xhigh`), but the manager itself runs at the pinned level. Likely over-spend on routine jobs (median 42 turns, but a heavy tail: top 5 workers = 48% of cost). Unproven benefit: no eval. Wrong in direction (rules 7, 8).
- **Manager model**: boot script `--model haiku`; settings default `model: sonnet`; the transcript shows the live session on Opus 5.5 after manual switches. Consequence: every reboot starts on Haiku with a resumed context (price cliff at 100k, weaker judgment) and invites switch churn. Agent bodies still say "run by a router agent (Haiku)": stale. Decide the manager model and make launch, settings and agent text agree.
- **Cost visibility**: none. No ledger, no per-job cost, no limit tracking. `/usage` works over Remote Control (bars, attribution) but its `f` auto-fix hint does not.
- **Turn/budget caps**: none on agents (`maxTurns` unset); `cachyos-run.ps1` pattern in manager-setup uses `--max-turns 40 --max-budget-usd 3` already for remote `-p` jobs: good, make it the default.
- **Fork/parallel**: Agent tool offers `fork`; nothing forbids it; manager runs 100k+ Opus context, so a fork is expensive. The research waves (this KB: ~15 workers) are fine if value is high, but they should be sized deliberately.
- **Baseline**: agent bodies tell workers to "Read ... CLAUDE.md", which is already auto-loaded (duplicate ~8k tokens plus a tool call). `syncClaudeAiPlugins:false` is set, yet connector MCP servers (Figma/Amplitude/Intercom/etc.) still appear in the worker tool list (visible in this worker's own deferred-tool list), contributing to the 52k baseline; check `/context` in a worker.
- **Thinking inflation**: `ultrathink` unused; fine.
- **Telegram/limits**: no limit-hit handling exists; RC does not auto-wait.

## Candidate changes for us
**C1. Correct the effort pins (settings.json).** Replace the `modelSettings` block with defaults-first values:
```json
"modelSettings": {
  "claude-opus-5-5":   { "effortLevel": "medium" },
  "claude-sonnet-5-5": { "effortLevel": "medium", "autoCompactWindow": 250000 },
  "claude-haiku-5-5":  { "effortLevel": "medium" }
}
```
Benefit: removes the `xhigh` pin on Sonnet; Opus 5.5 at medium >= Opus 5 high (docs). Risk: occasional shallower manager reasoning; mitigated by per-job `effort` on workers and Roman's `/effort high` from the phone (cache-safe on 5.5). Measure: compare worker turns/tokens for the same job type before/after via C5.

**C2. Make launch, settings and agent text agree on the manager model.** In `boot-claude.ps1` replace `'--model','haiku','--effort','high'` with the model you actually want (recommended: `'--model','opus','--effort','medium'`) and add `'--fallback-model','sonnet'`. Rationale: stops the Haiku-start/Opus-switch churn (rule 5) and the Haiku >100k tier. Alternative to test for a week: `--model sonnet` + `/advisor opus` (cheaper manager, Opus consulted at decision points; advisor re-reads the uncached transcript each call, rule 18). Edit the "run by a router agent (Haiku)" sentence in both agent files to "run by the manager agent". ## From Nate Herk / RoboNuggets / Karpathy

Added 2026-11-01 from 549 creator videos (Nate Herk, RoboNuggets, Andrej Karpathy). Practitioner evidence: [demonstrated] = shown working in a video, [opinion] = advice. Weigh below the official/benchmarked sources above; where they disagree see [[src-creators-disagreements]].

- **Match model to job.** Use cheaper models for sub-agents and simple tasks, and the strongest for deep reasoning. Why: model tiers differ widely in cost. [demonstrated] (T37; [[src-nate-herk-agent-practice]], [[src-robonuggets-agent-practice]])
- **Use deterministic workflows where no AI is needed.** Let the harness route events and call the LLM only when needed. Why: AI calls are token-billed. [opinion] (T38; [[src-nate-herk-agent-practice]])
- **Prune dead weight.** Run /doctor and /skill-doctor, and view a skill tree to find skills clogging context. [demonstrated] (T39; [[src-robonuggets-agent-practice]])
