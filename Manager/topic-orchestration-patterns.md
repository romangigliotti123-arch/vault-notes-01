# Orchestration patterns for a manager of subagents

Scope: supervisor/manager-worker, orchestrator-workers, hierarchical, swarm/handoff, blackboard, pipeline, routing, parallelisation, evaluator-optimizer, debate, plan-and-execute, market/contract-net; single vs multi-agent decision rules. Framework-specific material is in [[topic-multi-agent-frameworks]], failure data in [[topic-multi-agent-failure-modes]], Anthropic's own consolidated rules in [[topic-anthropic-agent-guidance]]. Written from the src- notes on disk (all opened 2026-10-29); the worker that was meant to write this file was stopped by the 5-hour usage limit, so this file was synthesised by the lead from its notes.

Constraints of OUR substrate (from [[src-ccdocs-sub-agents]], [[src-ccdocs-subagent-nesting-siblings-teams]]): nested subagents, depth 3, 20 concurrent, background by default so results arrive as notifications in a later turn, a subagent sees only its prompt + CLAUDE.md + git status (not the conversation), siblings CAN message each other via SendMessage only if named and given the tool, finished subagents are resumable by name/ID.

## TL;DR
- Our pattern IS orchestrator-subagent (manager + workers called as tools). Anthropic: "For most use cases, we recommend starting with orchestrator-subagent" and evolve only when a bottleneck is observed. Keep it; add structure to the manager (ledger, effort-scaling rules, verification), not more agents. [[src-claudecom-multi-agent-coordination-patterns]]
- Multi-agent only wins in three situations: context protection, genuine parallelisation (thoroughness more than speed), specialisation. Otherwise a single agent with good tools matches it at 3-10x fewer tokens. [[src-claudecom-building-multi-agent-systems]], [[src-claudecom-fold-subagents]], [[src-openai-practical-guide-building-agents]]
- Read-parallel is safe, write-parallel is not. Parallel writers make conflicting implicit decisions; keep one writer per artifact, give parallelism to reading/investigation/review. [[src-cognition-dont-build-multi-agents]], [[src-cognition-multi-agents-working]], [[src-langchain-how-and-when-multi-agent-systems]]
- Centralised coordination with validation contains error amplification (4.4x vs 17.2x independent) and the benefit of adding agents disappears when the single-agent baseline is already above ~45%. [[src-google-scaling-agent-systems]]
- A coordinator with an explicit ledger (facts, plan, progress, loop detection) beats a bare "who speaks next" chat by 31% in the Magentic-One ablation: the manager needs a task ledger file, not just memory. [[src-arxiv-magentic-one]]
- Hierarchy helps only when the manager can VERIFY; bouncing work back with vague feedback made reports worse. [[src-arxiv-loop-back-authority]]
- Fresh restarts and a planner/worker/judge split scale; locks, flat self-coordination and long-lived workers do not. [[src-cursor-scaling-agents]], [[src-anthropic-building-c-compiler]]

## Rules
1. **Use the simplest pattern that fits the job; decide per job, not per system.** Taxonomy: prompt chaining, routing, parallelisation (sectioning/voting), orchestrator-workers, evaluator-optimizer; workflows (code-defined paths) vs agents (LLM-directed). Most Roman jobs ("install X", "set up Y") are a single sonnet-worker call: do not add a planner, reviewer or second worker. Evidence: [[src-anthropic-building-effective-agents]] (2024-12-19). Confidence: high (official).
2. **Orchestrator-subagent is the default; know its two named weaknesses.** The orchestrator is an information bottleneck and details are lost across handoffs; without parallel running you pay multi-agent tokens for no speed gain. Mitigate: workers write artifacts to files and return paths (see [[topic-brief-prompt-engineering]]), run independent workers in the same message. Evidence: [[src-claudecom-multi-agent-coordination-patterns]] (2026-04-10). Confidence: high.
3. **Decompose by context boundary, not by role.** Planner/implementer/tester splits create a telephone game; the worker that builds a thing also tests it; merge specialists that chain on each other's output or touch the same data. ChatDev/MetaGPT-style role-play companies fail mostly on spec disobedience, repetition and weak verification, and role-spec fixes alone only gained single-digit points. Evidence: [[src-claudecom-building-multi-agent-systems]], [[src-claudecom-fold-subagents]] (2026-10-22), [[src-mast-why-multiagent-fail]], [[src-arxiv-chatdev]], [[src-arxiv-metagpt]]. Confidence: high.
4. **Share the whole relevant context, not a one-line task.** Cognition's two principles: share full traces, not just messages; actions carry implicit decisions that conflict. For us: a brief contains decisions already made and constraints, and pointers to artifacts/files holding prior outputs. Evidence: [[src-cognition-dont-build-multi-agents]]. Confidence: med (one product, strong argument, consistent with Anthropic's research-system lessons).
5. **Parallelise reading, serialise writing.** Anthropic's research system parallelises search but writes the final report in one agent; LangChain: "conflicting write actions typically produce far worse outcomes than conflicting read actions". For us: parallel workers may research/inspect/audit; installs, config edits and code changes on one target go to one worker at a time (or disjoint files/directories declared in the brief). Evidence: [[src-langchain-how-and-when-multi-agent-systems]], [[src-cognition-multi-agents-working]], [[src-anthropic-multi-agent-research-system]]. Confidence: high.
6. **Put effort-scaling rules in the manager's prompt.** 1 worker for simple fact finding, 2-4 for comparisons, more only for clearly divided complex research; without such rules agents spawned 50 subagents for trivial queries. Evidence: [[src-anthropic-multi-agent-research-system]]. Confidence: high. (Current CLAUDE.md says "run independent jobs in parallel" but gives no damping rule: see C1.)
7. **Pay the token multiplier only for high-value tasks.** Agents ~4x chat tokens, multi-agent ~15x; token use alone explained 80% of BrowseComp variance; a better model beat doubling the budget on an older one. On a subscription this is a usage-limit problem (see [[topic-model-effort-routing-cost]]). Evidence: [[src-anthropic-multi-agent-research-system]]. Confidence: high (measured).
8. **Cascade: single agent first, escalate to multi-agent only when needed.** Request cascading raised accuracy 1.1-12% and cut deployment cost up to 20%; MAS benefit shrinks as model capability grows. Evidence: [[src-arxiv-single-or-multi-agent-why-not-both]] (abstract only). Confidence: med.
9. **Capability ceiling and error amplification.** 260 configurations: if a single agent already exceeds ~45% accuracy, adding agents gives negative returns; independent agents amplify errors 17.2x vs 4.4x under centralised validation; best architecture depends on the task (sequential planning -70%, decomposable finance +80.8%). Evidence: [[src-google-scaling-agent-systems]] (2025-12-09). Confidence: high (controlled), but benchmark tasks not ours.
10. **Give the supervisor ledgers.** Magentic-One's orchestrator keeps a task ledger (facts given / to look up / to derive / guesses + plan treated as a hint) and a progress ledger with loop and stall detection; removing it cost 31%. For us the ledger is a file: job id, goal, worker, model/effort, state (A2A-style: submitted/working/input-required/completed/failed/canceled), deadline, artifact paths. Evidence: [[src-arxiv-magentic-one]], [[src-a2a-protocol-spec]]. Confidence: med-high.
11. **Hierarchy only where the manager can verify.** 86 paired runs: flat teams wrote better reports than hierarchical teams with revision authority (each revision -0.14 clarity, more hedging); authority helped only when the manager could verify the work. Send work back only with a concrete failed check or missing item. Evidence: [[src-arxiv-loop-back-authority]] (2026-09-13, abstract only). Confidence: med.
12. **Manager of managers = avoid.** Each hop is lossy: theory (delegated network dominated by a centralised decision maker absent new signals) and a snippet-only relay experiment (accuracy falls per stage). Delegation pays when it adds signals (tools, verification, fresh context) or relieves context limits. Keep depth at 1 (manager -> worker); forbid workers from spawning workers unless the brief says so. Evidence: [[src-arxiv-reliability-limits-multiagent-planning]]. Confidence: med-low (theory + unverified snippet), consistent with Anthropic's guidance.
13. **Where capacity should go: decomposition.** In a controlled QA study scaling the delegation role added ~11 EM points, scaling the executor ~2.6. Our manager's real job is decomposition and briefs, and the boot script runs it on a smaller model than its workers. See C2 and [[topic-model-effort-routing-cost]]. Evidence: [[src-arxiv-think-big-search-small]] (abstract; small-model QA, not coding). Confidence: med-low.
14. **Planner/worker/judge with fresh iterations scales; locks and flat self-coordination do not.** Cursor: locks cut 20 agents to the throughput of 2-3; flat agents became risk-averse; planners + grinding workers + a judge deciding to continue + fresh start each cycle worked; "periodic fresh starts to combat drift". Evidence: [[src-cursor-scaling-agents]] (2026-01). Confidence: med-high (vendor blog).
15. **Autonomous parallel agents need a near-perfect verifier and tiny logs.** The 16-agent C compiler run used no orchestrator (lock files in a shared repo) but a near-perfect test harness; cost ~$20k API. Not applicable at our scale; the transferable part is "verifier quality bounds everything". Evidence: [[src-anthropic-building-c-compiler]]. Confidence: high (primary), low relevance.
16. **Generator-verifier is a pattern, not a default.** "The verifier is only as good as its criteria"; cap loops and escalate. Debate/ensembles do not reliably beat self-consistency at equal compute (debate is hyper-parameter sensitive). Use a verifier for irreversible or high-stakes outputs, not as ceremony. Evidence: [[src-claudecom-multi-agent-coordination-patterns]], [[src-arxiv-mad-smit-should-we-go-mad]], [[src-du-multiagent-debate]]. Confidence: high. Details: [[topic-llm-judge-and-adversarial-verification]].
17. **Plan once, run independent steps in parallel, compare to a baseline.** Plan-and-execute / ReWOO / LLMCompiler save tokens and latency by planning a task DAG up front (ReWOO 5x token efficiency on HotpotQA; LLMCompiler up to 3.7x latency, 6.7x cost vs ReAct). Maps to: manager writes the job list with dependencies, launches independent workers together, joins. "AI Agents That Matter": always compare a fancy setup to the plain baseline on cost AND accuracy. Evidence: [[src-arxiv-rewoo]], [[src-arxiv-llmcompiler-and-agents-that-matter]], [[src-langchain-plan-and-execute-agents]]. Confidence: med (older models).
18. **Blackboard / market / contract-net: learn, don't build.** LbMAS (+4-5% on QA/math), blackboard data-science agents (13-57% relative) and COALESCE (20% cost reduction in simulation) are small-benchmark results from different task families. The transferable parts: shared state on disk instead of message passing (our file ledger), and explicit budget+success-criteria contracts in the brief ([[src-arxiv-agent-contracts]], single-source). Evidence: [[src-arxiv-lbmas-blackboard]], [[src-arxiv-blackboard-data-science]], [[src-arxiv-coalesce-task-outsourcing]], [[src-arxiv-agent-contracts]]. Confidence: low-med.
19. **Swarm/handoff is for user-facing specialist routing, not for a manager.** Handoff patterns save calls on repeat requests but cannot parallelise; subagent-as-tool processes ~67% fewer tokens on a multi-domain compare via context isolation. LangChain itself archived its supervisor library and recommends the plain tool-calling supervisor. Evidence: [[src-langchain-docs-multi-agent]], [[src-repo-langgraph-supervisor-swarm]]. Confidence: med-high.
20. **Prefer running a loop in fresh processes to an in-session loop.** Ralph: fresh context each iteration, state in files, one task per loop; the official Claude Code plugin loops inside one session via a Stop hook and accumulates context, so cap with max-iterations. For us: long multi-step jobs = a worker with a state file and `maxTurns`, resumable by SendMessage, not an unbounded in-session loop. Evidence: [[src-ghuntley-ralph]], [[src-claude-plugins-ralph-loop]]. Confidence: med.
21. **Fold subagents back when they add no value.** Measure with/without per task, repeat runs, look at which tasks changed, not the aggregate. Evidence: [[src-claudecom-fold-subagents]]. Confidence: med-high. (We have no per-job outcome log to do this; see [[topic-observability]].)
22. **Combine patterns deliberately: a worker may itself run a verifier loop; the manager only routes.** Managed Agents guidance: one agent per item then a second agent reviews EVERY item, one failing agent must not fail the run, set a session budget. Evidence: [[src-platform-managed-agents-multiagent]]. Confidence: high (official).

## What changed in 2026 (added 2026-11-01)
New Claude Code primitives sit on top of the manager-plus-subagents default; they do not replace it.
- **Who holds the plan is now the design axis.** Subagents, skills and agent teams: Claude decides turn by turn and results land in context. Dynamic workflows: a JS script holds the loop, branching and intermediate results, so the manager's context receives only the final answer; scale "dozens to hundreds of agents per run" vs "a few delegated tasks per turn" for subagents. Adversarial cross-review and claim voting can be coded into the script, and unverifiable claims are reported as unverified, not refuted. [[src-ccdocs-workflows-usage-and-limits]] (official). Use a workflow for a sweep/migration/audit over many items with the same step; keep subagents for the 1-5 job case that is our normal load.
- **Agent teams are a different thing from our workers.** Peers with a shared task list and mailboxes, experimental, off by default; best for parallel review and competing-hypothesis debugging, bad for sequential or same-file work; "3 focused teammates often outperform 5 scattered"; give each file ownership. [[src-ccdocs-agent-teams]] (official). Trap: while the env var is on, a subagent the manager NAMES (needed for SendMessage resumption) silently launches as a teammate; our setup must keep it unset or `0`. Teammates do not exist in `claude -p` sessions.
- **Session-to-session messaging is first-party.** A message from another session cannot grant consent, change config or run commands, and a bypass-mode receiver HOLDS messages for human approval by default (5-minute expiry). Relevant to the phone/Remote Control and CachyOS paths. [[src-ccdocs-cross-session-messaging]].
- **Task board as control plane.** OpenAI Symphony polls a Linear board, runs one isolated agent per task, requires proof of work (CI status, review feedback) before a PR lands; "works best in codebases that have adopted harness engineering". [[src-openai-symphony-repo]] (preview, trusted environments). Same shape as our job ledger plus a done-when evidence rule; supports keeping a ledger the manager reconciles, not chat memory.
- **Harness over model.** OpenAI's 1M-line agent-written product leaned on a docs directory as source of truth plus mechanical architecture rules and structural tests [[src-openai-harness-engineering-infoq]] (secondary); LangChain moved a fixed model 52.8% to 66.5% on Terminal Bench 2.0 by harness changes alone [[src-langchain-improving-deep-agents-harness]]. Böckeler's guides-and-sensors split is the clearest vocabulary [[src-bockeler-fowler-harness-engineering]]. Implication for a manager: invest in the check scripts and repo-resident rules workers run, not in more worker roles.
- **Google ADK's pattern catalogue** (pipeline, coordinator, fan-out/gather, hierarchical, generator-critic, refinement, HITL, composite) matches the taxonomy above; the only new operational rule is a unique output key per parallel agent [[src-google-adk-multi-agent-patterns]] (Dec 2025, vendor, pseudocode).
- Rule 6 (effort scaling) now has a native knob: workflow size guideline small <5 / medium <10 / large <50 agents, default medium (small on Pro), large-run warning at >25 agents or 1.5M tokens. [[src-ccdocs-workflows-usage-and-limits]].

## Where sources disagree
- **Cognition (single-threaded, share traces) vs Anthropic (orchestrator-subagent with isolated contexts).** LangChain reads them as compatible: reading parallelises, writing does not. Cognition's 2026 follow-up concedes useful multi-agent shapes (read-only helpers, reviewers with clean context, escalation to a stronger model). Follow: parallel read-only workers and fresh-context reviewers yes; parallel writers on the same artifact no. [[src-cognition-dont-build-multi-agents]], [[src-cognition-multi-agents-working]], [[src-langchain-how-and-when-multi-agent-systems]].
- **Multi-agent wins (Anthropic +90.2% on research evals) vs scaling study (negative returns above ~45% single-agent baseline, MAS benefit shrinks with stronger models).** Anthropic's task is breadth-first and parallelisable and its baseline was weak; the Google study covers mixed tasks. Follow the study for coding/admin jobs, Anthropic for broad research. [[src-anthropic-multi-agent-research-system]], [[src-google-scaling-agent-systems]], [[src-arxiv-single-or-multi-agent-why-not-both]].
- **Hierarchy (Cursor, Magentic-One: orchestrator beats chat) vs flat teams (loop-back study).** Cursor/Magentic evidence is about coordination of long work; the loop-back study is about revision authority on open-ended writing. They agree on "coordinator yes, unverifiable bounce-back no". [[src-cursor-scaling-agents]], [[src-arxiv-loop-back-authority]].
- **Debate/ensembles:** original paper positive, later benchmarks mostly negative at equal compute. Do not build debate. [[src-du-multiagent-debate]], [[src-arxiv-mad-smit-should-we-go-mad]].

## Applies to us
- Pattern: yes (orchestrator-subagent, depth 1). Already good: sonnet-worker default, parallel independent jobs, nested under one session.
- Missing: effort-scaling and spawn-damping text in the manager rules; a job ledger file; "one writer per artifact" rule; rule that vague bounce-back is banned; explicit "do not delegate what you can do in <5 tool calls" (CLAUDE.md says the manager does no work itself, which pushes trivial lookups through a worker at full cost: Anthropic's own sample says the opposite for simple work).
- Teams/swarm/blackboard/market: no. gastown/claude-squad-style orchestrators: learn (see [[topic-multi-agent-frameworks]]), do not adopt.

## Candidate changes for us
- **C1 (CLAUDE.md "Manager role", add after step 4):** "Sizing rule: do it yourself if it takes <= 3 read-only tool calls (status check, reading a file, one command to brief a worker). Otherwise 1 worker for a single-target job; 2-4 parallel workers only for independent read-only research or disjoint targets; never more than 5 without telling Roman why. One writer per file/system: workers that change the same thing run one after another. Workers do not spawn workers unless the brief says so." Benefit: stops over-delegation cost and conflicting parallel writes. Risk: the manager does a little more itself; mitigated by the 3-call cap. Evidence: [[src-anthropic-multi-agent-research-system]], [[src-cognition-multi-agents-working]].
- **C2 (decide the manager model):** the boot script starts the master on `--model haiku --effort high` although the task text calls it Opus-class; the one controlled study says capacity belongs at delegation/decomposition. Either confirm what the live model is (`/status`) and align boot-claude.ps1, or give the manager a "plan the job" step by a stronger model for non-trivial requests (the library has `task-decomposer`). Evidence: [[src-arxiv-think-big-search-small]].
- **C3 (job ledger):** `~\claude-host\jobs\ledger.md` (append-only, one line per job: id | time | goal | worker preset/model/effort | state | artifacts | verified Y/N). Manager appends at spawn and on each report. Evidence: [[src-arxiv-magentic-one]], [[src-a2a-protocol-spec]].
- **C4 (bounce-back rule):** "Send a worker back only with a concrete defect (failed check, missing item, contradicting evidence). Never 'improve this'. After two bounces, escalate a tier or tell Roman." Evidence: [[src-arxiv-loop-back-authority]].
- **C5 (verifier gate):** run the `verifier` preset only for irreversible/outward actions, system config changes, or when the worker's evidence is prose-only; otherwise the manager spot-checks one claim itself. Evidence: [[src-claudecom-multi-agent-coordination-patterns]], [[src-google-scaling-agent-systems]].
- **C6 (periodic fresh start):** long-lived orchestration states drift; write `session-notes` and restart the master on a schedule (see [[topic-context-window-management]], [[topic-long-running-always-on-agents]]). Evidence: [[src-cursor-scaling-agents]].

## Open questions
- No measurement of our own manager (success rate, tokens per job, over-delegation); needs the ledger plus cost logging.
- Whether sibling messaging (workers talking directly) is worth enabling: nothing in the evidence suggests it for our jobs.

## From Nate Herk / RoboNuggets / Karpathy

Added 2026-11-01 from 549 creator videos (Nate Herk, RoboNuggets, Andrej Karpathy). Practitioner evidence: [demonstrated] = shown working in a video, [opinion] = advice. Weigh below the official/benchmarked sources above; where they disagree see [[src-creators-disagreements]].

- **Make the orchestrator only delegate.** Tell it explicitly not to write emails, summaries or code itself. Why: orchestrators that do the work themselves skip the specialists and burn expensive context and limits. [demonstrated] (T1; [[src-nate-herk-agent-practice]])
- **Brief the lead agent as a project manager.** Say: don't execute, delegate to cheaper sub-agents, parallelize independent work, log progress to a build plan or per-agent folder, and flag open issues. Why: it keeps the expensive model cheap and leaves a written trail. [demonstrated] (T2; [[src-nate-herk-agent-practice]])
- **Assign one agent per specific job.** Avoid mega-agents. Why: broad agents get confused. Separate agents also let you give each its own memory, skills and files. [opinion] (T3; [[src-nate-herk-agent-practice]], [[src-robonuggets-agent-practice]])
- **Send bulky, throwaway work to a sub-agent.** Use one when the task would dump output or files you won't reread, for repeated jobs, or when you want an unbiased fresh look. Why: only a short summary returns to the main session. [demonstrated] (T4; [[src-nate-herk-agent-practice]], [[src-robonuggets-agent-practice]])
- **Choose skill or sub-agent by the context you need.** Skills usually run in the main session. Sub-agents get a clean window, can run in parallel, and can use another model. Why: it avoids polluting the main session. [opinion] (T5; [[src-nate-herk-agent-practice]])
- **Use specialist sub-agents for expert roles.** Examples are a code reviewer, builder, debugger, test runner, security auditor or researcher, with a main session acting as project lead. Why: a general assistant with skills is a jack of all trades. [opinion] (T6; [[src-nate-herk-agent-practice]])
- **Hardcode stable lookups and delegate searches.** Put known IDs into the skill and hand the searching to a sub-agent. Why: the agent otherwise re-fetches them each run, costing time and tokens. [demonstrated] (T7; [[src-nate-herk-agent-practice]])
- **Run independent work in parallel.** Examples are chapters, design variants, audits and test loops. Why: wall-clock time drops and context stays isolated. [demonstrated] (T29; [[src-nate-herk-agent-practice]], [[src-robonuggets-agent-practice]])
- **Match the term to the setup.** Parallel agents are separate terminals. Sub-agents are delegated by a parent. Agent teams share a task list and message each other. Why: each pattern needs different coordination. [opinion] (T30; [[src-nate-herk-agent-practice]])
