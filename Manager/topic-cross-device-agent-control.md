# Cross-device agent control: running Claude on Roman's other machines

Scope: dispatching jobs to a Claude agent on the CachyOS PC ("my pc") and Roman's Windows PC ("[host]") from the Windows host; robustness, credentials, SSH/Windows specifics, wake/sleep, GUI control. Mechanics (`claude -p` JSON over SSH, `--bg`, RC, cloud) are in manager-setup.md section 3 and not repeated. Synthesised by the lead from src- notes (worker stopped by usage limit).

## TL;DR
- A remote job is a distributed-systems call: set a timeout on everything, make it idempotent with a key, retry with jittered backoff, and track liveness with leases/heartbeats rather than assuming a reply will arrive. [[src-stripe-idempotency-and-aws-retries]], [[src-temporal-activity-timeouts-heartbeats]]
- Headless `claude -p` over SSH has a known failure class: it hangs on stdin/TTY in some versions (2.1.158 regression), exit 124 under `timeout`, silent exit 1 without a TTY. Always give stdin explicitly (pipe the prompt or `< /dev/null`), wrap in `timeout`, check exit 124, record the CLI version. [[src-claude-p-stdin-hang-issues]], [[src-ccdocs-headless-cli]]
- Each device holds its own login. A `/login` credential expires and a session that outlives it "stops making progress": add an expiry check per device; `claude setup-token` yields a one-year token stored by you (a credential: confirm-first). [[src-ccdocs-authentication]]
- Scope the SSH key the agent uses (`restrict`, `command=`, `from=`, `expiry-time`); a forced command alone is not a sandbox. The CachyOS key is currently unrestricted with passwordless sudo. [[src-openbsd-sshd-authorized-keys]], [[topic-agent-security]]
- Waking Wi-Fi machines is outside Tailscale's happy path (WoL is L2; Tailscale is L3); an always-on device on the same LAN must send the packet, which is what `linux-power.ps1` does. [[src-tailscale-wol-upsnap]]
- Prefer pull (worker connects outbound and claims jobs from a pool/queue) over push when devices sleep or roam: Cursor's self-hosted workers use an outbound HTTPS connection, pools, labels, claims and idle-release timeouts. A file-based queue plus lease is the cheap local equivalent. [[src-cursor-cloud-agents-self-hosted]]

## Rules
1. **Every remote call has a timeout, a retry budget and an idempotency key.** Clients are "in an uncertain situation" after a lost response; use a unique key per logical job and let the receiving side return the earlier result or resume; AWS: timeouts from latency percentiles, exponential backoff with jitter, retries only for idempotent operations, avoid correlated cron bursts. Apply to `cachyos-run.ps1`-style calls: job id in the command, a `jobs/<id>/status.json` on the device, check before re-running. Evidence: [[src-stripe-idempotency-and-aws-retries]]. Confidence: high.
2. **Detect dead workers with start-to-close timeouts and heartbeats; resume rather than restart.** Temporal: the server cannot detect a crashed worker without a Start-To-Close timeout; heartbeats can carry a progress payload so the next attempt continues; schedule-to-start latency (job waited for a worker) should be monitored with a reroute plan. Map: "device asleep" = schedule-to-start failure (wake and retry or tell Roman); "worker hung" = missed heartbeat (progress file mtime). Evidence: [[src-temporal-activity-timeouts-heartbeats]]. Confidence: high.
3. **Use leases for ownership and liveness.** Kubernetes Lease: node heartbeat by renewing a timestamp; leader election so only one instance runs. A job directory with `lease.json` (owner, renewTime) prevents two agents from working the same job after a retry. Evidence: [[src-stripe-idempotency-and-aws-retries]]. Confidence: med.
4. **`claude -p` over SSH: give it stdin, a TTY decision and a hard cap.** `timeout N claude -p ... < prompt.txt`, `--output-format json`, `--max-turns`, `--max-budget-usd`, `--permission-mode` explicitly, and treat exit 124 as "hung" not "failed". Regressions are version-specific (2.1.158 hung; 2.1.157 fine); record `claude --version` per device and pin/upgrade deliberately. Auth failures print on stdout as the result, not stderr. Evidence: [[src-claude-p-stdin-hang-issues]], [[src-ccdocs-headless-cli]]. Confidence: med-high (issue tracker, partly snippet-level).
5. **Long jobs: detach and poll, or use a session that survives SSH drops.** tmux (interactive, attach/detach) vs systemd (unattended service) are different tools; choosing wrong is "the most common structural mistake"; name tmux sessions after the job; mosh helps flaky mobile legs but conflicts with Tailscale SSH (`tailscale up --ssh` is not OpenSSH). For us: `setsid nohup ... > ~/claude-host/logs/<id>.json` on Linux and poll; or `claude --bg` there. Evidence: [[src-openreplay-remote-box-setup]], [[src-rogs-claude-code-mosh-tmux-ntfy]]. Confidence: med.
6. **Credentials per device; expiry is a failure mode.** Linux `~/.claude/.credentials.json` (0600), Windows `%USERPROFILE%\.claude\.credentials.json`; a login within 3 days of expiry prints a warning, after expiry "each model request fails with Login expired", and background/RC sessions that outlive it silently stop; `/status` shows the Login row. Add a daily no-LLM check per device (`claude auth status` / `/status`), and treat `claude setup-token` output as a secret. Evidence: [[src-ccdocs-authentication]]. Confidence: high.
7. **Windows OpenSSH specifics ([host]).** Default shell is cmd.exe (set `HKLM:\SOFTWARE\OpenSSH\DefaultShell` for PowerShell: a remote-access config change, confirm first); admin users' keys live in `%programdata%\ssh\administrators_authorized_keys` with ACLs limited to SYSTEM and Administrators (wrong ACLs make key auth fail silently); only password and publickey auth exist; domain users as `domain\user`; no `AuthorizedKeysCommand`. Pipe the prompt on stdin and call `claude.exe` by full path because non-interactive PATH lacks `~\.local\bin`. Evidence: [[src-msdocs-openssh-windows-config]]. Confidence: high (docs); [host] itself unverified.
8. **Scope the key the manager uses.** Per-key options: `restrict` (disables forwarding, PTY, rc), `command="..."` forced command (client command lands in `SSH_ORIGINAL_COMMAND`), `from=`, `expiry-time=`, `permitopen=`; certificates add restrictions (most restrictive union applies). A job-runner key could be `restrict,from="[tailscale-ip]",command="~/claude-host/tools/run-job.sh"` with the script validating a job id and a fixed prompt directory, instead of arbitrary bash with passwordless sudo. Changing authorized_keys on the main PC is a security/remote-access change: confirm first. Evidence: [[src-openbsd-sshd-authorized-keys]]. Confidence: high (mechanism), med (fit).
9. **Pull-based dispatch for devices that sleep.** Cursor's worker opens an outbound HTTPS connection, requests wait in a named pool until a worker claims them, routing by labels, one claim at a time, idle-release timeout keeps a worker for follow-ups, health endpoints. Local analogue: jobs written to a shared folder/Git repo/Tailscale file share; a small agent on each device claims with a lease and writes status/results back. Wake-on-LAN remains separate. Evidence: [[src-cursor-cloud-agents-self-hosted]], [[src-openai-codex-cloud-docs]]. Confidence: med (vendor pattern, not needed at 2 devices).
10. **WoL over Tailscale needs an L2 helper; Wi-Fi targets are fragile.** Tailscale's own guidance: an always-on device on the target's LAN sends the packet (Pi/UpSnap); their example assumes Ethernet. Roman's CachyOS case (Wi-Fi WoWLAN, first-suspend-only, reboot-first policy) is already handled in `linux-power.ps1`; the lesson is to treat wake as best-effort with verification (SSH reachable) and a human fallback. Evidence: [[src-tailscale-wol-upsnap]]. Confidence: high.
11. **GUI control on the Linux box is input injection, not a window API.** ydotool injects via uinput (works on Wayland/X11/console; needs the `ydotoold` daemon; no notion of windows; input goes to whatever is focused); xdotool reaches only XWayland; spectacle for screenshots; the permissioned route is the XDG RemoteDesktop portal/libei (consent prompt, no verified headless story). Anthropic's computer-use guidance: dedicated VM with minimal privileges, human confirmation for consequential actions, screenshots are an injection vector, and instruct "after each step take a screenshot and evaluate" because the model "sometimes acts as if its actions succeeded without explicitly checking". Evidence: [[src-ydotool-readme]], [[src-anthropic-computer-use-tool-doc]]. Confidence: high.
12. **Compare the agent-per-device model to a remote-tool model.** Cursor keeps the agent loop in the cloud and runs only tool calls on the user's hardware (no inbound ports). Our model runs a full Claude on each device (more capable, more credentials, more attack surface, more subscription usage). For simple remote actions (power, status, file fetch), a scripted tool with a JSON contract is cheaper and safer than a remote agent; use a remote agent only for judgement-heavy work. Evidence: [[src-cursor-cloud-agents-self-hosted]], [[topic-tool-and-mcp-design]]. Confidence: med.
13. **Hand-off of files between machines is the telephone-game risk across devices.** Cursor "Move to Cloud" does not carry uncommitted files; same for rsync-less SCP flows. Put job inputs/outputs in a named directory, copy with checksums, and make the report list absolute paths on the device. Evidence: [[src-cursor-cloud-agents-self-hosted]]. Confidence: med.

## Where sources disagree
- **tmux+mosh vs systemd vs `claude --bg`** for persistence: the practitioner posts prefer tmux/mosh for interactive work; Anthropic's agent view/daemon is for background sessions on one machine; for unattended single jobs a detached `claude -p` with a log is simplest.
- **Tailscale SSH vs OpenSSH:** Tailscale SSH removes key management but breaks mosh and is outside OpenSSH's per-key restriction options; our setup uses Tailscale ACL "accept" plus an OpenSSH-style key. Scoped keys need OpenSSH semantics.

## Applies to us
- Current: `cachyos-run.ps1` (arbitrary bash, plain output), `linux-power.ps1` (sleep/wake/status), `claude-rc.service` on Linux, Tailscale ACL accept, key `[private-path]` with passwordless sudo, [host] not configured (SSH logged in as [host]\roman once).
- Gaps: no job id/idempotency on remote runs; no remote liveness/progress file convention; no credential-expiry check on Linux/[host]; no `restrict`/forced-command scoping; no documented version pin; hang handling relies on a `TIMED OUT` string.

## Candidate changes for us
- **C1 (remote job envelope, tools\README.md):** every remote worker run gets `JOB_ID`, writes `~/claude-host/jobs/<id>/{prompt.txt,progress.log,result.json}`; the runner returns `{ok, exitCode, timedOut, jobId}`; the manager polls `progress.log` mtime for heartbeat. See [[topic-tool-and-mcp-design]] C1. Evidence: rules 1-3.
- **C2 (template for remote `claude -p`):** `timeout 1800 ~/.local/bin/claude -p --model sonnet --effort medium --max-turns 40 --max-budget-usd 3 --output-format json --permission-mode bypassPermissions < ~/claude-host/jobs/<id>/prompt.txt > .../result.json; echo $? > .../exit.code` with `CLAUDE_CODE_RETRY_WATCHDOG=1`; exit 124 = hung. Evidence: rule 4.
- **C3 (credential expiry check):** scheduled no-LLM check (`ssh cachyos "claude auth status"` equivalent) logged to the digest; alert only inside 3 days of expiry. Evidence: rule 6.
- **C4 (scoped job-runner key; needs Roman's OK):** a second key on the Linux PC with `restrict,from=...,command=run-job.sh`; keep the full key for interactive admin. Evidence: rule 8.
- **C5 ([host] onboarding checklist for a worker):** confirm `ssh [host]` alias, `claude.exe` full path and version, login status, default shell behaviour (do not change it), `administrators_authorized_keys` ACL state; write results into `RUNBOOKS\[host].md`. Evidence: rule 7.
- **C6 (wake as verified step):** keep `linux-power.ps1 wake` but add `-Json` with `{woke, secs, sshReady}` and a one-line human fallback message. Evidence: rule 10.
