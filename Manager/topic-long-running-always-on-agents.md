# Long-running, always-on agents: durability, supervision, resumability
Scope: how to keep a 24/7 Claude Code manager (plus its workers) correct across crashes, reboots, usage limits and days of drift. Mechanics of subagents/RC already in manager-setup.md (not repeated). Observability/digests live in [[topic-observability]]; context handling in [[topic-context-engineering]] and [[topic-context-window-management]]; security hooks in [[topic-agent-security]]; failure taxonomy in [[topic-multi-agent-failure-modes]].

## TL;DR
- State must live in files (ledger + progress notes + git), never only in the manager's context: "each new session begins with no memory of what came before" ([[src-anthropic-effective-harnesses-long-running]]). We have NO job ledger today; job state exists only inside one 7 MB resumed conversation and in subagent transcripts.
- Design every job as at-least-once with idempotent effects: unique job id, step keys for outward side effects (Telegram/Mail/git push), record intent before acting. Every durable-execution engine (Temporal, DBOS, Inngest, Restate) says the same ([[src-temporal-activity-definition]], [[src-inngest-how-functions-run]], [[src-dbos-architecture]]).
- You do not need Temporal: the transferable core is "append-only ledger + scan for incomplete work on startup + idempotency keys + timeouts" ([[src-dbos-architecture]]). A 60-line Python CLI covers it (tested, see C1).
- Supervision must check liveness (heartbeat freshness), back off, and trip a breaker. Our own log shows 6 watchdog restarts in 35 min on 2026-10-28 (log.md attributes at least three of them to the watchdog not recognising the resumed master); the ClaudeHost task's `-NoExit` means Task Scheduler's RestartOnFailure never fires; the watchdog is now disabled, so a dead master stays dead ([[src-ms-task-scheduler-restart]], local probe).
- Usage-limit pauses: the interactive auto-wait is documented as NOT starting in Remote Control sessions; `CLAUDE_CODE_RETRY_WATCHDOG=1` is the documented unattended switch and is unused here ([[src-ccdocs-usage-limit-wait]], [[src-ccdocs-errors-retry-watchdog]]).
- Cap everything outside the model's judgement: iterations, turns, wall-clock, retries per job, restarts per hour. "The default behavior on any unexpected state is to stop, not to continue" ([[src-nightcrawler-episodic-execution]]).
- Success claims must be verified by something other than the claimer (git state, tests, a second agent); "hallucinated handoff" is a named overnight failure mode ([[src-nightcrawler-episodic-execution]], [[src-anthropic-harness-design-long-running-apps]]).
- Pull, don't push: Roman said no recurring reports. Keep a daily digest FILE and answer "what happened overnight" on demand; alert only on breaker trips and expired deadlines.

## Rules
1. **Put durable state in files and git, not in context.** Initializer writes `init.sh`, a progress log and a feature list; each later session reads git log + progress file, picks one unfinished item, runs a baseline check, commits. Evidence: [[src-anthropic-effective-harnesses-long-running]] (https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents, 2025-11-26). Confidence: high (official; scoped to web-app coding).
2. **Use machine-readable task lists the agent may only flip, not edit.** The feature list is JSON with a `passes` flag; JSON chosen because models were less likely to overwrite it than Markdown; "It is unacceptable to remove or edit tests". Same in Nightcrawler (`tasks.json` incomplete->complete only). Evidence: [[src-anthropic-effective-harnesses-long-running]], [[src-anthropic-quickstart-autonomous-coding]] (https://github.com/anthropics/claude-quickstarts/tree/main/autonomous-coding), [[src-nightcrawler-episodic-execution]]. Confidence: high / low-med.
3. **One item per session/iteration.** Both the Anthropic harness and Ralph ("one task per loop") fail when the agent tries everything at once or declares victory early. Evidence: [[src-anthropic-effective-harnesses-long-running]], [[src-ghuntley-ralph]] (https://ghuntley.com/ralph/, 2025-07-14). Confidence: high (Anthropic) / med (Ralph, anecdotal).
4. **Prefer a fresh process per episode over one immortal session.** Nightcrawler: "Sessions will end. Build around that."; each episode is a new `claude -p` that reads mission + previous handoff and verifies the handoff against git. Anthropic's managed-agents design makes the same split: the session log lives outside the harness so "nothing in the harness needs to survive a crash". Evidence: [[src-nightcrawler-episodic-execution]] (practitioner, low-med), [[src-anthropic-managed-agents]] (https://www.anthropic.com/engineering/managed-agents, 2026-04-08, high). Confidence: med.
5. **Failure compounds, so durable execution plus deterministic safeguards beat prompting.** Anthropic's research system: "Agents are stateful and errors compound"; they built systems that "resume from where the agent was when the errors occurred", with "deterministic safeguards like retry logic and regular checkpoints", and tell the agent when a tool is failing so it adapts. Evidence: [[src-anthropic-multi-agent-research-system]] (https://www.anthropic.com/engineering/multi-agent-research-system, 2025-06-13). Confidence: high.
6. **Reliability decays with the number of dependent steps, not context length.** Geometric law; tool-use tasks fell from near-perfect to near zero in ~16 steps; shrinking context made it worse. So keep each delegated job short, with verification at boundaries, and budget reliability per chain instead of trusting one long run. Evidence: [[src-arxiv-how-fast-do-agents-rot]] (https://arxiv.org/abs/2609.01660, 2026-08-31, preprint). Confidence: med.
7. **Keep a job ledger: id, status, owner, worker, deadline, attempts, note.** Append-only; state = fold of events; on every start, scan for incomplete (PENDING) jobs and resume or mark lost. DBOS does exactly this with Postgres: "scans for incomplete (PENDING) workflows" and recovers "from the last completed step". Evidence: [[src-dbos-architecture]] (https://docs.dbos.dev/architecture). Confidence: high (vendor doc); the file-based simplification is our inference.
8. **Make every outward side effect idempotent with a key, and record intent before acting.** Temporal: "You should always make your business logic Activities idempotent"; Inngest: "a refund can succeed before Inngest saves the step result and retries the step" (the crash window between effect and checkpoint); Stripe: the client-generated key makes retries return the saved result. For us the effects are Telegram replies, git pushes, PRs, mail: key = `<job_id>:<step>`. Evidence: [[src-temporal-activity-definition]], [[src-inngest-how-functions-run]], [[src-stripe-idempotent-requests]] (https://docs.stripe.com/api/idempotent_requests). Confidence: high.
9. **Treat delivery as at-least-once and make the effect effectively-once.** Temporal: "these functions may be executed more than once" while completion is "observed ... exactly once". When a ledger shows intent without completion, the state is ambiguous and must be verified outside (did the message arrive? did the push land?), not blindly re-sent. Evidence: [[src-temporal-activity-definition]], [[src-inngest-how-functions-run]]. Confidence: high.
10. **Retry with exponential backoff AND jitter, cap retries with a budget, and retry at one layer only.** "Retries that increase load can make matters significantly worse"; "retry at a single point in the stack"; side-effecting calls are unsafe to retry without idempotency. Claude Code already retries transient API errors up to 10 times with backoff, so the manager must not wrap worker calls in a second blind retry loop; a re-brief is a different, counted action. Evidence: [[src-aws-timeouts-retries-jitter]] (https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter, 2019-12-05), [[src-ccdocs-errors-retry-watchdog]] (https://code.claude.com/docs/en/errors.md). Confidence: high.
11. **Put a circuit breaker on anything that can loop: restarts, re-briefs, re-spawns.** Closed/open/half-open; after N consecutive failures stop and alert; "Any change in breaker state should be logged". Our watchdog had none (6 restarts in 35 min on 2026-10-28, each firing a boot prompt; log.md attributes at least three to a detection bug, the others coincided with the master-session swap). Evidence: [[src-fowler-circuit-breaker]] (https://martinfowler.com/bliki/CircuitBreaker.html, 2014-03-06); local: claude-host\log.md lines 2026-10-28 10:55 PM-11:30 PM. Confidence: high.
12. **Detect stuck loops mechanically.** OpenHands flags: same action->same observation 4x, same action->error 3x, 3 consecutive agent messages without progress, A/B ping-pong 6 cycles; thresholds hardcoded and a legit polling task can trip them, so make thresholds configurable and scoped to the post-last-user-message window. Practitioner rule that caught many overnight incidents: "retry up to 3 times, then log the blocker to a pending file and move to the next task". Evidence: [[src-openhands-stuck-detector]] (https://docs.openhands.dev/sdk/guides/agent-stuck-detector), [[src-yurukusa-unattended-accidents]] (undated; 20 consecutive "fixed" claims on one error). Confidence: high (SDK doc) / low-med (anecdote).
13. **Every job has a timeout; long jobs must heartbeat.** Temporal: "your operation should either complete within a few minutes or it should heartbeat"; at least one timeout must be set. Claude Code analog: subagents restart after a stall window (`CLAUDE_ASYNC_AGENT_STALL_TIMEOUT_MS`, default 10 min; workflow agents max 6 attempts then fail). Evidence: [[src-temporal-activity-definition]], [[src-ccdocs-workflows-durability]] (https://code.claude.com/docs/en/workflows.md). Confidence: high.
14. **Liveness = fresh heartbeat, not process existence.** systemd `WatchdogSec=` requires periodic `WATCHDOG=1` pings and kills the service if the interval is exceeded. Our watchdog tested `claude.exe` command lines by regex and misfired for the resumed master (log.md 2026-10-28 11:33 PM); and a hung-but-alive master passes a process check. A hook that touches a heartbeat file on every Stop/PostToolUse gives a checkable signal. Evidence: [[src-systemd-service-restart]] (https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html), local log.md 2026-10-28 11:33 PM. Confidence: high (concept) / med (hook-as-heartbeat is our design).
15. **Restart policy needs delay, rate limit and a real failure exit.** systemd: `Restart=on-failure`, `RestartSec=`, start-limit; Task Scheduler: RestartOnFailure Count+Interval. Local probe: ClaudeHost has RestartOnFailure 5 x 1 min but the action is `powershell -NoExit boot-claude.ps1`, so when claude.exe exits the PowerShell stays alive, the task keeps "Running" and RestartOnFailure never triggers; trigger is logon only. Evidence: [[src-ms-task-scheduler-restart]], [[src-systemd-service-restart]]. Confidence: high (probe is direct).
16. **Know what Claude Code's own supervisor does and does not cover.** Background sessions are restarted if their process dies unexpectedly (unless you killed them), survive sleep, and become `failed` (<48 h) or `stopped` after a reboot; interactive sessions are not supervised. The master here is interactive (started by Task Scheduler), so none of that applies to it. `claude agents --json` is the supported interface, not `~/.claude/jobs`. Evidence: [[src-ccdocs-agent-view]] (https://code.claude.com/docs/en/agent-view.md). Confidence: high.
17. **Usage-limit pauses: decide the policy in advance.** Interactive sessions auto-continue after a claude.ai limit resets, but "Claude Code doesn't start the wait on its own" in Remote Control sessions, and never in `-p` or background sessions; workflow runs also do not pause there (agents fail). `CLAUDE_CODE_RETRY_WATCHDOG=1` retries 429/529 indefinitely, "backs off up to 5 minutes ... or until the limit resets when the response carries a rate-limit reset time", but fails immediately on spend-limit 429s. Test before relying on it for the RC master. Evidence: [[src-ccdocs-usage-limit-wait]] (https://code.claude.com/docs/en/interactive-mode.md), [[src-ccdocs-errors-retry-watchdog]], [[src-ccdocs-workflows-durability]]. Confidence: high (docs) / low (behaviour for the RC master untested).
18. **Know the session-scoped scheduler's limits before using /loop for durability.** `/loop` and CronCreate only fire while Claude is running and idle; recurring tasks expire after 7 days; a missed fire is not caught up; a self-paced loop is not restored on `--resume` and in background sessions stops if the wakeup falls due while the process is down. Use it for in-session polling only. Evidence: [[src-ccdocs-scheduled-tasks-loop]] (https://code.claude.com/docs/en/scheduled-tasks.md). Confidence: high.
19. **Choose the scheduler by failure mode.** Cloud scheduled tasks: machine can be off, min 1 h, 100 runs/h/account, 30 manual+API fires/h/task, no local files; Desktop tasks: app must be open and PC awake, one catch-up run for the most recent missed time (7-day lookback); `/loop`: session only. For this Windows host the only fully durable local option documented is the OS scheduler (Task Scheduler) launching `claude -p` (our inference; Anthropic documents Desktop tasks, which need the Desktop app). Evidence: [[src-ccdocs-routines-cloud]], [[src-ccdocs-desktop-scheduled-tasks]], [[src-ccdocs-scheduled-tasks-loop]]. Confidence: high (limits) / med (inference).
20. **State the missed-run policy inside the job.** Desktop doc advice: guardrails in the prompt ("If it's after 5pm, skip the review and post a summary of what was missed"). ClaudeDriveRetry (retry every 30 min until 12:00) is already a good local example of a bounded retry window. Evidence: [[src-ccdocs-desktop-scheduled-tasks]]; local scheduled-task list. Confidence: high.
21. **Condition-driven loops need a bound and an external judge.** `/goal` uses a separate small model to judge "met / not met / impossible" after each turn, clears itself on auth failure, exhausted credits, context overflow, unavailable model, pauses on rate/usage limit, stops after several no-tool turns, and advises "or stop after 20 turns" in the condition. ralph-loop: "Always rely on --max-iterations as your primary safety mechanism"; completion promise is exact-match only. Evidence: [[src-ccdocs-goal]] (https://code.claude.com/docs/en/goal.md), [[src-claude-plugins-ralph-loop]]. Confidence: high.
22. **Same-session loops accumulate context; fresh-process loops do not.** The Ralph plugin loops inside one session (context grows, compaction); Huntley's original is a bash loop with the same prompt each time and state in files. For multi-hour jobs the second form is the safer analogue; `/goal` fits bounded work (<~20 turns) in one session. Evidence: [[src-claude-plugins-ralph-loop]], [[src-ghuntley-ralph]]. Confidence: med.
23. **Resumability needs determinism and recorded results.** Workflow scripts make `Date.now()`, `Math.random()` throw "so that a relaunched run repeats the same agent() calls"; completed agents return saved results, the first changed or failed agent and everything after it reruns; the run does not continue by itself after the session exits (relaunch via `claude --resume`). DBOS/Inngest need the same: non-deterministic work only inside steps. Evidence: [[src-ccdocs-workflows-durability]], [[src-dbos-architecture]], [[src-inngest-how-functions-run]]. Confidence: high.
24. **Human-in-the-loop is a persisted state with a timeout policy, not a blocking question.** LangGraph `interrupt()` persists state and "waits indefinitely"; Inngest `waitForEvent` returns null on timeout; both rerun code before the pause on resume, so effects before the pause must be idempotent. In Remote Control, permission prompts and AskUserQuestion stay open until answered, other forwarded dialogs expire after 5 minutes (`dialogExpiry`). Evidence: [[src-langgraph-interrupts]], [[src-inngest-how-functions-run]], [[src-ccdocs-remote-control-limits]]. Confidence: high.
25. **Plan for RC disconnects that only a local action can fix.** Interactive RC reconnects by itself after outages, but "could not reach the Remote Control server for about 30 minutes" disconnects until someone runs `/remote-control` locally; `claude remote-control` server mode exits after ~10 minutes offline. A phone cannot repair a session it cannot reach, so a local supervisor must. Evidence: [[src-ccdocs-remote-control-limits]] (https://code.claude.com/docs/en/remote-control.md). Confidence: high.
26. **Verification of "done" must come from outside the claimant.** "Agents reliably skew positive when grading their own work"; premature completion and "hallucinated handoff" (report says done, git says not) are documented overnight failures; /goal's evaluator is "a fresh model rather than the one doing the work". Evidence: [[src-anthropic-harness-design-long-running-apps]] (2026-03-24), [[src-nightcrawler-episodic-execution]], [[src-ccdocs-goal]]. Confidence: high / low-med.
27. **Deterministic guards beat prose rules when nobody is watching.** Unattended incidents (deleted src/ twice, push to main, PUT without GET, 20x false "fixed") were stopped by a PreToolUse hook blocking destructive commands plus a retry rule; the Replit database wipe happened despite explicit freeze instructions in context. Credit mapping to our confirm-first list. Evidence: [[src-yurukusa-unattended-accidents]] (low-med), [[src-replit-db-deletion-incident]] (snippet only), [[src-ccdocs-hooks]]. Confidence: med.
28. **Hard caps live outside the model.** AutoGPT's own docs warn continuous mode "may run forever"; Nightcrawler's default limits: 24 episodes, $50 total, $5 per episode, 10 errors, 3,600 s per episode, 12 h wall clock; Anthropic's C-compiler run still used a loop and lock-file task claims with ~2,000 sessions. On a subscription the cap unit is turns, wall-clock and 5-hour-block share, not dollars. Evidence: [[src-autogpt-continuous-mode]] (snippet only), [[src-nightcrawler-episodic-execution]], [[src-anthropic-building-c-compiler]] (https://www.anthropic.com/engineering/building-c-compiler, 2026-02-05). Confidence: med.
29. **Memory drifts: store dated facts, supersede explicitly, prune.** "State drift" (acting on superseded information even when the current version is in context) is reported as a primary long-run failure cause; Manus keeps a todo file rewritten at the end of context and keeps failed attempts visible ("Erasing failure removes evidence"). Snippet-level arXiv evidence, treat as hypothesis. Evidence: [[src-arxiv-agent-state-drift-snippets]] (snippet only), [[src-manus-context-engineering]] (https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus, 2025-07-18). Confidence: low-med.
30. **Make idle monitoring nearly free.** OpenClaw's heartbeat design: a checklist file read each tick, a silent token (`NO_REPLY`) when nothing to say, `activeHours`, `idleOnly`, and the model call skipped entirely when the checklist is empty. Claude Code's Monitor tool streams script output and "avoids polling altogether". Do the checking in a script; wake the LLM only on a change. Evidence: [[src-openclaw-heartbeat]] (partly snippet), [[src-ccdocs-scheduled-tasks-loop]]. Confidence: med.
31. **Bound disk and log growth explicitly.** Transcripts are deleted silently after `cleanupPeriodDays` (default 30; 0 is invalid); the supervisor's `daemon.log` has no documented rotation; LangGraph checkpoints "accumulate" and need a retention policy; the OTel file exporter rotates only if `rotation:` is configured. Locally: projects\ is 98 MB (64 MB of it subagent transcripts for one master conversation), log.md grows by hand-written lines. Evidence: [[src-ccdocs-errors-retry-watchdog]], [[src-ccdocs-agent-view]], [[src-langgraph-persistence]], [[src-otel-collector-fileexporter]]. Confidence: high.
32. **Updating a live agent system needs a plan.** Anthropic runs "rainbow deployments" because "we can't update every agent to the new version at the same time"; the Claude supervisor moves idle sessions to a new binary and leaves working ones alone; `claude respawn` picks up a new binary. Our weekly maintenance (disabled) stopped and restarted Claude; any re-enable must close the job ledger first. Evidence: [[src-anthropic-multi-agent-research-system]], [[src-ccdocs-agent-view]]. Confidence: med.
33. **Review the system on a cadence using the logs, not memory.** Ralph: "tuning a guitar": when it misbehaves adjust the prompt; Hamel: read real traces and cluster failures bottom-up. Weekly: list jobs by outcome (failed/partial/re-briefed), pick the top two failure patterns, change one brief template or agent preset. See [[topic-observability]] rules on failure clustering. Evidence: [[src-ghuntley-ralph]], [[src-hamel-field-guide]] (https://hamel.dev/blog/posts/field-guide/, 2025-03-24). Confidence: med.
34. **Simplify the harness as models improve.** "Every component in a harness encodes an assumption about what the model can't do on its own"; remove one component at a time. A ledger, breaker and heartbeat should stay (they guard infrastructure failure, not model weakness); context-reset rituals may not. Evidence: [[src-anthropic-harness-design-long-running-apps]], [[src-anthropic-managed-agents]]. Confidence: high.

## Where sources disagree
- **Same-session vs fresh-process loops.** Anthropic's ralph-loop plugin and `/goal` keep one session alive with a Stop hook; Huntley's original Ralph and Nightcrawler restart a fresh process per iteration; Anthropic's harness blog also uses fresh sessions with file handoff. Follow: fresh process for multi-hour or repeatable jobs (bounded episodes through `claude -p`), `/goal`/plugin for short, verifiable single-session work. The manager itself stays one interactive RC session because Roman needs the chat.
- **Exactly-once vs at-least-once.** Restate says each invocation "runs exactly once regardless of failures" ([[src-restate-durable-execution]]); Temporal, Inngest and DBOS say steps/activities may run more than once and must be idempotent ([[src-temporal-activity-definition]], [[src-inngest-how-functions-run]], [[src-dbos-architecture]]). The honest reading is the same: exactly-once is the observed result of at-least-once execution plus deduplication. Follow the second group for design; messages to Roman are the only effects where duplication is visible.
- **Single agent vs multi-agent for long tasks.** Anthropic's harness blog leaves open "whether a single, general-purpose coding agent performs best" ([[src-anthropic-effective-harnesses-long-running]]); Huntley insists Ralph is monolithic ([[src-ghuntley-ralph]]); Carlini ran 16 parallel agents with lock files ([[src-anthropic-building-c-compiler]]). Not decisive for a manager; what transfers from all three is file-based state and claim locks, not the topology.
- **Heartbeat polling vs event-driven.** OpenClaw/guides favour periodic heartbeats; Claude Code docs say Monitor "avoids polling altogether and is often more token-efficient" ([[src-openclaw-heartbeat]], [[src-ccdocs-scheduled-tasks-loop]]). For us: script-only heartbeats and hook events; no LLM polling.
- **How much autonomy.** AutoGPT's docs and the overnight-incident posts urge caps and approval; Anthropic ran a compiler build for ~2 weeks at ~$20k API with a verifier-heavy design and no approvals ([[src-autogpt-continuous-mode]], [[src-anthropic-building-c-compiler]]). Autonomy was safe only where the verifier was strong; Roman's tasks (messages, devices) have weak verifiers, so keep caps and confirm-first.
- **Cost anecdotes.** Ralph's "$50k for $297" vs Anthropic's "$9 solo vs $200 full harness" ([[src-ghuntley-ralph]], [[src-anthropic-harness-design-long-running-apps]]): treat the former as marketing, the latter as measured but single-run.

## Applies to us
Current setup (read 2026-10-29): `ClaudeHost` Task Scheduler task, logon trigger only, `powershell -NoExit boot-claude.ps1`, RestartOnFailure 5x/1 min, IgnoreNew; `boot-claude.ps1` resumes conversation 78968f1c with `--model haiku --effort high --dangerously-skip-permissions` and a boot prompt demanding an exact status line plus the 5-line footer; `ClaudeWatchdog`, `ClaudeHealthCheck`, `ClaudeWeeklyMaintenance` all Disabled (Roman's request, 2026-10-28); `ClaudeDriveRetry` running; RC via `remoteControlAtStartup`; Telegram channel removed from boot on 2026-10-28; `settings.json` has no hooks, no telemetry env, no `CLAUDE_CODE_RETRY_WATCHDOG`; log.md (118 lines) is hand/boot-script written; worker presets (`sonnet-worker`, `opus-builder`) have no `maxTurns`, no job id, no progress/heartbeat duty.
- Rule 1-3 (files not context): PARTIAL. Good: session-notes/, reports/, log.md exist. Missing: a machine-readable list of open jobs; the manager's "to-do" is whatever is in a 7 MB resumed conversation (it compacted at least once on 2026-10-28, `compact_boundary` in the transcript).
- Rule 7-9 (ledger, idempotency): MISSING. Subagent transcripts do carry usable job metadata for free (`subagents/agent-*.meta.json` has `description`, `agentType`, `toolUseId`, `spawnDepth`, `finished`, optional `effort`), which makes a retro-fitted ledger cheap, but nothing records deadline, owner, attempts or outward effects. After a master crash the new session has no list of what was in flight and background subagents' fate is undocumented (open question 1).
- Rule 10-12 (retries, breaker, stuck detection): WRONG in the supervisor. Evidence: log.md shows "Claude successfully reloaded" at 10:55, 11:00, 11:05, 11:10, 11:15 and 11:30 PM on 2026-10-28 (at least three were watchdog false negatives, fixed at 11:33 PM by widening a command-line regex; the earlier ones coincided with the session swap); each restart re-issues the boot prompt. No restart cap, no backoff, no alert. Worker re-briefs have no counter either.
- Rule 14-16 (liveness, restart policy): WRONG/MISSING. `-NoExit` defeats RestartOnFailure; with the watchdog disabled a crashed `claude.exe` is never restarted, and an RC disconnect (30-minute heartbeat failure) needs a local `/remote-control`. Roman asked for no recurring REPORTS; a silent supervisor that only acts (and logs) is a different thing, but re-enabling anything that was explicitly disabled needs his OK.
- Rule 17 (usage limits): GAP. Master is an RC session; docs say auto-continue does not start there. `CLAUDE_CODE_RETRY_WATCHDOG=1` is unused. Workers run as nested subagents of an RC session; workflow runs would fail rather than pause.
- Rule 18-20 (scheduling): OK-ish. No `/loop` in use; ClaudeDriveRetry is a reasonable bounded retry. Do not move recurring duties into `/loop` (7-day expiry, session-bound).
- Rule 24-25 (HITL, RC): PARTIAL. confirm-first exists as prose in CLAUDE.md only; there is no record of what was proposed, approved or expired. The Telegram sections of CLAUDE.md (voice-note rule, pairing) are stale since the channel was removed from boot: that is memory drift in the instructions themselves (rule 29). The "Pending work" block mixes finished, superseded and contradictory Linux wake notes (it says both "NEVER suspend" and "WORKING ... SUPERSEDES"); a Haiku-class manager must reason through that on every turn.
- Rule 27-28 (guards, caps): MISSING. Bypass-permissions master with zero hooks; confirm-first not enforced by anything deterministic; no `maxTurns` on workers; no per-job deadline.
- Rule 30-31 (cheap monitoring, disk): OK so far (small footprints: .claude 100 MB, [private-path] 1.4 MB with existing guards). No rotation for log.md/watchdog.log/daemon.log.
- Rule 33 (review cadence): MISSING by design (Roman disabled reports); a pull-based digest satisfies both ([[topic-observability]]).
- Model note: the master runs on Haiku (`--model haiku`). Reconciliation and breaker logic should therefore be scripts with simple outputs, not judgement the Haiku manager must re-derive each boot.

## Candidate changes for us
C1. **Add a job ledger CLI and make the manager use it.** New `~\claude-host\tools\jobs.py` (tested prototype, 60 lines: `new`, `set`, `list [--stale|--all]`, `effect`, `effect-done`; append-only `claude-host\jobs\ledger.jsonl`, torn last line tolerated, statuses queued|running|needs_roman|done|failed|lost|cancelled, `attempts` = number of `running` events, deadline default +45 min). Prototype source kept at `~\AppData\Local\Temp\claude\C--Windows-system32\78968f1c-7f98-4d3e-a2f7-b4e068a165e5\scratchpad\e1\jobs.py` for the lead to copy. Add to CLAUDE.md under "Manager role": "Job ledger: before spawning any worker run `python ~\claude-host\tools\jobs.py new "<title>" --worker <preset> --deadline-min <N>` and put the returned id (e.g. J261029-001) in the brief and the Agent `description`. Set `running` when spawned, `done`/`failed` only after I have checked the report against the goal, `needs_roman` when blocked on him. Never re-spawn a job with attempts>=2: report it to Roman as NEEDS." Benefit: crash/reboot recovery, answerable "what is in flight", attempt counting. Risk: small extra tool calls per job; Haiku forgetting to log (mitigated by C5 hook cross-check).
C2. **Boot reconciliation instead of a chatty boot prompt.** In `boot-claude.ps1` replace the status/footer demand with: "This is an automatic boot notice. Run `python ~\claude-host\tools\jobs.py list` and `... list --stale`. For each open job: if its worker transcript shows a final report, verify it and mark done/failed; otherwise mark `lost` and re-brief at most once (attempts<2); then reply with one line: `Restarted: <reason>. Open jobs: <n>, re-run: <n>, need you: <n>.` Do not run other tools." Plus have the script itself first run `jobs.py list --stale` and embed the output in the prompt (no model tool call needed). Benefit: restart no longer silently drops work. Risk: re-running a half-finished job duplicates effects, hence C3.
C3. **Idempotency rule for outward effects.** Add to CLAUDE.md and both worker presets: "Before any outward side effect (message to Roman or others, git push, PR, publish, purchase request) run `jobs.py effect <job_id> <step-key>`. NEW = proceed, then `effect-done`. DONE = skip. INTENT-ONLY = a previous attempt may have succeeded: check the real state first (e.g. `git ls-remote`, the chat) before repeating." Benefit: no duplicate Telegram/pushes after crashes. Risk: workers forget; limit to the effect types in the Always-confirm list.
C4. **Unattended-wait setting.** Add `"env": {"CLAUDE_CODE_RETRY_WATCHDOG": "1"}` to `~/.claude/settings.json` (and `export CLAUDE_CODE_RETRY_WATCHDOG=1` in any `claude -p` worker script). A usage limit cannot be forced for a test, so verify only that the variable is accepted (start a `claude -p` with it set and `--debug`) and watch what happens at the next real limit. Add one CLAUDE.md line: "If a long job shows no progress, a usage limit may be pending; check `claude agents`/StopFailure events before re-spawning." Benefit: master stops dying on 429/529 and waits for the limit window. Risk: appears hung to Roman; not proven for RC (open question 3). Settings are a config change by the lead, not by this worker.
C5. **Hooks for heartbeat + event log (shared with [[topic-observability]] C1).** `SessionStart` -> write `claude-host\run\master.pid` (the hook script records its parent pid via `os.getppid()`; verify on this host that this is claude.exe and not an intermediate shell) plus a timestamp; `Stop`, `SubagentStop`, `StopFailure` -> `touch claude-host\run\heartbeat.txt` and append to events.jsonl. These are the signals C6 supervises.
C6. **Silent supervisor (needs Roman's OK because it replaces the disabled watchdog).** New task `ClaudeSupervisor` every 5 min, runs `claude-host\tools\supervise.py` (no LLM, no reports). Logic: if master pid from `run\master.pid` is alive AND (no open jobs OR heartbeat age < 30 min) -> exit 0. Else restart `ClaudeHost` (Stop-ScheduledTask, then Start) and append `restart` to `jobs\supervisor.jsonl`. Breaker: if >=3 restarts within 60 min, STOP restarting, write `run\BREAKER_OPEN`, and exit; boot prompt/next owner message mentions it once. Backoff: wait 1, 2, 4 minutes between the three attempts. Also change ClaudeHost to drop `-NoExit` or keep it but let the supervisor own restarts (RestartOnFailure can never fire with `-NoExit`). Benefit: fixes the real gap without reports or the command-line-regex fragility that contributed to the 10-28 restarts. Risk: any restart kills in-flight nested subagents (unknown), so restart only when the heartbeat is stale; first week run in log-only mode.
C7. **Worker preset additions (sonnet-worker and opus-builder).** Add to the rules: "If the brief contains a job id, append one line to `~\claude-host\jobs\<id>\progress.md` at start and about every 10 minutes of work, and write your final report to `jobs\<id>\report.md` as well as returning it. Stop and report PARTIAL after 3 failed attempts at the same step instead of continuing. Never repeat an outward side effect without `jobs.py effect`." Add frontmatter `maxTurns: 80` (sonnet-worker) and `maxTurns: 150` (opus-builder) per manager-setup.md section 6; values are placeholders to tune from the digest. Benefit: partial output is recoverable; runaway guard. Risk: maxTurns truncates legitimately long builds (it returns partial output, resumable with SendMessage).
C8. **Retry/escalation policy text for the manager.** Add to CLAUDE.md "Manager role": "Retry policy: a failed or partial job gets at most ONE re-brief with the specific gap named (and one tier up in model/effort only if the failure was capability, not environment). Same failure twice, or job past its deadline, or three restarts in an hour = stop, set status needs_roman, and tell Roman in one line what is blocked. Default on unexpected state: stop and ask, never improvise outward actions." Benefit: bounded loops; matches Nightcrawler/yurukusa rules.
C9. **Prune and date the instruction files (memory drift).** CLAUDE.md: remove or collapse the Telegram section and voice-note rule (channel removed from boot 2026-10-28), delete the finished "STATUS"/"REBOOT TEST" narrative and the superseded Linux-wake paragraphs, keep one "Linux power" block with a date; add a line "Facts here are dated; if two entries conflict, the later date wins." Move history to `session-notes\`. Benefit: smaller, non-contradictory context for a Haiku manager; fewer stale-instruction errors. Risk: losing context; keep a backup like the existing .bak files.
C10. **Scheduling policy line.** Add to CLAUDE.md: "Recurring or delayed duties go to Windows Task Scheduler running a script or `claude -p` with `--max-turns` and a timeout; never rely on `/loop` or CronCreate for anything that must survive a restart (7-day expiry, session-bound, no catch-up). For catch-up jobs write the staleness rule into the job itself."
C11. **Log rotation.** Weekly (cheap script, no LLM): if `log.md`, `watchdog.log`, `desktop-layout.log` exceed 500 lines/1 MB, move older lines to `log-archive\<name>-YYYY-MM.md`; keep `cleanupPeriodDays` at 30 (or raise to 60 if Roman wants longer replay, projects\ is only ~100 MB). Rotating the daemon log is not supported by a documented setting; check size monthly.
C12. **Approval records (HITL).** When asking Roman a confirm-first question, create the ledger event `needs_roman` with the question, the proposed default, and an expiry ("ask again after 24 h, never act on silence"). On approval, record `approved by Roman (RC message at <time>)` in the job note, then proceed. Benefit: audit trail and crash-proof approvals ([[topic-observability]] C4).

## Appendix: reference design (minimal, files only)
Everything below is derived from the rules above; prototypes of `jobs.py`, `hook_log.py` and `digest.py` were run against real transcripts on this host (see [[topic-observability]]).

### A. Job states and who may set them
```
queued --(manager spawns worker)--> running --(report received AND checked by manager/hook)--> done
   |                                   |--(worker returned PARTIAL/failed, or deadline passed)--> failed | lost
   |                                   |--(worker or manager needs Roman's answer)--> needs_roman --(answer)--> running | cancelled
   '--(Roman cancels)--> cancelled     '--(master restarted, no report found)--> lost --(one re-brief)--> running (attempts=2)
```
- `done` is set only by the manager AFTER comparing the worker's VERIFIED section with the goal (rule 26). A worker never sets its own `done`.
- `lost` = no final report and the worker transcript has no final message; allowed transitions: one re-brief (attempts <= 2) or `needs_roman`.
- Each event line: `{ts, id, status, note}`; job creation adds `title, worker, owner, deadline`; effects are `{ev:"effect", id, key, state:intent|done}`.

### B. Failure matrix (detection -> automatic response -> who tells Roman)
| failure | detection | automatic response | tell Roman |
|---|---|---|---|
| master claude.exe dead | supervisor: pid from `run\master.pid` not alive | restart ClaudeHost (backoff 1/2/4 min), reconcile ledger on boot | one line after restart only if jobs were lost |
| master alive but hung | open job exists and `run\heartbeat.txt` older than 30 min | one restart (same path) | same |
| restart loop | >=3 restarts in 60 min | open breaker, stop restarting, keep logs | yes, once, with the reason |
| RC disconnected (30-min heartbeat) | not detectable from outside RC; local `/remote-control` needed | (open: send keystroke via input.ps1 only if layout enforcer allows; otherwise leave) | cannot (phone cannot reach it) |
| usage limit | StopFailure matcher `rate_limit` in events.jsonl; RETRY_WATCHDOG waits | no new spawns until reset; jobs stay `running`/`queued` | one line when the wait starts if > 1 h |
| API overloaded 529 | Claude Code retries (10x, backoff) | none | no |
| worker stalled | Claude Code stall window (10 min) restarts subagent; ledger deadline | one re-brief, then `failed` | on second failure |
| worker says done but evidence missing | manager check of VERIFIED vs goal; hook cross-check of report file | mark `failed` with gap, one re-brief | only if still failing |
| duplicate side effect risk | `jobs.py effect` returns DONE/INTENT-ONLY | skip or verify externally | no |
| disk filling | weekly rotation script; guard at 2 GB (exists for screenshots) | rotate/delete only whitelisted logs | if > 80% C: |
| PC reboot | boot task + ledger reconcile | as master dead | one line |
| other device unreachable (CachyOS asleep) | worker reports SSH timeout | job `needs_roman` or retry after `linux-power wake` per CLAUDE.md | only if Roman's task needs it |

### C. Supervisor pseudocode (`tools\supervise.py`, scheduled every 5 min, no LLM)
```
state = read(run\supervisor.json)      # {restarts: [timestamps]}
if exists(run\BREAKER_OPEN): exit
alive = pid_alive(read(run\master.pid)) # written by SessionStart hook; never regex command lines
open_jobs = any open job in ledger
hb_age = now - mtime(run\heartbeat.txt)
if alive and (not open_jobs or hb_age < 30 min): exit
recent = [t for t in state.restarts if now - t < 60 min]
if len(recent) >= 3: write(run\BREAKER_OPEN, reason); log; exit
sleep(60 * 2**len(recent))
Stop-ScheduledTask ClaudeHost; Start-ScheduledTask ClaudeHost
state.restarts.append(now); log("restart", reason=alive ? "stale heartbeat" : "process dead")
```
Reset the breaker by deleting `run\BREAKER_OPEN` (Roman or manager after fixing the cause).

### D. Boot reconciliation (what the new master does, ~5 tool calls)
1. `jobs.py list` and `jobs.py list --stale`.
2. For each open job, look for a final report in `jobs\<id>
eport.md` or the subagent transcript (`agent-*.jsonl` whose meta `description` contains the id).
3. Report found: verify against the brief, mark `done`/`failed`. Not found: mark `lost`.
4. If attempts < 2 and the job is safe to repeat (idempotent or effects not yet `done`), re-brief once; otherwise `needs_roman`.
5. One-line reply. No footer.

### E. Overnight policy (quiet hours, e.g. 22:00-07:00 local)
Allowed unattended: read-only checks, ledger reconciliation, bounded retries, rotation scripts, digest generation. Not allowed unattended: any outward message, push, publish, device sleep/wake, deletion outside whitelisted caches. Anything needing those becomes `needs_roman` with a proposed default and is raised in the morning, once.
