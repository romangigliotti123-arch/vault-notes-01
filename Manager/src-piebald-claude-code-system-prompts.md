## Key claims
- Writing subagent prompts (v2.1.235): "Brief the agent like a smart colleague who just walked into the room"; explain what/why, what you ruled out, enough surrounding context for judgment calls; ask for a short response explicitly ("report in under 200 words"); lookups -> exact command, investigations -> the question ("prescribed steps become dead weight when the premise is wrong"); "Terse command-style prompts produce shallow, generic work."; "Never delegate understanding" (no "based on your findings, fix the bug").
- Delegation cost (v2.1.296): "A fresh agent costs more than it looks... both handoffs drop detail, and neither of you can tell what the other missed... Its mistakes come back in the same confident register as its findings, and an agent handed your hypothesis tends to return it confirmed." Do it yourself when it is a handful of tool calls. "if you cannot write a clear one [brief], you do not understand the task well enough to hand it off."
- Restraint (v2.1.215): do not spawn a subagent to review/re-verify work you can verify inline; do not redo delegated work while waiting; "One well-briefed subagent for a large independent chunk is worth more than several loosely-briefed ones".
- Coordinator mode (v2.1.299): workers cannot see the conversation; prompts self-contained; add a purpose statement so workers calibrate depth; state what "done" looks like; for research say "do not modify files"; implementation prompts say "Run relevant tests and typecheck, then commit and report the hash" ("first layer of QA; a separate verification worker is the second layer"); continue vs spawn by context overlap (verify with a FRESH worker; wrong-approach retry -> fresh); "Trust but verify worker reports - a worker's summary describes what it intended to do, not necessarily what it did. ... check the actual diff before relaying success to the user"; verification = "proving the code works, not confirming it exists", try edge cases and error paths, "Investigate failures - don't dismiss as unrelated without evidence".
- Approval relay: when a worker stops at a user-approval gate, spawn a FRESH worker whose prompt quotes the user's exact approval words and the literal approved action; do not SendMessage the approval (no agent message is user consent). Keeps the worker that read untrusted input separate from the one that executes the privileged action.
- Worker side (coordinator-worker-instructions v2.1.271): complete exactly what was asked; do not fix unrelated issues, suggest as follow-ups; stop and report on confusing file state from other workers; "Don't retry the same failed approach more than once"; if ambiguous pick most likely interpretation and note the assumption. Output structure: 1) what you did/found with paths, lines 2) "Summary: one sentence the coordinator can relay". Good: "Added Redis cache implementation. Tests pass, typecheck clean. Committed abc123." Bad: "I looked at files X, Y, and Z."
- Reporting outcomes (v2.1.251): "Report what actually happened, not what you intended... that claim must rest on a result you observed in this session... If you did not check, say you did not check. If any step failed, was skipped, or came back different from what you expected, say so in the first sentence of your report... When you stop before the task is complete, your first line says so plainly and names what is left."
- Agent tool usage notes (v2.1.302): "Trust but verify: an agent's summary describes what it intended to do, not necessarily what it did"; results are not visible to the user, relay yourself; do not poll or sleep for background agents; "Never fabricate or predict them in any format"; tell the agent whether to write code or only research.
- Subagent final message: "report all of your findings directly as your final assistant message... The parent agent reads your text output only - not files". Share absolute paths; snippets only when load-bearing. (Variant: SubagentHandback tool, plain-text endings not delivered.)
- Background job agent (v2.1.286): machine-readable status lines because a classifier reads message text: `result: <one-line headline>` (only completion signal), `needs input: <exactly what>` (only when one human action unblocks and guessing is costlier), `failed: <reason>` (structurally impossible). Before `result:`, "run a sanity check... and say what you checked". "Restate" tool results in own text.
- Workflow subagents return via a schema-validated StructuredOutput tool called exactly once; re-call on validation error.
