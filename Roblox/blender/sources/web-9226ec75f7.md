# web-9226ec75f7

Personal-use research note. Brief quotes only, with attribution; see the original at the URL above.

## Summary
Blender Python API troubleshooting page on script crashes. Core rule: do not hold direct references to Blender data when modifying its container or during undo/redo; re-fetch by index or key. Covers collection re-allocation, undo invalidation, mode switching, removed data, and sys.exit. Generic bpy guidance, not Roblox-specific.

## Claims
- c1: Holding a direct reference to a collection item (e.g. from CollectionProperty.add()) then adding more items can crash Blender; re-fetch by index after modifications. *(doc, high; bpy-scripting-headless)*
- c2: Undo/redo should be assumed to invalidate all ID instances (Object, Scene, Mesh, etc.) and their sub-data. *(doc, high; bpy-scripting-headless)*
- c3: bpy.ops.object.mode_set EDIT/OBJECT re-allocates object data; mesh.polygons etc. must be re-accessed after switching mode or script crashes. *(doc, high; bpy-scripting-headless)*
- c4: Adding vertices/points re-allocates the underlying array; the fix is to add all points at once or re-assign references after adding. *(doc, high; bpy-scripting-headless)*
- c5: After bpy.data.*.remove(), accessing the removed variable raises ReferenceError, but sub-references like mesh.vertices taken earlier may still crash. *(doc, high; bpy-scripting-headless)*
- c6: Setting Object.hide_viewport/hide_select/hide_render rebuilds collection caches; iterate over Collection.all_objects[:] (a list copy) instead of the live iterator. *(doc, high; common-mistakes-fixes)*
- c7: Renaming bpy.data items during iteration re-sorts them; convert the iterator to a list first to avoid skipping or repeating objects. *(doc, high; common-mistakes-fixes)*
- c8: Use the faulthandler module to locate the script line causing a crash, since the crash may be inside Blender's C code. *(doc, high; bpy-scripting-headless)*
- c9: Some Python modules (e.g. argparse on invalid args) call sys.exit(), which closes Blender and looks like a crash; setting sys.exit = None helps locate it for debugging. *(doc, medium; bpy-scripting-headless)*
- c10: Modifying library (linked) data from Python is not blocked; pointing linked data at new local data and then undoing can crash Blender. *(doc, medium; bpy-scripting-headless)*
- c11: Data modified in operators should always get an undo step; missing undo steps cause broken undo stacks and crashes. *(doc, medium; common-mistakes-fixes)*
- c12: Python RNA property callbacks should be fast; calling operators from them is unsupported and can cause undo issues or infinite update loops. *(doc, medium; bpy-scripting-headless)*

## Techniques
- t1: **Index-based re-fetch**: Store indices or string keys, not object refs. Add all items first, then fetch by index (scene.test_items[0]) before setting properties.
- t2: **Re-access after mode switch**: After mode_set to EDIT/OBJECT, reassign polygons/vertices/bones from the object data before use.
- t3: **Snapshot iteration**: Iterate over a list copy (collection.all_objects[:]) or list(bpy.data.objects) when modifying visibility or names.

### Code: Safe re-fetch after container modification (from doc)
```python
first_item = bpy.context.scene.test_items.add()
for i in range(100):
    bpy.context.scene.test_items.add()

# This is safe, we are getting again desired data *after*
# all modifications to its container are done.
first_item = bpy.context.scene.test_items[0]
first_item.name = "foobar"
```

### Code: Re-access polygons after mode switch (from doc)
```python
mesh = bpy.context.active_object.data
polygons = mesh.polygons
bpy.ops.object.mode_set(mode='EDIT')
bpy.ops.object.mode_set(mode='OBJECT')

# Polygons have been re-allocated.
polygons = mesh.polygons
print(polygons)
```

## Quotes (brief, for attribution)
> Do not keep direct references to Blender data (of any kind) when modifying the container of that data, and/or when some undo/redo may happen  (docs.blender.org)
> For safety, you should assume that undo and redo always invalidates all ID instances  (docs.blender.org)

## Contradictions flagged
- Modern undo/redo does not systematically invalidate all pointers; unchanged data may keep valid pointers. (vs The doc's own blanket advice to assume undo invalidates all ID instances)
