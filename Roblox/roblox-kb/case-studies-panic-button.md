# Case study: Panic Button

**Genre:** Casual mobile action (genre not specified in notes)

RoyalDev's mobile-oriented game. Mentions span a prior title, a 'best result' title and a first game, so they may cover several RoyalDev projects sharing this name.

Also referred to as: The Panic Button, Panic button game

## Numbers
- 0.72% D1 retention on the creator's prior game (RoyalDev, self-reported) [G1993]
- ~8,000 visits from ads left running, the speaker's best result (RoyalDev, self-reported) [G1995]

## What creators say about it
- Overly difficult, niche gameplay with no tutorial or reward made kids on mobile walk around and leave. ([RoyalDev 2026-08 0:01](https://youtu.be/RXmiJkaZWV4?t=1), [RoyalDev 2026-08 0:01](https://youtu.be/LpqqLed1dBU?t=1))
- Unclear onboarding and a confusing physical map, plus unpolished presentation, were blamed for 0.72% D1 retention (self-reported). ([RoyalDev 2026-08 0:01](https://youtu.be/LpqqLed1dBU?t=1))
- Building without a plan meant the original idea was lost mid-project and the speaker's first game failed. ([RoyalDev 2026-09 1:24](https://youtu.be/MZ-nsDEVXH4?t=84))
- AI assistance let the speaker build a game in under a week and learn TeleportService through an AI rundown. Verify AI-generated code before shipping. ([RoyalDev 2026-08 6:08](https://youtu.be/erhgduyGzdM?t=368))
- Ads left running untouched produced ~8,000 visits, the speaker's best result (self-reported). ([RoyalDev 2026-08 4:06](https://youtu.be/mLMXeMWmTwU?t=246))

## Transferable patterns
- Add a tutorial and early rewards before adding difficulty, especially on mobile
- Write a short plan and scope before building
- Use AI for fast prototyping, then verify output
- Let paid traffic run long enough to measure before judging a game
