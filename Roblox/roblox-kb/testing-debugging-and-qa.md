# Testing Debugging And Qa

_debugging tools, logging, unit/integration testing, QA, bug triage, release checks._

## Overview
Roblox's official 2026 guidance pushes testing toward automation and wider reach. Regression tests should be automated and saved as files so old features don't silently break, especially in multiplayer games. Device simulators cover many platforms in the cloud, but performance judgments still need real low-end hardware. Early testing (friend access, up to 10 friends) and multi-client views are announced for late 2026, and on-device debugging from Studio for early 2027. Asset Moderation feedback during development should be checked before publishing. Nightly automated iterations need fully automated tests because no manual test can run between them. Existing rules on playtesting, debugging, profiling and real-device checks still stand.

## Rules and findings
- **Playtest after every few small changes, not after a big batch** (multiple-creators): Catching issues early is easier than untangling several changes at once. Stop the playtest after each check and verify changes in isolation before building further. Playtest the full start-to-finish flow after each round, because small changes can have unexpected effects. - **Use Test or Test Here, not Run, when you need an avatar** (multiple-creators): Run does not insert your avatar. Test or Test Here inserts it, so you can interact with scripted content and see animations play. Use Test Here to start from a chosen location. - **Test in the right mode: solo client-server, multiplayer with 2+ players, and SLIM or friend features with multiple clients** (multiple-creators): Because of the client-server model, test in more than one mode before release. Friend testing needs 2 clients plus 1 server (3 Studio instances). SLIM avatars, friends-locator and voice isolation also need Team Test with friends or alts. - **Handle errors defensively: status codes, guards, catch blocks and loader tolerance** (multiple-creators): Retry RESOURCE_EXHAUSTED (429) with backoff. - **Verify tags, trust policies, story flows and reachability in Studio** (multiple-creators): Tags added in Studio persist across sessions but are not guaranteed to persist forever, especially if tagged instances are modified. Put the template back in ServerStorage before testing. Studio always reports Pending for trust policies, so skip the check when IsStudio is true and print the result for each level. Set Workspace.SandboxedInstanceMode = Experimental to debug permissions. Use showAllPlayers = RunService:IsStudio() so locators show all players only in Studio. ## Where creators disagree
- **Whether to test DataStore saves in Studio or in a published build**

- **Where to verify pickup and live behaviour**
  - Itz_FloppyFish (2023, T5766): publish and play on the live game page to verify pickup and respawn.

- **Use of waits to fix bugs**
  - Roblox DevForum (2019, T5064): wait() may hide a bug; use Heartbeat:Wait() or Stepped:Wait() instead, which are at least 2x faster.

- **Where to test monetisation and passes**
  - SimTek Game Development (T11828, Q1226, T11829): Studio grants passes for free and does not keep them after death, so use the live Roblox player.

- **Latency magnitude for testing**
  - Roblox Creator Docs (T14814, N5837): 50-150 ms as the baseline to approximate players.

- **Prints versus breakpoints**
  - GnomeCode (T11458, T11459): add prints at each step to find how far execution gets.

- **Use of emulators or simulators for performance testing**
  - Roblox [OFFICIAL] (T17609): use device simulators for cloud verification across platforms, plus performance checks on low-end hardware.
  - Existing knowledge rule: do not judge performance from Studio or emulators.

## Instructions for an agent using this file
- If a playtest needs an avatar or interaction, then use Test or Test Here, not Run.
- If the feature is multiplayer, friend-, SLIM- or voice-dependent, then test with 2 clients (3 Studio instances) or with friends or alts before shipping; a solo test is insufficient.
- If an 'attempt to index nil' error appears, then add WaitForChild before the access; if an event does nothing, then print inside the handler and check name capitalisation.
- If a bug only appears mid-run, then use breakpoints (log-message or conditional) instead of editing code between runs; use Reload Plugin, not Save, while stepping.
- If replication, ownership or latency looks wrong, then use the Client/Server toggle, Network owners visualisation, and Network Simulator one condition at a time with a zero-value baseline.
- If DataStores fail in Studio, then publish first, enable Studio Access to API Services, and check Output for save errors; for lag, use the 2021 approach of a published build.
- If a purchase flow is tested, then use Studio or a one-player server, not a live account that already owns the pass.
- If an HTTP call returns 429, then retry with backoff; if 500 or 503, then treat as transient.
- If the target is mobile, then test on at least one low-end Android device and run a 10-15 minute thermal session.
- If a stack trace points only to a signal module, then use breakpoints to find the firing signal, or reproduce with task.cancel.
- If a loop or frequently hit line needs inspection, set a conditional breakpoint or logpoint before adding prints.
- If the error is 'attempt to index nil', check name spelling and case, missing returns, and WaitForChild before changing logic.
- If verifying monetisation or persistence, use the live Roblox player with a non-dev account; do not sign off on Studio results alone.
- If measuring performance, use Manual graphics quality 10 with Performance Stats On and report device results separately from Studio numbers.
- If testing race conditions or desync, add 0.5-1 s lag; for everyday baseline, use 50-150 ms.
- If profiling, remove all breakpoints first, because they disable native execution.
- If a shared ModuleScript fires breakpoints in the wrong context, set Trigger At to client, server or edit.
- If the code was agent-edited, playtest it and check Output before adding more changes.
- If a bug cannot be reproduced, record exact steps, try tiny variations, then fix; reproduce before editing.
- If debugging is taking a long time, treat it as the core skill rather than a sign of failure; budget more time for fixing than for writing.
- If a bug only appears with many players or after release, schedule a scale test before shipping.
- If an event or print shows nothing, bisect with prints before editing logic.
- If a feature is broken and the cause is unclear, split it into sub-problems and search each one.
- Before publishing, read the draft/publish reminder and remove any :Mock() or test-only tracking.
- If testing saves, mock ProfileStore and confirm the mock is removed before release.
- If judging mobile performance, profile on a real device over local Wi-Fi, not mobile data or Studio emulation.
- If you need playtesting realism, prefer real testers over AI bots; use bots only for overload tests.
- If you build in-game debug UI, keep it hidden by default and toggle it with a key.
- If a regression risk exists in multiplayer code, automate the test and save it as a file so it runs on later changes.
- If generated unit tests are available, save them to files and re-run them after each change.
- If you need cross-platform coverage, use cloud device simulators, but judge performance only on real low-end hardware.
- If Early testing is available in the account, invite up to 10 age-checked friends of similar ages before publishing.
- If you run nightly automated iterations, make every test automated; manual tests cannot run between iterations.
- If Asset Moderation flags an asset during development, fix it before publishing.
- If a feature (multiple client views, on-device testing) is announced but not live, do not write steps that depend on it; use the existing multi-client and real-device rules instead.
- If a new test item repeats an existing rule, skip it.
- If an AI tool edited gameplay code, playtest death and respawn before reporting the change as done.
- If save or rejoin is broken, fix persistence before building features that rely on saved data.
- If a live update changes announcements or multi-player behaviour, check it on a live server with a second client, including a phone where possible.
- Skip new print-statement advice that repeats 'Confirm an event fires with a temporary print'; only add the removal step if the code is going to production.
- If a feature is gated by a gamepass or ownership, test both the owned and non-owned paths before release.
- If a Studio purchase doesn't grant a pass, delete the pass from inventory to test the non-owner prompt.
- If a feature involves checkpoints or respawn, die after reaching each checkpoint and confirm the spawn point.
- If placement or rotation looks wrong, draw CFrame axes and enable the grid before changing the math.
- If a server function returns early without output, add a print or warn that names the missing values.
