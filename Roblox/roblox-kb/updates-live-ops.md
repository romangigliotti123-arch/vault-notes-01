# Updates Live Ops

_update cadence, events, seasonal content, keeping a live game alive._

## Overview
Live ops on Roblox is a traction-gated discipline. Creators and official Roblox guidance agree that release is the start of live operations. The first 7-14 days after launch are the most feedback-rich window: check feedback daily, fix bugs fast (same-day silent patches), and iterate the core loop. Once a game gains traction, such as home recommendations, move to weekly or bi-weekly content. Without traction, creators advise stopping and starting a new project. Official sources say regular updates and engaged players (100+ highly engaged in 60 days) affect Kids/Select eligibility. Seasons use startUtc/endUtc for countdowns and windows. Keep a public changelog, announce delays, and audit third-party audio and policy changes early. Indie figures are self-reported.

## Rules and findings
- **Run a regular content cadence of 1-2 weeks** (multiple-creators): Ship something (cosmetics, pets, furniture, outfits, event content) every 1-2 weeks, reusing existing systems. Treat it as the base your game multiplies on. Going longer lets the game go stale. Minimum is monthly; weekly or biweekly if the team can manage it. Max 2-3 weeks per cadence release. - **Keep cadence releases to existing systems** (multiple-creators): Don't add new features, currencies or mechanics in cadence drops. Add them in major updates first, which also open new avenues for cadence content. - **Don't drop cadence while building a big update** (one-creator-repeated): Keep cadence running while programmers build the expansion. Otherwise the expansion launches to a shrunken base (illustrative 500 vs 1000 CCU, scaling to 1500 vs 3000). Major updates run about quarterly (alternate modes, content drops, systems). Large expansions run 4-6 months. The 2021 talk suggested big updates every 4-6 weeks (older). Expansion effort is 1-3 months of team resources. Build expansions as evergreen, updatable systems. - **Prefer meaningful, thematic updates over volume** (multiple-creators): Too much content bloats the game and makes players quit or feel they can't keep up. Balance this against releasing too little, which disengages players. Quality per update matters more than volume. Players judge floor-based updates by size. - **Alternate minor and major updates** (multiple-creators): Ship consistent small updates plus periodic big ones. Alternate minor updates (features, items, abilities) with major chapter updates to spread workload. Space content, feature and patch releases apart so risky features don't collide with big launches. Creators and players return for big updates. - **Theme each release** (multiple-creators): A constrained theme (e.g. domestic, fantasy, polar pets) makes ideation easier, marketing simpler and avoids retreading ground. Tie it to other systems (furniture, cosmetics) and cultural references. - **Mix permanent and limited-time content** (multiple-creators): Permanent content gives a long tail. Limited-time content drives urgency and monetisation, and tests ideas. - **Handle seasonal and holiday content deliberately** (multiple-creators): Save seasonal ideas for the right time. Release holiday updates about a week before the holiday and reuse past content. Release about 60% in week one and 40% over the next three weeks. Pick internationally appealing themes. Create your own anniversary or lore holiday to stand out. Plan ahead (5 holiday updates planned). Real-world events give a ready reason for content. Seasonal updates (3 Christmas and 3 Halloween weekly) filled content gaps. - **Run live events as gathering moments** (multiple-creators): Live events at set dates and times draw dense player counts. Major events run every ~2-3 months, built up with smaller updates. The best events change the game without kicking players out. Reported results: Jailbreak events gave over 500% more CCU, Oceans peaked at 550K+ (presenter-reported), and Lunar Overture reached a 160K record with +75.5% average CCU and +84.2% returning users. Events can reactivate lapsed players. - **Trigger events with server-synced time** (multiple-creators): Use the DateTime API with a fixed UTC time rather than tick(), which desyncs across servers. Choose a time suited to your main audience's timezone (the 6am PST trigger drew few players). For event windows use start/stop epoch timestamps so later servers stop the event. Convert dates carefully with the right timezone. The 2020 os.time approach is older. - **Build events cheaply and keep them paced** (multiple-creators): Build events as cutscenes reusing existing modules (sloppy code is acceptable if the map resets). Avoid events that feel dead (a 10-15 minute event with little happening). Lock event content behind in-game timers so you can ship without shutting down servers. Release event content in timed chunks (4 missions, 42 hours apart) paired with a month-long battle pass. Give first-N finishers (first 1,000) limited UGC rewards. Scope to deadlines: Roblox events give about 1 month, so keep them small. ## Checklist
- [ ] Pick a cadence you can sustain and write it down
- [ ] Plan live ops before building the game
- [ ] Plan releases roughly three updates ahead; keep a backlog
- [ ] Ship a small themed drop every 1-2 weeks (monthly minimum)
- [ ] Use existing systems for cadence drops; save new systems for major updates
- [ ] Schedule a major update about quarterly and big expansions every 4-6 months
- [ ] Keep cadence running during expansion development
- [ ] Release on Friday; cut off dev Wednesday night or Thursday midday
- [ ] Build hype on Wednesday; announce the date in advance
- [ ] Set up an Events and Updates entry for each update
- [ ] Start teasing a few months out; post renders/clips 3-7 days before launch
- [ ] Run a 1-2 week in-game countdown for big updates
- [ ] Announce in Discord, Twitter, group, in-game bulletins and with influencers
- [ ] Dedicate the first post-launch week to bug fixes and polish
- [ ] Watch the first 48 hours after each update
- [ ] Monitor metrics, spender balances and feedback; set KPIs before designing
- [ ] Theme every release and save seasonal ideas for the right time
- [ ] Plan holiday updates a week early; release about 60% in week one
- [ ] Run a live event every 2-3 months at a time that suits your main audience's timezone
- [ ] Use DateTime or UTC (not tick()) for event triggers
- [ ] Scope events to about one month of build time and keep them from feeling dead
- [ ] Add end-game systems after day 30 and refresh dailies
- [ ] Buff rather than nerf; ease difficulty over time
- [ ] Plan monetisation six weeks ahead
- [ ] Step back periodically to remove bloat; daily-update in week one if you are a small indie game
- [ ] Set a target cadence: weekly ideal, monthly minimum, and write the cadence into the schedule.
- [ ] Split planned work into minor updates (every 1-2 weeks, or 2-4 weeks on existing mechanics) and major updates (every 2-3 months).
- [ ] Estimate effort for each cadence update and confirm it is under three weeks.
- [ ] Build cadence content on existing systems (maps, pets, quests, weapons, vehicles) and art variants.
- [ ] Sprint Monday and ship Friday if running a weekly rhythm, as one indie team does.
- [ ] Keep a 6-12 month roadmap scoped to team capacity.
- [ ] Schedule at least one week of rest between seasons.
- [ ] Plan seasons around one-month lengths as a starting point.
- [ ] Write each announcement with specific new content, within 60 characters, and no more than one every 3 days.
- [ ] Set notification strings within 99 characters.
- [ ] Define the target KPI for each event before building it.
- [ ] Set start and end dates and reward limits on every reward banner.
- [ ] Keep published events to 10 or fewer ongoing or upcoming at once.
- [ ] For Off-Platform Featuring, submit at least 7 days ahead, target 7-30 day runs, and do not edit after submission; confirm creator is 13+ with a linked email.
- [ ] Announce events in advance and promote both externally and in-game (login pop-ups, UI alerts, lobby).
- [ ] Use configs for live tuning and schedule timed events by switching config values.
- [ ] Use experiments to test feature versions on player groups before full rollout.
- [ ] Add missions with each new feature; consider double XP in the final week of a season.
- [ ] Rotate shop stock and refresh rewarded ad rewards on a set schedule.
- [ ] Set a crash-rate alert and a webhook to Discord, Slack or PagerDuty before each release.

## Where creators agree
- Regular, predictable updates keep a live game alive and stale games lose players (Roblox Creators, Roblox, RobloxOfficial, AlvinBlox, kra_DeZ, Tizzy, Zyonic, Daiorg, SmartyRBX).
- Theming releases and mixing small and big updates is endorsed by multiple official talks.
- Cadence should be sustainable: MiniToon, Bad Business, Jailbreak and 99 Nights all slowed down.
- Time-limited events and countdowns drive urgency and spikes.
- Fix bugs soon after launch and use feedback and metrics.
- Frequent but meaningful updates keep players returning; volume alone is not enough (T3578, T4175, T3636, T4174).
- Announce events and updates in advance and across multiple channels (T4048, T4049, T3930).
- Limited-time events and seasonal content create urgency and drive logins (T3978, T4566, T4630).
- Measure retention and monetization after each update, not just installs or spikes (T4838, T3705, T3807).
- Keep cadence sustainable against real team capacity; burnout and bloat are real risks (T4567, T4624, N1871).
- Consistent post-launch updates keep a game from looking dead: janisjanis01 (T6505, T6090), Duckable (T6101, T6462), rasdev (T6701, T6860), and Roblox Creator Docs (T7218).
- Notifications help bring players back to a game: janisjanis01 (T6431) and rasdev (T6860).
- Frequent updates and new content lift player counts after launch: janisjanis01 (T6575, T6745) and Duckable (T6619).
- Keep updating after launch: Matt The Method (earnings collapsed when updates stopped), VuukStudios (update to extend life), PineappleDev (frequent post-launch updates), and official Roblox guidance all favor sustained updates.
- Respond to user feedback: official Roblox guidance and VuukStudios both say feedback should drive fixes and iteration.
- Consistent timing matters: DevForum post and existing schedule rules both favor reliable, predictable updates.
- Keep shipping content: stopping updates loses players (Last Level Studios T15721, CORSO T16035, Last Level Studios Q1477).
- Every shutdown carries player-loss risk, so restarts should be managed carefully (Last Level Studios T15730, Q1477).
- Stopping or slowing updates hurts a live game's visibility and chart position (RoWatcher, StudioKrew, GamesBeat).
- Weekly updates are cited as a strong default for live games (GamesBeat, RoWatcher, StudioKrew).
- Regular events and recurring content drops are the main way indie teams keep players returning.

## Where creators disagree
- **Frequency versus meaningfulness**
  - RobloxOfficial (2025) and kra_DeZ: update weekly or even daily; stale games shouldn't be rewarded.
  - Roblox Creators (2022-01) and RobloxCreators (2022-12): don't assume smaller, more frequent updates are better; meaningful updates beat frequent ones and you can burn out.
  - kra_DeZ says big content dumps ran him out of ideas, while Roblox Creators note 99 Nights trended up during a six-week hiatus.
- **Cadence length**
  - 2021 Roblox Creators: major updates every 4-6 weeks and monthly minimum.
  - Later talks (2022-2023): major update quarterly and expansions every 4-6 months.
  - Creators vary on weekly versus bi-weekly (Wacky Wizards weekly; MiniToon, Bad Business bi-weekly).
- **Visible bug fixes**
  - RobloxCreators (2021): ship a dedicated bug-fix week to show players you care.
  - Roblox Creators (2022-01): keep bug fixes invisible in larger patches and focus on real content.
- **Daily patching**
  - Tizzy and kra_DeZ: ship daily patches or updates (unverified).
  - Official: keep cadence releases scheduled and plan ahead.
- **Update frequency in the first weeks**
  - Existing knowledge file: update daily in the first weeks (indie, unverified).
  - Roblox Creator Docs: weekly is ideal and monthly is the minimum (T4174, N1917); daily is not recommended as a standing rhythm.
- **Config publish propagation time**
  - Roblox DevForum indie post (N1674, 2025-11): within 5 minutes, or a 15-minute rollout.
  - Roblox Creator Docs (N1750, 2026-10): about 15 seconds to 1 minute with Publish now. The official figure supersedes the indie claim.
- **Minor update interval**
  - Existing knowledge file and Roblox Creator Docs (T4814, N2169): every 1-2 weeks if sustainable.
  - Roblox Creator Docs (T4464, N2039): every 2-4 weeks on existing mechanics. Both are official; the choice depends on team capacity.
- **Minimum update cadence (floor)**
  - Existing file rule: treat monthly as the cadence floor, weekly as ideal.
  - rasdev (T6701, N2853): update weekly, monthly, or every two months; any consistent schedule works. Newer self-reported claim, not a platform rule.
- **Timing of major updates**
  - Existing file rule: ship expansions and major updates on a longer cycle.
  - janisjanis01 (T6433): ship big updates regularly; a major update drew 15.3K CCU and the creator kept a weekly cadence afterward.
  - Duckable (T6619): planned two updates within days after launch to lift player counts.
- **Continue or abandon a weak post-launch game**
  - VuukStudios (T13436, T13632): stop updating and start a new project if the game gets no home recommendations or fails to hook after about 2 weeks of daily updates.
  - Q1412 (VuukStudios): a game is only finished when it's dead; release does not mean finished.
  - Matt The Method (T13176): earnings collapsed once updates and promotion stopped; keep updating and promoting to sustain revenue.
- **Post-traction cadence**
  - VuukStudios (T13436): weekly updates once a game gets home recommendations.
  - VuukStudios (T13755): bi-weekly suits bigger titles; weekly or bi-weekly once traction shows.
- **Adding new content types vs. keeping cadence releases on existing systems**
  - GosuGamers: adding new content types (anomalies, Classes) keeps a horror game fresh (T17432).
  - Existing file rule: keep cadence releases to existing systems.
- **New region vs. improving underused areas**
  - Roblox official listing: ship big drops as named new worlds with counts (T17557, N7309).
  - StudioKrew: fixing underused areas (99 Nights' Biome Refresher) can beat a new region on returns (T17524).

## Instructions for an agent using this file
- If the game is new, then plan daily or near-daily patches in the first week or two, then weekly planned updates, then bi-weekly once stable.
- If the team is small or near burnout, then move to bi-weekly or monthly and keep a backlog; do not copy another game's schedule.
- If a big expansion is in development, then keep shipping cadence drops using existing systems so the base doesn't shrink.
- If adding a new mechanic, currency or system, then put it in a major update, not a cadence drop.
- If scheduling a release, then target Friday, cut dev off Wednesday night or Thursday midday, and announce the date ahead.
- If hyping an update, then run a 1-2 week countdown, post small teasers 3-7 days before, and avoid teasing 6-8 months out.
- If building a live event, then trigger it with DateTime at a fixed UTC time that fits your main audience, keep it long enough not to feel dead, and avoid server shutdowns.
- If a holiday is coming, then release about a week early, put about 60% in week one, reuse past content, and favour internationally appealing themes.
- If a feature threatens the economy, then remove or fix it despite objections; prefer buffing underused items over nerfs.
- If citing indie CCU or revenue claims, then label them self-reported and prefer official statements.
- If the team cannot ship at least monthly, flag the schedule risk and plan a recovery phase rather than going silent.
- If an update needs more than three weeks of effort, split it or move it to the major-update tier (every 2-3 months).
- If an announcement is needed sooner than three days after the last one, combine it with the pending announcement; keep text within 60 characters and notifications within 99.
- If an event would exceed 10 published ongoing or upcoming events, end or retire one before publishing another.
- If submitting for Off-Platform Featuring, submit at least 7 days ahead and do not edit after submission.
- If the event goal is unclear, define the target KPI (e.g. DAU) before building anything.
- If a metric is lagging, target the next update at that metric (e.g. D1 or D7 retention) and check it after release.
- If an update severely hurts metrics, roll back first, then profile with Developer Console, Script Profiler and MicroProfiler; set a crash-rate alert and webhook before any release.
- If a seasonal update is being rushed under deadline pressure, scale it down rather than ship a weak version.
- If a value needs tuning, prefer a config change over a republish, and test feature versions with experiments first.
- If the update changes the player data format, restart all outdated servers instead of relying on bleed-off (T9620).
- If the update is non-disruptive, keep the default migration and accept that versions may split for a while (T9619).
- For time-sensitive releases, deploy content hidden behind a config, then flip the value (T9621, T8936).
- Before publishing, test the update and monitor errors and crash rate in the first minutes; roll back severe regressions (T6415, T6627).
- When planning the next update, use a pre-update follow notification to bring players back (T6431, N2713).
- For events and rewards that need no code change, use the LiveOps dashboard rather than republishing (T7532).
- For holiday or month-long offers, use a FixedTime bundle that ends at a set UTC time (T7813).
- Deactivate leaderboards instead of deleting them to preserve data (T9006).
- For UGC items, limit post-publish changes to fixes; do not redesign items after publishing (T9594).
- Verify tool names and defaults against current Creator Hub docs; treat 2019-2023 numbers as possibly outdated, and poll Open Cloud async operations until done is true (T8338).
- If a game has just launched, plan a 7-14 day window of daily feedback checks and fixes before judging the idea.
- If a bug is severe, ship a same-day silent patch and add it to the changelog.
- If a game shows traction (for example home recommendations), move to weekly or bi-weekly content updates.
- If a game shows no traction after the post-release window, flag it for a continue-or-abandon decision instead of forcing more updates.
- If pursuing Kids/Select eligibility, track highly engaged players over 60 days and keep the game actively maintained.
- If an update depends on third-party audio, run Audio Discovery on the published place and start review early.
- If a season is planned, set startUtc and endUtc before launch.
- If the team plans a 17+ conversion, warn that Team Create members will be removed.
- If a group transfer is completed, re-release the game publicly or it stays hidden.
- If a breaking change is planned, cap it at once per week and announce it a day ahead.
- If a game has been dormant, prioritise shipping an update to it before building a new game.
- If a restart is needed, use a soft-shutdown flow with a lobby and TeleportService and avoid hard shutdowns.
- If a major update is planned, staff it with specialists rather than the existing core team.
- If an old feature is being re-released, rebalance it and gather feedback first.
- If a new player is churning, weigh onboarding fixes against new-content work.
- If the team is about to run ads, confirm fresh content, icon and thumbnail are ready first.
- If the game receives harsh critique, ship a targeted update that addresses the specific complaints rather than a generic one.
- If a game's chart position is falling and it has not shipped content recently, recommend a content drop before adding more events.
- If a game is anime-tied, recommend timing a major update to a season launch, and label the claim as unverified.
- Treat indie figures (GGAID, RoWatcher, GamesBeat) as directional, not benchmarks.
- Cite Roblox official listings as platform ground truth for what a game announced, not for performance.
- Do not present a long seasonal event as a fix for retention; pair it with a content drop.
- When a rule conflicts (new content types vs. existing systems), propose a small test release and measure, rather than picking one side.
- When a Roblox roadmap date is stated, treat it as provisional and re-check it before committing a live-ops date to players.
- When a live game underperforms, consider bundling new characters, items, visuals and fixes into one major update before adding small drips.
- When an outage happens, post a status update during downtime and a confirmation on return, rather than going silent.
- When a Roblox design concern is raised, respond with proposed changes early rather than waiting for enforcement.
- Label indie outcomes (self-reported) separately from official Roblox figures when citing them.
- If a game has a multi-month gap between major content drops, prioritise cheap recurring systems over starting another large build, and say so in the schedule.
- If an admin-triggered event spikes concurrency, check the sustained baseline at 24-72 hours before counting it as a success.
- If the user asks to edit a game published before the age-verification change (per T18685), limit edits to essential changes and warn that edits may trigger mandatory age verification.
- If the user asks for an update plan, include one visible new hook (arena, pet or mechanic) and at least one rare unlock (T18718).
- If the user asks about session length or idle play, suggest a timed random event on a ~30-minute loop (T18600), and recommend measuring against the baseline before keeping it.
- Do not treat single-creator, self-reported items (T18600, T18718, T18685) as established fact; present them as creator practice unless confirmed by official docs.
- If advising on a relaunch of old content, cite the greatest-hits and voting rule (T18959) and label it as indie, self-reported.
- If advising on a limited-time reward, consider never-again badges (T18743) only when the event has a firm end date.
- Do not present non-Roblox benchmarks (N8161, N8162) as expected Roblox outcomes.
