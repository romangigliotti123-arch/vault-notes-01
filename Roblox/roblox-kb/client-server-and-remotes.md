# Client Server And Remotes

_client/server model, replication, RemoteEvents/Functions, network ownership, latency, server authority patterns._

## Overview
Client/server knowledge centres on server authority: clients send validated inputs or intents, the server owns state, rewards and physics, and replication carries server truth. The newest material (2025-2026) shifts toward engine Server Authority with BindToSimulation, InputAction polling and GetTouchingParts for rollback-safe gameplay, while older indie tips on hand-built remotes, client ownership and Touched remain as tradeoffs. Practical guidance covers remote safety (pcall, timeouts, batching, payload size), replication primitives (attributes, replicas, streaming), late-joiner sync and deliberate ownership. Typical latency is 100-300 ms, so plan for at least one round trip. Official docs override older community workarounds.

## Rules and findings
- **Make the server the authority and validate every client value** (multiple-creators): Clients can send any value, type or structure to a RemoteEvent or RemoteFunction. Before applying an action, check existence, ownership, range, team, inventory space, funds and types. Clamp requests. Run the same validation code on client and server so the client can predict and the server can mirror it. Reject and resync on failure. Keep server code out of clients. - **Predict locally, then reconcile with the server** (multiple-creators): Let the client act immediately (animation, UI, equip preview), then ask the server to perform the action. Be ready to resync when the server rejects (for example, removing an item the player never had). Show immediate local feedback while waiting so actions do not look stuck. For simulation code, use Server AuthorityMode with PredictionMode rollback and deterministic ability callbacks; enable the listed workspace flags before use. - **Send minimal identifiers and let the server look things up** (multiple-creators): Send only an action name, object name, target CFrame or a server-owned reference such as the equipped gun. The server must find the object itself and check it exists and is equipped. Do not send origin positions from the client except for shot checks. For grabbing, the server checks the object is not held by another player and cancels the grab if it is. - **Keep hit detection, damage and tool activation on server with client input** (multiple-creators): Tool Equipped, Unequipped and Activated events only work in LocalScripts. - **Use RemoteEvents for one-way signals and RemoteFunctions for client-to-server results** (multiple-creators): RemoteEvents are fire-and-forget. Use a RemoteFunction (InvokeServer / OnServerInvoke) when the client needs a returned value, such as spins, purchases, placement or equip. Do not use RemoteFunction:InvokeClient: it can error, throw if the client disconnects, or yield forever. Use RemoteEvents for server-to-client UI and notifications. A get-from-server call backed by a RemoteFunction is the read pattern. - **Enforce remote direction and the player-first signature** (multiple-creators): Design each remote with a fixed direction (client-to-server or server-to-client). - **Serialize compactly and validate schema** (multiple-creators): Convert dictionaries to arrays for remote payloads to avoid per-key string overhead; hardcode field order in a shared PackFormat module. - **Respect remote payload type limits** (multiple-creators): Functions, metatable-based objects and ServerStorage or client-created instances in remote arguments arrive as nil. Metatables are lost. - **Use UnreliableRemoteEvent for continuous non-critical data** (multiple-creators): UnreliableRemoteEvent suits continuously changing data. Payloads over 1,000 bytes may be dropped. Connect handlers before firing: a RemoteEvent queues messages with no handler (limited by count and memory; overflow errors), but an unreliable one discards them immediately. Unreliable messages are dropped when throttled; RemoteEvent excess is delayed. Include a timestamp or sequence number and ignore messages older than the latest handled. Skip updates without leaving stale state. - **Do not assume ordering across remote types or with property changes** (multiple-creators): Avoid relying on RemoteEvents for state ordering: they can arrive before or after property and attribute changes. - **Plan physics around network ownership and anchored state** (multiple-creators): Anchored BaseParts are always server-owned and cannot be reassigned, so plan physics mechanisms around unanchored parts. - **Run cosmetics, VFX, animation and audio on the client** (multiple-creators): Create VFX on the client via FireAllClients or a short string like SpawnParticle, not server-created particles. ## Checklist
- [ ] Identify every remote and mark it client-to-server or server-to-client; fire only in its direction (T9136).
- [ ] Validate every client argument on the server for type, existence, ownership, range and cost before mutating state (T7460, T9721).
- [ ] For each RemoteFunction, return a success boolean and assign only one OnServerInvoke callback (T5353, T9956).
- [ ] Use RemoteFunctions only for client-to-server results; use RemoteEvents for server-to-client notifications and UI (T9955).
- [ ] Put remotes in ReplicatedStorage and route them through one typed network or SerDes module (T9957, T6387, T5730).
- [ ] Add per-player rate limits (last-fired timestamp, 0.1 s example) and kick or drop spam (T5610).
- [ ] Estimate payload per second and keep it under roughly 25 kB/s, with half reserved for Roblox replication (T5417, N2330).
- [ ] Send deltas, changed items and arrays, not whole tables; pack frequent data or use buffers (T5127, T5728, T6261).
- [ ] Use UnreliableRemoteEvent for continuous data; keep payloads under 1,000 bytes and include sequence numbers (T9958, N3937, T9959).
- [ ] Connect handlers before firing remotes or unreliable messages will be lost or queued (T9961).
- [ ] Do not assume ordering between remotes and property/attribute changes; add sequence numbers when order matters (T7869, T9960).
- [ ] Run VFX, animations, tweens and sounds on clients; send only the trigger and location (T5593, T8278, T6262).
- [ ] Never tween or animate server-side objects; the replicated property changes every frame (T8278).
- [ ] Keep the first-person view model local to the camera, not parented to the character (T4999).
- [ ] Interpolate look or tilt on the server from throttled (~0.1 s) updates rather than per-frame remotes (T5001).
- [ ] Validate weapon hits on the server: origin near character, hit near part, no walls between, with latency tolerance (T7469).
- [ ] Keep server-only data in ServerStorage or ServerScriptService; never in ReplicatedStorage (T5491, T8134).
- [ ] Replicate player profile data with ReplicaService or a generic module; mark sensitive keys private (T5578, T9850).
- [ ] Call SetValue on replicated state alongside saved-data changes so UI matches the server (T5579).
- [ ] Process purchases on the server: check product, balance and eligibility, then deduct or grant (T4983, T6377).
- [ ] Use WaitForChild with a timeout for remotes, modules, tool children and runtime-created instances on the client (T5909, T8579).
- [ ] Use LocalScripts for camera, input, UI and tool activation; use server Scripts for authoritative logic (T7659, T9096).
- [ ] Use Script.RunContext Client when a script must run on each client rather than in a tool or starter folder (T9883).
- [ ] Disconnect connections with Disconnect(), Once() or Trove when no longer needed (T5500, T5738).
- [ ] Keep cloud, secret, data and messaging API calls in server scripts only (T8939, T10257).
- [ ] Pick the model per game: competitive shooters, racing, sports and combat should evaluate engine Server Authority first.
- [ ] Under Server Authority, read input by polling InputAction.GetState in BindToSimulation, not Changed/Pressed events.
- [ ] Under rollback, detect contacts with GetTouchingParts in BindToSimulation rather than Touched.
- [ ] Connect RemoteEvent listeners before any server fires; use WaitForChild with exact remote names on the client.
- [ ] Wrap every client InvokeServer in pcall and define a fallback return value.
- [ ] Wrap every server InvokeClient in a task.delay timeout of about 5 s.
- [ ] On PlayerAdded, send current world state (weather, timers, camera lock) to that player only.
- [ ] Batch related updates into one remote or one table per frame instead of many small remotes.
- [ ] Send shot origin, direction, synced timestamp and shot ID; have the server rewind and deduplicate.
- [ ] Throttle directional sends with a dot-product check and a trailing delayed send.
- [ ] Replicate state via attributes server-to-client; send client intents through a single RemoteEvent.
- [ ] Create and modify Replicas only on the server; call RequestData once on the client and Subscribe players.
- [ ] Grant purchases in ProcessReceipt; reward handlers return true only when actually granted.
- [ ] Verify group membership on the server with GetGroupsAsync after the join prompt.
- [ ] Destroy server-owned objects to unload them rather than reparenting.
- [ ] Keep ownership deliberate: server-own NPC roots, avoid frequent SetNetworkOwner churn.
- [ ] Send round-end results (winning team, each client's own team) in the event payload.
- [ ] Test with Test > local server, one player and two instances, changing things on each side to see what replicates.
- [ ] Put each new server feature behind a server-side flag that defaults to off.
- [ ] Ramp a new flag 1% → 5% → 10% → 50% → 100%, watching crash rates at each stage.
- [ ] Keep a kill switch: turn the flag off immediately if crashes spike.
- [ ] Assign each RemoteFunction variable a name different from its OnServerInvoke handler function.
- [ ] On CharacterAdded, fire a RemoteEvent so clients remove or rebuild custom PlayerGui.
- [ ] Check ResetOnSpawn before assuming PlayerGui persists across respawns.
- [ ] Pair enter/exit events with a periodic server sweep that forces exit for stale players.
- [ ] Do not make server logic depend on instances created in a LocalScript.
- [ ] Make player-data changes in server-side ProximityPrompt.Triggered handlers, not in client code.
- [ ] Keep turret, aim and AI targeting on the server even when it costs performance.
- [ ] Give server-side timing windows for parry and dodge inputs enough tolerance for latency.
- [ ] Do the heavy one-time indexing on the server, then have clients fetch chunk data via RemoteFunction.
- [ ] Keep Charm atoms server-side and replicate them when state must live outside components.
- [ ] Explicitly require server validation when AI tools generate remote code, since they may not add it unprompted.
- [ ] For async turn-based games, request push-notification opt-in and fall back to in-game turn indicators when declined (T17675).
- [ ] For competitive games, combine server authority with custom matchmaking to control match composition (T17600, indie, self-reported).
- [ ] Before shipping offline-capable features, audit every economy value stored on the client and move validation to the server (T17635).
- [ ] Apply cosmetics on the server in PlayerAdded and CharacterAppearanceLoaded so they reapply on respawn (T17778).
- [ ] Before honoring a client sprint or similar action, check server-side health and alive status (T17891).
- [ ] Confirm the generated RemoteEvent exists and validate its input on the server (T17891).
- [ ] Before a teleport, fire a server-to-client RemoteEvent so the client can show a transition GUI.
- [ ] Use separate start and stop RemoteEvents for toggle actions such as sprint; the server owns the state change.
- [ ] Before placing an item on a client request, verify PlayerData exists, the item type is valid, and the count is at least 1.
- [ ] Use Players:GetPlayerFromCharacter in shared server handlers (such as humanoid death) to identify the player.
- [ ] Clone template tools to give them to players; do not move the source copy.
- [ ] Use Camera:ViewportPointToRay for mouse position instead of the deprecated Mouse object.
- [ ] Confirm RemoteEvents referenced by AI-generated scripts exist in ReplicatedStorage before testing (low-advice source).
- [ ] Call PromptGamePassPurchase from a LocalScript and pass the local player.
- [ ] In a server Script, connect MarketplaceService.PromptGamePassPurchaseFinished and check player, gamepass ID and wasPurchased before granting.
- [ ] Key gamepass ownership checks on player.UserId, not player.Name.
- [ ] Before moving a drop or pickup to the client, confirm the reward is granted only after a server-side validity check.
- [ ] Do not set Anchored on tools a character is holding; check for ground-clipping or stuck characters when testing tools.
- [ ] Treat client-side pickup or drop visuals as cosmetic, and keep reward state in server containers.
- [ ] Replace direct game.ServiceName references for non-main services with game:GetService('ServiceName').
- [ ] If a script throws 'is not a valid member of DataModel', check for direct service access and switch to GetService.

## Where creators agree
- All creators agree the server must validate client requests; the client cannot be trusted (T4920, T7460, T5357, T5122, T9954).
- All creators agree cosmetic VFX, effects and animation belong on clients and should not be replicated from the server (T5593, T5727, T6262, T8278, T5840, T8762).
- Creators agree remotes should sit in ReplicatedStorage and be accessed through a wrapper or typed module (T5350, T9957, T6387, T5358).
- B Ricey, Crusherfire and the official docs agree on using WaitForChild for remotes and runtime-created instances on the client (T5909, T5862, T7223, T8579).
- Creators agree on using RemoteFunctions when the client needs a return value (T5352, T5908, T5603, T5353).
- Indie DevForum and Crusherfire agree on compact serialization and bandwidth discipline (T5417, T5728, T6261, T5729).
- Official docs and indie creators agree on rate limiting per player and gatekeeping (T7471, T5610, T9150).
- The server owns authoritative state; clients only send requests and render replicated results.
- Validate every remote argument on the server, including the Player argument, and never trust client-supplied instances or amounts.
- Use RemoteEvents for fire-and-forget messages and RemoteFunctions only when the client needs a reply.
- Run cosmetics, VFX, sound and UI-only effects on the client; the server validates and handles hitboxes.
- Late joiners must be sent current client-run state explicitly.
- Replicated attributes and objects are the preferred way to share state, not custom remote chatter.
- Client-to-server attribute writes do not replicate; server-to-client does.
- Touched is exploitable when driven by client physics and should not carry gameplay under rollback.
- Roox4 (T16203), RoyalDev (T16621) and Amora (T16026) agree that core gameplay logic and data changes belong on the server. Client-side versions cause desync or can be manipulated, so client values are never trusted.
- Several 2025-2026 sources reinforce that latency and server timing must be designed in, not left to chance (T16395, T16203).
- T17600 (indie, self-reported) and T17635 (official) both place competitive and economy trust on server-side validation, consistent with the existing server-authority rules.

## Where creators disagree
- **Scope of WaitForChild on the client**
  - Crusherfire (Q954): only needed for instances in ReplicatedFirst local scripts or instances created during runtime.
  - B Ricey (T5909) and official docs (T7223, T8579): use WaitForChild on remotes and shared modules on the client, since they may not exist yet when the script runs.
  - Resolution: use it for remotes and modules anyway; it is harmless and matches official guidance.
- **Server-side animation and character positioning**
  - DevForum (T5604): handle character positioning and animation playback on the server so both characters replicate to all clients.
  - Crusherfire (T6262) and official docs (T8278, T8272): never tween or play animations on the server; run them on clients and create Animators locally.
  - Official and Crusherfire guidance is newer and more specific; prefer client-side animation with server state.
- **Single consolidated network module vs separation of server and client logic**
  - B Ricey (T5358, N2318) and Crusherfire (T6387): route everything through one RemoteEvent, one RemoteFunction and a typed wrapper.
  - Official docs (T9720): avoid a unified module containing both startServer and startClient logic; it exposes server code to clients. Acceptable only for a high-touch network module.
  - DevForum (Q937, T5730): separate remote logic from game logic with a SerDes layer.
- **Damage passed as a remote parameter**
  - DevForum author (Q913): disclaimer admits passing damage as a parameter is a beginner simplification and should not be done.
  - Official docs (T7460, T9721) and DevForum (T4920): the server must validate and own damage; never trust a client-sent damage value.
  - Resolution: do not pass damage from the client.
- **Manual network ownership control**
  - DevForum (T5197): SetNetworkOwnership() to client for smooth dragging.
  - Official docs (T8051, T7775): the engine assigns ownership of simulated parts; anchored parts are always server-owned.
  - Resolution: check the current network ownership guide before hand-setting ownership; validate drag range on the server (N2285).
- **RemoteFunction direction**
  - Indie and B Ricey: use RemoteFunction for return values (T5352, T5908).
  - Official docs (T9955): avoid RemoteFunction:InvokeClient for server-to-client calls because it can error or yield forever.
  - Resolution: RemoteFunctions are safe for client-to-server; use RemoteEvents for server-to-client.
- **Remote minimization vs more remotes for organization**
  - Official docs (T9718): minimise remote usage; prefer player data replication, attributes and tags first.
  - B Ricey (T5358): consolidate into a single RemoteEvent and RemoteFunction behind a wrapper.
  - Both can hold: consolidate when remotes are necessary, but prefer replication primitives when state can be replicated.
- **Who owns physics and parts for responsiveness**
  - Roblox DevForum (T10664, T11334), Roblox DevForum (T12059) and Roblox Creator Docs (T15631) favour transferring ownership to clients for smooth or responsive motion, noting it is insecure in multiplayer (T10664) or needs clamping (T11334).
  - Suphi Kaner (T11611, T12611), GnomeCode (T13182) and Roblox Creator Docs (T15632) favour server ownership or avoiding frequent ownership changes, since clients can cheat and changes cost physics time.
- **Where hit detection runs**
  - Roblox DevForum (T12159) has clients detect hits against server-sent hitbox data and report back via RemoteEvent, trading slight input delay for smoothness. This conflicts with the server-owned hit rule in the existing file.
  - ArTheDev (T13906) and Roblox DevForum (T13127) keep the server authoritative but accept client aim and timestamps, rewinding and deduplicating shots on the server. This is a hybrid.
- **Creating instances on the client**
  - Roblox Creator Docs (T14104) says client-side solid modeling does not replicate; ByteBlox-style guidance and Roblox DevForum (T13084) say create new instances only on the server during the beta.
  - Roblox Creator Docs (T15148) recommends instance stitching on the client for instant visibility with no server round trip, and Roblox DevForum (T12208) suggests client-created predictable projectiles.
- **Touched for gameplay**
  - Roblox DevForum (T10866) calls Touched a tradeoff for ping compensation rather than a free solution.
  - Roblox DevForum (T13107) says avoid Touched under rollback and use GetTouchingParts in BindToSimulation instead.
- **Remote payload limits**
  - Roblox DevForum (T10924) says keep Sent and Received under 5-10 ms, citing 50 as a ceiling; the unit is unclear.
  - Roblox DevForum (T11942) says keep buffers under 50 MB; the two numbers measure different things and should not be mixed.
- **Where Server Authority is toggled**
  - Roblox DevForum (T13095) says Workspace > Server Authority > AuthorityMode = Server.
  - Roblox DevForum (T13210, T13286) say set the AuthorityMode attribute on Workspace. Both may be true for different builds, so verify in Studio.

## Instructions for an agent using this file
- If an action changes game state (currency, inventory, placement, damage, pickup), then validate on the server (existence, ownership, range, cost) before mutating; never accept client-sent results.
- If the client needs a return value from the server, then use a RemoteFunction (client-to-server) that returns a success boolean; for server-to-client calls use RemoteEvents instead of InvokeClient.
- If a value changes continuously (look angle, tilt, position), then throttle sends (about 0.1 s), use UnreliableRemoteEvent, keep the payload under 1,000 bytes, and interpolate on the receiving side.
- If a payload is large or frequent, then send deltas or changed items, use arrays and packed fields (or buffers), and estimate kB/s against a 25 kB/s self-budget.
- If a visual effect, animation, tween or sound is cosmetic, then run it on the client; the server sends only a trigger and a location (same CFrame/Position for everyone).
- If a server rejects a client action, then resync the client UI from authoritative state and keep the local feedback reversible.
- If the client reads a runtime-created instance, remote or shared module, then WaitForChild with a timeout and nil-check before use.
- If a script must control only one player (camera, input, UI, push-to-talk), then use a LocalScript or RunContext Client; keep authoritative logic in server Scripts in ServerScriptService.
- If the data should be hidden from other clients or used for cheat-sensitive logic, then keep it in ServerStorage/ServerScriptService or a server module and replicate only what the client needs.
- If order matters between remotes or between a remote and an attribute/property change, then add a sequence number or send both through the same remote type; do not assume arrival order.
- If the game is competitive (shooter, racing, sports, combat), evaluate engine Server Authority first and have clients send only inputs.
- If running under rollback or Server Authority, do not gate gameplay on Touched; use GetTouchingParts in BindToSimulation and store prior contacts in attributes.
- If you add a new remote, first check whether an attribute, a replica, or a batched existing remote can carry the data.
- If you call InvokeServer, wrap it in pcall and return a safe fallback; if you call InvokeClient, add a timeout around it.
- If a server event fires on join or on a replicated chunk, connect listeners first and handle existing children with GetChildren().
- If a client needs to see late-created state, send the current value on PlayerAdded to that player only.
- If you write shared geometry or models, generate them on the server; client-only instances will not replicate.
- If you build cosmetic projectiles or VFX, create them client-side, relay only important events, and validate hits on the server.
- If a sync bug appears only on other clients, check whether the source is a Motor6D transform or a client-owned part before blaming the remote.
- If a figure comes from 2022-2024 indie posts (byte costs, argument limits, timing), flag it as unverified and re-check.
- If the task adds a new server feature, ship it behind a default-off server flag and ramp it in stages.
- If you write a RemoteFunction, give its variable a different name from the OnServerInvoke handler.
- If a LocalScript creates objects, do not write server logic that depends on them.
- If an interaction changes player data, route it through a server-side ProximityPrompt.Triggered handler or a validated remote handler.
- If a feature involves timed client inputs (parry, dodge), widen the server-side window to cover latency.
- If the task moves computation to clients for performance (AI, turrets, aim), keep authority on the server and flag the desync trade-off.
- When generating remote code with an AI tool, explicitly require server-side validation of every client value, because generated code often omits it.
- If the task needs respawn-safe client UI, fire a server event on CharacterAdded and clean up on the client side.
- If state must live outside components, consider Charm atoms with replication instead of ad hoc remotes.
- If your code relies on objects a client created, do not assume the server or other clients can see them.
- If a game is competitive and Server Authority is available, enable it, then use client prediction for responsiveness and let the server simulate and decide outcomes.
- Treat Server Authority as shipped (per 2026-09 official statement), not experimental, when answering questions dated after 2026-09.
