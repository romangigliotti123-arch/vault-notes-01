# Optimization And Streaming

_memory, instance streaming, rendering cost, mobile and low-end performance, profiling, lag diagnosis._

Evidence base: 809 extracted items from 223 videos by ArTheDev, B Ricey, BloxxedDev, BubuTheDev, ByteBlox, Crit, Crusherfire, Cumin, Duckable, Emancyphur, FrenkyRBLX, GamesBeat, GnomeCode, JustDucksey, Last Level Studios, Lnor Roblox, PineappleDev, RoBuilder, Roblox, Roblox Creator Docs, Roblox DevForum, Roox4, SimTek Game Development, Suphi Kaner, TechSpectrum, TheNexusAvenger, Yann, janisjanis01 (2016-09-05 to 2026-10-30). Roblox changes quickly: check the date on each source and see Date context below.

## Overview
Sources converge on budgeting before optimising: full-game memory around 400-500 MB, CPU frame time 15-20 ms, phone GPU 13-20 ms, and sent network under 50 KB/s with received traffic watched too. Mobile crashes are usually memory problems, so check memory first. Per-frame and per-part logic is the main code cost; replacing per-wheel raycasts with one raycast is the clearest example. Large worlds can use native streaming or, in one 2020 case, custom frame-time-throttled reparenting. Native Instance Streaming is now preferred over hand-rolled streaming. Newer additions cover transparency at 0 or 1, SpotLight shadows, SLIM defects, and object pools.

## Rules and findings
- **Measure before optimising** (multiple-creators): Profile first: Performance Summary (Ctrl+Shift+F5) for FPS, MicroProfiler (Ctrl+Alt+F6; pause with Ctrl+P) for frame spikes vs steady cost, Developer Console (F9, Memory tab) for memory, Script Profiler for per-script CPU, Luau heap snapshot diffs for leaks. Re-check after each fix. - **Judge performance on a real client on low-end hardware** (multiple-creators): Studio skews stats. Evaluate on a client with Graphics Mode manual and max quality, and test on low-end phones. A powerful PC barely ran one game; ~65% of players are on Android. Run a 10–15 min mobile session to detect thermal FPS decline. - **Enable instance streaming if the game can handle it** (multiple-creators): StreamingEnabled is the highest-impact way to cut client memory and join time (only the area near spawn replicates). Tune StreamingMinRadius (default 64) and StreamingTargetRadius (default 1024) and StreamOut/IntegrityMode settings (T8571) if OOM persists. Test with radius 64 while traversing, teleporting and revisiting areas; bugs appear at stream edges. Older 2021 content-streaming advice is the same idea. - **Set Persistent or Atomic on models that streaming breaks** (one-creator-repeated): Use ModelStreamingMode Persistent for content that must always be accessible (never streams out), Atomic when scripts need all child parts together. - **Do not desync streamed instances on the client** (multiple-creators): Local reparenting, Clone into Workspace, or client Destroy breaks replication and streaming; treat as exception. - **Choose CollisionFidelity by cost, cheapest first** (multiple-creators): Box is cheapest, then Hull, then Default, PreciseConvexDecomposition costliest and rarely justified. - **Disable collision, touch and query on non-interactive parts** (multiple-creators): For grass, vines, mushrooms, leaves and bushes walk-through: CanCollide and CanTouch off, CollisionFidelity Box. CanTouch and CanQuery cause lag when many build up; CanQuery is only exposed when CanCollide is off. Raycasts and Region3 still hit parts with CanQuery on. Keep CanTouch only where touch events are scripted. - **Anchor parts that do not need physics; use Adaptive stepping** (multiple-creators): Unanchored parts force extra physics work. Anchor static props and static NPCs. Set PhysicsSteppingMethod to Adaptive (60/120/240 Hz as needed; fixed mode runs 240 Hz, 4x per frame). - **Cut shadow and light cost** (multiple-creators): Each shadow costs render resources. Disable CastShadow on tiny or hidden detail, items in shadow, and unseen items. Disable Light.Shadows where unneeded, limit range and angle, cull lights room by room. Point lights cost more on low-end devices; merge small nearby lights. Shadows are disabled below graphics quality 4. - **Limit semi-transparent and overdraw-heavy layers** (multiple-creators): Overlapping transparency causes overdraw (planter example: hundreds of thousands of overdrawn pixels). Merge several transparent parts into one union, avoid stacking layers over large screen areas, and do not put decals or textures on fully transparent objects (mobile problems). - **Batch remote traffic, use small data types, and diagnose network separately** (multiple-creators): Batch many small remotes into fewer large packets (less CPU, memory, network). Spread clones across several frames or batches, and pair with object pooling. This is a concrete case of the general rule to spread expensive work across frames. Sources: [janisjanis01 2025-06 9:49](https://youtu.be/W9JYImC0FBg?t=589), [janisjanis01 2025-06 9:49](https://youtu.be/W9JYImC0FBg?t=589). Newest source 2025-06-15.
- **For small-space games, swap whole sections instead of streaming gradually** (single-mention): GnomeCode (indie, self-reported) suggests that instantly swapping the map to the next section at transition points keeps a small-space game feeling continuous. Treat this as a design option for linear, discrete-section games. Measure the swap hitch on a low-end device before adopting it. Sources: [GnomeCode 2020-06 34:09](https://youtu.be/Z74HM6xcsBE?t=2049). Newest source 2020-06-26.

## Checklist
- [ ] Record baseline FPS (Performance Summary), frame-time spikes (MicroProfiler), and memory (Developer Console) on a low-end client before changing anything.
- [ ] Enable StreamingEnabled; set ModelStreamingBehavior Improved, StreamingIntegrityMode PauseOutsideLoadedArea, StreamOutBehavior Opportunistic if OOM persists.
- [ ] Keep StreamingMinRadius 64 and StreamingTargetRadius 1024 by default; drop to 64 in testing.
- [ ] Set ModelStreamingMode Atomic for scripted models, Persistent for always-needed content; flatten nested hierarchies.
- [ ] Set Model.LevelOfDetail to SLIM on static models; avoid runtime changes to them.
- [ ] Keep RenderFidelity on Automatic; use Precise for landmarks and Performance for decor.
- [ ] Set CollisionFidelity to Box on small or non-interactive parts; Hull for convex; avoid PreciseConvexDecomposition.
- [ ] Turn off CanCollide, CanTouch and CanQuery on walk-through foliage and decorative parts.
- [ ] Anchor every part that does not move, including static NPCs.
- [ ] Disable CastShadow on tiny, hidden or in-shadow items; limit light count and range.
- [ ] Delete hidden parts, terrain under surfaces, duplicates and stray parts; hollow terrain with Subtract.
- [ ] Merge transparent parts; avoid stacked transparent layers and decals on transparent objects.
- [ ] Reuse MeshIds; avoid SpecialMesh and most UnionOperations; combine static meshes late in development.
- [ ] Shrink textures 1–2x where invisible; leave MetalnessMap empty on non-metallic surfaces.
- [ ] Create sounds at runtime instead of storing them in SoundService.
- [ ] Destroy references to unused animations and audio so they unload.
- [ ] Batch remotes; use Vector3int16, Int8-packed colours and axis-aligned CFrames where possible.
- [ ] Replace wait() with task.wait; spread heavy loops across frames; use parallel Luau for DataModel-free compute.
- [ ] Spawn purely visual items on the client; keep server work to tiny authoritative blocks.
- [ ] Disable unused humanoid states and Evaluate State Machine on static NPCs.
- [ ] Set PhysicsSteppingMethod to Adaptive.
- [ ] Keep MeshParts under 10,000 vertices, Scene Draw Count near 500, and budget mobile triangles.
- [ ] Keep server memory under 50% using 6.25 GiB + 100 MiB × peak players.
- [ ] Alert on ClientMemoryUsagePercentage and OOM exits per platform; investigate crash rates above 2–3%.
- [ ] Run a 10–15 min mobile session to detect thermal FPS decline; re-test after each optimisation.
- [ ] Capture MicroProfiler with Ctrl+F6 (Cmd+F6) during play, then pause with Ctrl+P on the spike before analysing.
- [ ] Ask Assistant whether a spike is physics-bound or script-bound and which category has the highest exclusive time.
- [ ] For server spikes, use the Developer Console server MicroProfiler (max 60 frames, 4 s delay); use counters mode for startup-to-dump data.
- [ ] On mobile, open the MicroProfiler web UI at the device IP:1338 (default 30 frames; add /90 for more).
- [ ] Fix one baseline low-end device (2014–2020 phone or laptop; 3.5 GB RAM threshold) and test every milestone on it.
- [ ] Check frame time against 16.67 ms (60 FPS) and 33.33 ms (30 FPS); flag spikes, and aim above about 40 FPS on mobile.
- [ ] Check draw calls under about 1,000 and triangles under about 1M on the baseline device.
- [ ] Keep visible parts near about 5k in the render area; test at 9k to see where FPS falls.
- [ ] Anchor static parts; check Awake parts visualization in playtest to find moving assemblies.
- [ ] Replace Neon on large part-count builds with SmoothPlastic.
- [ ] Turn Haze off and avoid dynamic clouds.
- [ ] Set PointLight shadows only where they add meaningfully.
- [ ] Confirm Instance Streaming is on and streaming radii are at defaults (min 64, target 1024).
- [ ] Set ModelStreamingBehavior to Improved and PredictiveStreamingMode to Enabled, then re-test on low-end hardware.
- [ ] Clear VideoFrame.Video when out of view and ensure no more than two videos play at once.
- [ ] Set RollOffMaxDistance on positional sounds; disable AcousticSimulationEnabled unless realistic audio is needed.
- [ ] Keep UIShadows near 100 on screen and set SurfaceGui MaxDistance deliberately.
- [ ] Watch the Developer Console Memory tab and PlaceScriptMemory across sessions for growth with player interactions.
- [ ] Auto-clean debris after about 30 seconds and add cleanup for any player-driven fragmentation.
- [ ] Measure network with the Network Stats overlay (Shift+F3, then Shift+1); multiply Studio network numbers by player count.
- [ ] Keep replication under about 50 KB/s per client and budget per-player unit counts.
- [ ] Check Open Cloud request volume against 2,500 per minute per server.
- [ ] Set an explicit short DataStore/MemoryStore expiration instead of the 45-day default.
- [ ] Run stress tests with many invited players before launch and check server headroom before adding about 50 more avatars.
- [ ] Test particle-heavy effects for emission rate, lifetime and speed; avoid high emission with long lifetime and low speed.
- [ ] Set a memory target: full game 400-500 MB; investigate near 1000 MB or when phones exceed 800-900 MB on 2 GB RAM devices.
- [ ] Read Place memory (not Core memory) in Developer Console, and check texture and character memory at higher player counts.
- [ ] Disconnect event connections and check that memory returns after a session or after leaving an area.
- [ ] When diagnosing mobile crashes, check memory usage before anything else.
- [ ] Verify the FPS counter by setting Roblox Maximum frame rate to 120 or 144 and confirming it tracks the cap (uncapped was about 200-240 FPS in one test).
- [ ] Check sent traffic stays well under 50 KB/s and received traffic stays well below about 70 KB/s in the network stats.
- [ ] Replace per-wheel raycasts with one center raycast and a line orientation constraint for vehicles.
- [ ] Set fractional transparency values to exactly 0 or 1 on large maps.
- [ ] Prefer shadowed SpotLights over shadowed PointLights where the design allows.
- [ ] Test SLIM assets for Z-fighting, corroded metal and UV issues, and confirm with a Highlight in Workspace.
- [ ] Check the place file against the 100 MB size limit.
- [ ] Use object pools for frequently spawned, recycled models, and measure the gain.
- [ ] Keep encoded audio short and module scripts small.
- [ ] Load 60 fps mocap animations on demand; each can be 200-300 KB.
- [ ] Enable streaming during development from the start, even if you disable it for release.
- [ ] Only if native streaming cannot meet the need: add frame-time throttling, a priority queue, a minimum reparent count and a settings slider.
- [ ] Count instances on the client during loading, not in Studio; aim for about 150,000 or fewer with streaming on.
- [ ] Estimate load time at about 1 second per 10,000 instances and keep total join load under about 15 seconds.
- [ ] Estimate client memory at about 500 bytes per instance (12,000 instances is roughly 6 MB).
- [ ] Reset Script Memory counters, play a session, and check for module counts that climb steadily.
- [ ] Check the unparented instances view for models or parts that keep growing over time.
- [ ] Deparent parts you want unloaded instead of parenting them under Lighting or hiding them.
- [ ] Compare client and server instance counts to verify zone culling works.
- [ ] Remove unused sound instances outside runtime.
- [ ] Release animation references for dead characters and NPCs.
- [ ] Keep base meshes low-poly and bake fine detail into normal maps.
- [ ] Keep mesh imports under the 20,000-polygon limit; aim near 5,000 polygons for boat-scale props.
- [ ] Pair Instance Streaming with Texture Streaming and SLIM compositing for high-fidelity worlds (indie guidance).
- [ ] Test a distant streaming-enabled spawn island to reduce initial instance load.
- [ ] Re-check part-size assumptions against the October 2026 reduced limits.
- [ ] For tycoons and idle games, test the fully upgraded or maximum-progression state on a low-end device before release.
- [ ] Track part, effect and light counts per upgrade tier to find which unlock causes the largest frame-time jump.
- [ ] Include a maximum-inventory test account in load-in and load-time tests.
- [ ] If players can get stuck on the loading screen, provide a skip option as a fallback.
- [ ] Before cloning many items (around 100 or more), batch or stagger the clones across frames rather than spawning all at once.
- [ ] Measure FPS during bulk spawns (for example 100 clones) to confirm the spawn cost is acceptable.
- [ ] If the game is a small linear space with discrete sections, consider an instant section swap at each transition point instead of gradual streaming.
- [ ] Measure the frame-time spike during the section swap on a low-end device before shipping it.

## Where creators agree
- Profile before optimising (Developer Console, MicroProfiler, Performance Summary) across DevForum, Crusherfire, and OFFICIAL docs.
- Enable instance streaming to cut memory and load time (DevForum T5845, RoBuilder T6218, Crusherfire T6250, OFFICIAL T8280).
- Use Box collision for small, non-interactive or non-moving items (DevForum T5427/T5545, Crusherfire T6244, OFFICIAL T8469).
- Turn off CanCollide/CanTouch/CanQuery on walk-through foliage and decor (DevForum T5426/T5546, Crusherfire T6245).
- Shadows and light are expensive; limit them (DevForum T5430/Q910, Crusherfire T6253, OFFICIAL T8276).
- Overlapping transparency is costly (DevForum Q915, OFFICIAL T6915, Creator Docs T7403).
- Batch remote traffic and avoid per-frame loops (DevForum T5419/T5080, Crusherfire T6260).
- Test on low-end devices and client, not Studio (DevForum T6658/T6603, OFFICIAL T8434).
- Delete hidden and duplicate content (DevForum T5431, OFFICIAL T8689).
- Anchor static parts (DevForum T5486, OFFICIAL T8265).
- Turn on Instance Streaming for most games, especially large ones; it reduces memory, join time and frame cost (official and indie).
- Anchoring static parts and cutting physics are the largest frame-rate levers (T12980, T12983, T13365, T11266, N4998).
- Test on real low-end hardware, not a dev PC; Studio numbers are not representative (T13359, T15250, T12981, T15252).
- Visible or rendered load drives FPS more than total map content (T12982, T11261).
- Keep visual-only motion and spawning on the client to avoid network cost (T11152, T11402, T11405, T11615).
- Shadows and lighting are major low-end costs; reduce them (T10915, T15015, T15642, T10820).
- Consistent frame time matters more than average FPS (T15601, T13361).
- Use Persistent models sparingly (T14080; indie advice on Atomic/Persistent agrees on restraint).
- Memory is the main constraint on mobile: TechSpectrum (T15857) and Last Level Studios (T15939, T15940) both tie crashes and limits to memory.
- Per-frame work is costly: BubuTheDev (T16118, a per-0.1-second script) and Roox4 (T16268, per-wheel per-frame logic) both show that constant per-frame loops hurt performance.
- Design for low-end devices first: Last Level Studios (T15938) and TechSpectrum (T15860) both budget against phone limits.
- Streaming benefits from frame-time-based control: Last Level Studios (T15798, T15799) and the existing rule to measure before optimising agree that frame data should steer decisions.
- Official and indie sources agree instance streaming is the core lever for building large worlds (T17599, T17702, T17703).
- Official guidance and the existing deparenting and streaming rules agree that reducing the client-side instance count is the main way to cut load and memory (T17702, T17701, N7569).

## Where creators disagree
- **Which CollisionFidelity is most expensive**
  - DevForum T5428 (2021-03): Hull is the most resource-heavy, Box quickest, Default mixed.
  - DevForum T5545 (2021-06, later): Box cheapest, then Hull, then Default, PreciseConvexDecomposition most costly.
  - OFFICIAL T8469: Hull for convex shapes, PreciseConvexDecomposition only when precision justifies its high cost. Later framing supersedes T5428.
- **RenderFidelity default strategy**
  - DevForum T5485 (2021-05) and T6070 (2025-01): set Performance on distant parts or MeshParts.
  - Crusherfire T6255 (2025-07): set MeshPart to Automatic instead of Precise; Performance only if visuals allow.
  - OFFICIAL T8468 (2026-10): keep default Automatic unless needed; detail drops with distance. Official supersedes older blanket Performance advice.
- **Shadows and lighting setup**
  - DevForum T5483 (2021-05): use Voxel lighting or skip ShadowMap/Future to cut lag dramatically.
  - Crusherfire T6253 (2025-07): Shadow Map lighting with global shadows disabled drops shadow draw calls to zero for mobile.
  - OFFICIAL N3395: shadows disabled below quality 4. Newer nuance (Shadow Map with shadows off) supersedes blanket Voxel advice for mobile.
- **Disabling humanoid states**
  - DevForum T5171 (2019-11): disable unused states (climbing, swimming) and enable when required.
  - DevForum T5490 (2021-05): disabling HumanoidStateTypes made no measurable difference; consider non-humanoid NPCs.
  - Crusherfire T6256 (2025-07): disable Evaluate State Machine on static NPCs; disable unused states on walking-only NPCs.
- **Dev Console vs MicroProfiler for memory**
  - DevForum T5050 (2019-02): Performance/Memory stats widget for memory.
  - OFFICIAL T8257: use Developer Console rather than MicroProfiler Counters mode for memory; X-ray view finds allocation timing.
- **wait() usage**
  - DevForum T5065 (2019-02): avoid wait(); it can overshoot by seconds.
  - OFFICIAL T7040 and T10073: use task.wait / parameters:Pause() at loop starts. Replace wait() with task.wait as the current recommendation.
- **Unions**
  - DevForum T5540 (2021-06): avoid UnionOperations for most cases.
  - DevForum T6070 (2025-01): set Unions to Automatic fidelity via command-bar scripts.
  - DevForum T5484 (2021-05): set Unions and MeshParts to Box collision for physics cost.
- **Streaming target radius**
  - Suphi Kaner (T11674, 2023-03): lower StreamingTargetRadius to about 128 studs to cut client memory and network.
  - Roblox Creator Docs (T14075, T14074, 2026-10): keep 1024 default; smaller reduces server load but shortens full-detail distance.
  - Resolution: use the official 2026 defaults unless memory-limited, then test the smaller radius.
- **StreamOutBehavior**
  - Roblox Creator Docs (T14073, 2026-10): Opportunistic to aggressively garbage-collect and reduce out-of-memory crashes.
  - Suphi Kaner (T11677, 2023-03): LowMemory for large static worlds; Opportunistic for worlds with many server-moved instances.
  - Resolution: choose per world type and test on low-end devices.
- **Lighting cost of ShadowMap**
  - Indie DevForum (T10820, 2020-10): ShadowMap and Future are the most expensive options.
  - Indie DevForum (T11264, 2021-12): ShadowMap is the default for well-optimised games; Future only for demanding visuals.
  - Resolution: T11264 is more recent and reflects the default-choice view; treat T10820 as dated.
- **RenderStepped vs Heartbeat for per-frame work**
  - Indie DevForum (T10709, 2020-06): RenderStepped with a modulus counter for camera checks.
  - Indie DevForum (T12206, 2024-06): use Heartbeat for heavy projectile work, since RenderStepped runs before render.
  - Resolution: prefer Heartbeat for heavy work; keep RenderStepped only for camera-tied, lightweight tasks.
- **Network throughput thresholds**
  - Indie DevForum (T11406, 2022-06): client receive below about 100 kbps, send below about 20 kbps.
  - Indie DevForum (T13135, 2025-12): replication throttle about 50 KB/s.
  - Indie DevForum (T13363, N5172, 2026-05): suggested total data about 80 KB/s.
  - Resolution: units differ (kbps vs KB/s) and purposes differ (author target, throttle, suggested total). Use the throttle as a hard ceiling.
- **Frame-rate targets**
  - Indie DevForum (T11261, 2021-12): 60 FPS with about 5k visible parts.
  - ByteBlox (N4728, 2024-11): above about 40 FPS minimum for mobile.
  - Resolution: targets depend on platform; pick the target per device tier.
- **Predictive streaming on low-end devices**
  - Roblox Creator Docs (T14078, 2026-10): fewer pauses and pop-in with no code changes.
  - Indie DevForum (T13651, 2026-07): predictions are skipped on resource-constrained client devices.
  - Resolution: enable it, but verify streaming on low-end hardware rather than assuming it applies.
- **Whether to hand-roll streaming**
  - Last Level Studios (T15795-T15809, 2020) built a custom reparent-based streaming system and reported roughly doubled FPS.
  - Existing knowledge file rule: do not hand-roll streaming; use native Instance Streaming and its settings. Newer guidance wins: native streaming is preferred, and the custom approach is only for cases native cannot cover.
- **Mobile memory figures versus platform change**
  - TechSpectrum (2021) gives 400-500 MB for full games and 800-900 MB typical on 2 GB phones.
  - Phone RAM and Roblox memory behaviour have changed since 2021; these figures are a starting guide, not a current ceiling.

## Instructions for an agent using this file
- If a game is slow on phones, then check Performance Summary and MicroProfiler on a low-end client first, not Studio; if frame bars are consistently tall, fix a per-frame cost, and if they spike occasionally, look for bursty work (loops, large remotes, instance floods).
- If memory is climbing, then use Developer Console memory tab and Luau heap snapshot diffs, then destroy unused sounds, animations and clones.
- If the game has many instances on join, then enable StreamingEnabled and set Persistent or Atomic for scripted or always-needed models.
- If a model breaks under streaming, then flatten nested Persistent/Atomic hierarchies and avoid client-side reparenting or Clone into Workspace.
- If a part does not move or need collision, then anchor it, set CanCollide/CanTouch/CanQuery off, and use Box CollisionFidelity.
- If a part is small or cosmetic, then use Box collision, Automatic RenderFidelity, and disable CastShadow.
- If many transparent layers stack, then merge them into one union or reduce layers; do not place decals on fully transparent objects.
- If you see wait() in a loop, then replace with task.wait and spread heavy work across frames or use parallel Luau for DataModel-free compute.
- If remote traffic is high, then batch into fewer large packets, use small data types, and keep incoming traffic under ~50 KB/s.
- If server memory approaches 50%, then plan capacity with 6.25 GiB + 100 MiB × peak players and keep MaxPlayers lower if needed.
- If a project needs memory or join-time gains, enable Instance Streaming and keep StreamingMinRadius 64 and StreamingTargetRadius 1024 before tuning.
- If a frame goal is missed, first classify the bar colour (orange, blue, red) and only then pick a script, render or physics fix.
- If a fix improves average FPS but not spikes, keep profiling; spikes are what players feel.
- If advice comes from a 2018–2021 DevForum post and conflicts with 2025–2026 official docs, follow the official docs and say the older advice is superseded.
- If a suggested streaming radius is smaller than the official default, verify memory need on a low-end device before adopting it.
- If many server-owned parts are tweened, replace with client-side animation playback or client-only visuals.
- If Open Cloud or HTTP request volume approaches limits, batch and back off; do not just retry.
- If a claim is self-reported with no measurement or is marked low-advice, label it unverified in recommendations.
- Do not recommend Atomic or Persistent on every model; use Atomic for parts that must load together and Persistent sparingly.
- Treat Studio FPS and Studio memory as non-representative; ask for physical low-end device measurements before concluding.
- If a project targets mobile, check memory against the 400-500 MB full-game guideline before tuning rendering.
- If a mobile crash appears, check memory usage first.
- If the user wants custom streaming, first suggest native Instance Streaming; only add a frame-time-throttled reparent queue if native streaming cannot meet the need.
- If a vehicle or enemy has per-wheel raycasts running every frame, replace them with one center raycast plus orientation constraint.
- If large maps show fractional transparency, set 0 or 1 and confirm the effect in MicroProfiler.
- If a light is shadowed, prefer SpotLight over PointLight where the look allows.
- If SLIM is considered, verify which geometry is SLIM with a Highlight in Workspace and test known defects first.
- Treat indie figures as self-reported; prefer measured data from MicroProfiler and Developer Stats.
- Give newer advice (2025-2026) precedence over 2020-2021 advice where they conflict, and say so.
- Treat [low-advice] items as lower-confidence; do not present them as authoritative.
- If the client instance count is approaching about 150,000 with streaming on, reduce instances (deparent, stream, pool) before adding more features.
- If a module or model count climbs steadily during play, run the Script Memory reset and check unparented instances before tuning rendering.
- If a boat-scale or prop mesh is well above about 5,000 polygons, move the extra detail into a normal map; never exceed the 20,000-polygon import limit.
- If client and server instance counts match, treat zone culling as broken and investigate before optimising anything else.
- Do not tune gameplay around late-2026 features (adaptive radius, path pre-fetching, 500-stud draw distance floor) until they are confirmed live.
- When targeting low-end Android, test both current and possibly raised draw distance behaviour, since the minimum may rise to 500 studs.
- Treat indie figures (GamesBeat T17599, N7476) as self-reported, not platform ground truth.
- Use the 1-second-per-10,000-instances figure as a rough estimate; always confirm with a measured join on a real low-end device.
- If a game's performance degrades as players progress (tycoon, idle, upgrade-based games), test the maximum-progression state, not only the start state, on a low-end device.
- Treat large FPS drops tied to progression as a content-scaling problem: profile the MicroProfiler and count visible parts and draw calls per upgrade tier before changing rendering settings.
- If a task involves spawning or cloning many items at once, batch or stagger the spawns across frames instead of doing them in a single frame.
- If a task involves load-in or loading-screen flow, test with a full-inventory account and consider a skip fallback.
- Treat the 100-clone FPS figure as a self-reported indicator. Confirm with a profiler on a low-end device before quoting it.
- If a game is a small, linear, discrete-section space, you may suggest instant section swaps as an alternative to gradual streaming, but label it as an unverified indie suggestion.
- If a section swap is proposed, require a frame-time measurement on low-end mobile before recommending it.
- Do not replace the existing streaming rules (PauseOutsideLoadedArea, ModelStreamingBehavior, streaming radii) with this tip for open-world games.
