# Code Architecture And Frameworks

_OOP, modules, services, Knit/Promise/ECS/signals, project structure, reusable systems, clean code._

Evidence base: 464 extracted items from 207 videos by Amora, ArTheDev, B Ricey, ByteBlox, Chase Higgins, Crit, Crusherfire, Duckable, Emancyphur, Generalist Programmer, GnomeCode, Itz_FloppyFish, Last Level Studios, Leif, PineappleDev, Possible Panda, Raul, Roblox Creator Docs, Roblox DevForum, SimTek Game Development, Stewiepfing, Suphi Kaner, VuukStudios, XTB7, janisjanis01 (2014-09-03 to 2026-10-30). Roblox changes quickly: check the date on each source and see Date context below.

## Overview
Roblox architecture advice converges on plain ModuleScript classes (Class.__index, methods on the class table, instance data on self), thin client and server entry scripts that require modules and run a two-phase init/start lifecycle, and CollectionService tags that bind component classes to instances. Cleanup goes through Trove/Janitor and Promise finally. Signals break circular requires, and reusable code is abstracted by pulling differing values into data tables. Frameworks such as Knit and Nevermore are optional and contested. Newer sources (2025-2026, plus official Creator Docs 2026-10) favour small single-purpose modules and explicit state machines with one set_state path.

## Rules and findings
- **Build classes as ModuleScripts with Class.__index = Class and a new() that returns setmetatable({...}, Class)** (multiple-creators): This is the standard Roblox OOP pattern. Define methods on the class table with colon syntax, not on each instance. Always return the constructed object; forgetting the return makes method calls fail. Use dot indexing inside modules for clarity. Sources: [Roblox DevForum 2014-09](https://devforum.roblox.com/t/all-about-object-oriented-programming/8585), [Roblox DevForum 2014-09](https://devforum.roblox.com/t/all-about-object-oriented-programming/8585), [B Ricey 2021-04 9:01](https://youtu.be/KNT-vjqB_qI?t=541), [Roblox DevForum 2022-01](https://devforum.roblox.com/t/roblox-oop-object-oriented-programming/1639499), [Roblox DevForum 2022-01](https://devforum.roblox.com/t/roblox-oop-object-oriented-programming/1639499). Newest source 2024-02-21.
- **Keep one class or responsibility per ModuleScript and split big scripts** (multiple-creators): Large scripts become hard to change. A 1000+ line tycoon module was called painful; split by system (Cell/Maze/Room, Components folder, PlotStorage for serialization and DataStore). Main scripts should only wire events to module functions. Sources: [Roblox DevForum 2014-09](https://devforum.roblox.com/t/all-about-object-oriented-programming/8585), [B Ricey 2022-09 5:28](https://youtu.be/MyK4o2pIpQw?t=328), [B Ricey 2022-09 9:34](https://youtu.be/MyK4o2pIpQw?t=574), [Crusherfire 2024-02 3:51](https://youtu.be/28z_064N-lc?t=231), [B Ricey 2024-02 8:21](https://youtu.be/FaEMgVDlaNQ?t=501). Newest source 2024-04-14.
- **Don't create a class for a single function; introduce an object only when state must persist** (multiple-creators): Use plain functions for stateless logic (e.g. a cooldown needs state, a single helper does not). Don't wrap a Roblox Instance in a class unless it adds behaviour; a standalone isolated script is fine. Sources: [B Ricey 2022-09 7:10](https://youtu.be/MyK4o2pIpQw?t=430), [B Ricey 2022-04 4:22](https://youtu.be/5bI6l6SHBDU?t=262), [B Ricey 2022-09 14:29](https://youtu.be/MyK4o2pIpQw?t=869). Newest source 2022-09-23.
- **Prefer composition over inheritance** (multiple-creators): Build entities from components (Engine, Wheel) with has-a relations; a boat-car is a combination of existing parts. Deep is-a trees (Car to Plane) get messy and a broken parent breaks all children. Mixins are the term to search. NOTE: this supersedes 2014-2020 inheritance advice. Sources: [B Ricey 2021-04 1:15](https://youtu.be/KNT-vjqB_qI?t=75), [B Ricey 2021-04 3:25](https://youtu.be/KNT-vjqB_qI?t=205), [Roblox DevForum 2020-09](https://devforum.roblox.com/t/concepts-object-oriented-programming-in-roblox/761267), [B Ricey 2021-04 15:29](https://youtu.be/KNT-vjqB_qI?t=929), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/resources/plant-reference-project). Newest source 2026-10-28.
- **Do not inherit from Roblox Instances; hold a reference to the model and pass it into new()** (one-creator-repeated): Luau classes should not subclass Instances because models are C++-backed. Keep Workspace model references out of component modules so one class can drive many models via Car.new(model). Call components through their owner (self.Engine:TurnOn()) rather than copying their methods onto the main class. Sources: [B Ricey 2021-04 6:18](https://youtu.be/KNT-vjqB_qI?t=378), [B Ricey 2021-04 7:36](https://youtu.be/KNT-vjqB_qI?t=456), [B Ricey 2021-04 14:28](https://youtu.be/KNT-vjqB_qI?t=868). Newest source 2021-04-03.
- **Inheritance is acceptable for small families of repeated UI or variant classes** (single-mention): Duckable uses a base button class with spawn and merge subclasses instead of copy-paste. This conflicts with the composition default; limit it to shallow hierarchies. Sources: [Duckable 2026-08 5:41](https://youtu.be/Cc7HT3uNjeQ?t=341). Newest source 2026-08-04.
- **Place shared modules in ReplicatedStorage and server-only modules in ServerScriptService or ServerStorage** (multiple-creators): Any module both client and server require belongs in ReplicatedStorage (e.g. remote wrapper, shared types, queue, config). Server-only logic and data stay on the server, and clients never see server modules. Official docs say the same. Sources: [B Ricey 2020-12 3:09](https://youtu.be/6ZgzabMLkKQ?t=189), [B Ricey 2021-01 3:28](https://youtu.be/xwaCg7SWUhc?t=208), [Roblox DevForum 2022-01](https://devforum.roblox.com/t/roblox-oop-object-oriented-programming/1639499), [Crusherfire 2024-02 2:36](https://youtu.be/28z_064N-lc?t=156), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/scripting/module). Newest source 2026-10-28.
- **Keep server scripts in ServerScriptService and character-only scripts in StarterCharacterScripts** (multiple-creators): Never put server scripts in StarterPlayerScripts. Character scripts (health regen, stamina) re-clone on every respawn. Standalone models keep their scripts inside the model. Sources: [Crusherfire 2024-02 0:33](https://youtu.be/28z_064N-lc?t=33), [Crusherfire 2024-02 1:56](https://youtu.be/28z_064N-lc?t=116), [B Ricey 2022-09 1:23](https://youtu.be/MyK4o2pIpQw?t=83), [Itz_FloppyFish 2023-04 0:28](https://youtu.be/H6LsbS_SA2w?t=28). Newest source 2024-02-11.
- **Use one server entry point and one client entry point that require a bootstrap or loader** (multiple-creators): Single entry points give deterministic startup order (official). Creators differ on the mechanism: Knit services/controllers, or a Module Loader that loads modules from containers or tags with a priority attribute (e.g. high number for DataService). Multiple independent scripts give isolation but non-deterministic order. Sources: [B Ricey 2021-01 4:51](https://youtu.be/xwaCg7SWUhc?t=291), [Roblox DevForum 2022-01](https://devforum.roblox.com/t/roblox-oop-object-oriented-programming/1639499), [Crusherfire 2024-02 8:39](https://youtu.be/28z_064N-lc?t=519), [Crusherfire 2025-08 0:32](https://youtu.be/dJjZ7ml9bSo?t=32), [Crusherfire 2025-08 27:55](https://youtu.be/dJjZ7ml9bSo?t=1675). Newest source 2026-10-28.
- **Pick a framework only if you need its organisation; note the singleton trade-off** (multiple-creators): Knit gives services and controllers and a lightweight copy-paste install, and B Ricey called it amazing in 2021. In 2022 he warned that it leans on singletons. Matter ECS is an alternative for component-based games. Choose the simplest option for the project. - **Use singleton ModuleScripts for global systems, since require caches the module** (multiple-creators): Systems like Network, PlayerData or Market should be singletons called with dot syntax; all callers share one object. This is the official recommendation. Use a metatable __index to let client and server service modules inherit a shared base so they can expand later. Sources: [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/resources/plant-reference-project), [Crusherfire 2025-12 17:14](https://youtu.be/6Q_p2ObUXSo?t=1034), [B Ricey 2021-01 5:33](https://youtu.be/xwaCg7SWUhc?t=333). Newest source 2026-10-28.
- **Share data through ModuleScripts; use BindableEvents for coordination and round logic** (multiple-creators): Official guidance: prefer module scripts for shared data and bindables for actions and round structure. Let multiple scripts listen to the same BindableEvent so new start/end behaviour needs no rewiring. Use BindableEvents in ServerStorage for server-only signals. Sources: [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/scripting/events/bindable), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/education/battle-royale-series/timers-and-events), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/education/battle-royale-series/timers-and-events), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/education/battle-royale-series/timers-and-events), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/education/battle-royale-series/landing). - **Expose a narrow public API and hide internals** (multiple-creators): Expose simple functions (getValue, updateValue, ChangeValue(player, name, value)) as the only way other scripts modify state. Keep heavy logic in local helpers, use underscore prefixes for private members, and separate Local Functions from Module Functions sections. - **Drive behaviour from CollectionService tags, not hardcoded names** (multiple-creators): Put one manager per tag category and wire every tagged instance; tags auto-clear when a player leaves. Use GetInstanceAddedSignal and GetInstanceRemovedSignal so runtime tags are handled, since Init alone misses them. Toggle behaviour with AddTag/RemoveTag. - **Guard tag iteration so stray tags cannot break the game** (one-creator-repeated): Iterate with GetTags() and only create components whose module exists. A third-party tag added by accident can break a complex game (Q918). Attach components per instance with new(instance) and Init(). - **Give every object a single cleanup path: Trove, Janitor, Maid, or destroy()** (multiple-creators): Store self._trove = Trove.new(), add instances and connections with trove:Add(...), and make destroy() a single line calling self._trove:Destroy(). Trove can also hold functions for teardown. Janitor is more feature-complete; Trove is simpler and works with Knit. Official docs require destroy() to disconnect connections, since connected instances are not garbage collected. Sources: [Roblox DevForum 2018-02](https://devforum.roblox.com/t/psa-connections-can-memory-leak-instances/90082), [Roblox DevForum 2019-08](https://devforum.roblox.com/t/how-to-use-a-maid-class-on-roblox-to-manage-state/340061), [B Ricey 2022-08 5:11](https://youtu.be/2Msrw5w5cTs?t=311), [B Ricey 2022-08 6:16](https://youtu.be/2Msrw5w5cTs?t=376), [B Ricey 2022-08 12:35](https://youtu.be/2Msrw5w5cTs?t=755). Newest source 2026-10-28.
- **Make observers return cleanup functions and add them to a main Trove** (single-mention): Observers (tag, attribute, children, descendants) replace manual event wiring. Nest them, e.g. observe a tag then an attribute, guard for valid values, and put per-instance loops in a Trove cleared on removal. Add each observer's cleanup to the main Trove to tear down the whole system. - **Wrap yielding Roblox APIs in Promises and cancel them on Destroying** (one-creator-repeated): Use Promise.new with resolve, reject and onCancel around TweenService so tweens can be cancelled, retweened or reset cleanly. Use Promise.delay instead of task.delay when the action depends on an object, and cancel it on the part's Destroying event. Promises are usable by anyone who knows when to use them. - **Make helper functions pure and move them into ModuleScripts** (multiple-creators): Pure functions take inputs, return outputs, and read no external variables, so they can be moved into shared modules and reused. Serialization functions with typed return values are a good example. Use whichever paradigm fits: OOP for stateful objects, FP for stateless helpers. - **Validate on both client and server using the same shared pure validator** (multiple-creators): Put validators in ReplicatedStorage so the client gives preview feedback and the server does the authoritative check. Keep data, purchases and authority on the server; keep UI and client feedback on the client. Use guard clauses with early returns to avoid deep indentation. - **Emit custom change signals from your own classes** (one-creator-repeated): Mimic instance events such as Destroying or AncestryChanged: fire a LevelChanged-style signal with the old value after updating state. - **Type-check everything with --!strict and shared export types** (multiple-creators): Put --!strict at the top of each script you want checked. - **Name things clearly and comment and indent for review** (multiple-creators): Name variables after what they hold (teamScore, teamColor), lowercase local names, and name scripts after their single purpose (LeaderboardHandler). - **Use local variables; avoid globals that clutter the whole script** (multiple-creators): Locals have limited scope inside a block; globals stay accessible across the whole script and clutter it. - **Give every module an init then start phase** (multiple-creators): Require all modules first, call initialize (setup) on each, then initiate/start (cross-module calls and connections). - **Auto-load module folders into one table** (multiple-creators): Loop a folder's ModuleScripts into a table keyed by script name, then run init on each. ## Checklist
- [ ] Start each class as a ModuleScript: Class.__index = Class, Class.new returning setmetatable, colon methods, return the object.
- [ ] Put shared modules in ReplicatedStorage; server-only in ServerScriptService or ServerStorage; never ship server logic to clients.
- [ ] Keep server scripts out of StarterPlayerScripts; use StarterCharacterScripts for per-character logic.
- [ ] Choose one server entry script and one client entry script; load modules through a bootstrap or loader so startup order is deterministic.
- [ ] Split any script doing multiple jobs; one responsibility per module, named after its purpose.
- [ ] Before adding inheritance, ask whether composition (has-a components) works; default to composition.
- [ ] Don't inherit from Roblox Instances; wrap the model in a reference and pass it into new().
- [ ] Use CollectionService tags to attach behaviour; wire GetInstanceAddedSignal and GetInstanceRemovedSignal, not just an initial GetTagged loop.
- [ ] Iterate with GetTags() and guard against missing modules before creating components.
- [ ] Give every object a Trove, Janitor or Maid, and make destroy() a single cleanup call that disconnects connections.
- [ ] Wrap yielding APIs (TweenService) in Promises with onCancel and cancel on Destroying.
- [ ] Write helper logic as pure functions in shared ModuleScripts; keep validators in ReplicatedStorage.
- [ ] Keep constants, IDs and stage lists in one config ModuleScript; avoid hardcoded counts or limits.
- [ ] Use attributes for per-object tunables created in Studio; use config modules when many objects share values.
- [ ] Add --!strict to scripts and define shared export types in a ModuleScript.
- [ ] Use local variables, descriptive names, indentation and a top-of-file block comment.
- [ ] Expose a narrow public API (getValue, updateValue, ChangeValue) and hide internals behind underscore-prefixed members.
- [ ] Use BindableEvents for coordination and ModuleScripts for shared data.
- [ ] Clone prefabs from storage instead of building properties at runtime.
- [ ] Check Workspace.SignalBehavior (Default, Immediate or Deferred) before debugging event order.
- [ ] Decide on Knit or a module loader only after weighing singleton coupling; Knit suits service/controller organisation.
- [ ] Package reusable systems with no game-specific dependencies; keep game logic in a separate implementation folder.
- [ ] Use Trove, Janitor or Maid for all cleanup; prefer Wally installation over copy-paste.
- [ ] When a stage changes, shut down the old handler before initialising the new one.
- [ ] Consider Sera for shared serialization schemas if a project needs typed server-client serialization.
- [ ] Put setup in initialize and cross-module connections in start for every module, and call them from one server and one client bootstrap.
- [ ] Auto-load each module folder into a table keyed by name, and check that no two module names are the same.
- [ ] Save each require() to a top-level local once; for profiles, use a Cache module keyed by UserId.
- [ ] Keep methods on the class table and per-object data on self; export the class type from the constructor.
- [ ] Subclass only for a shared behaviour family, and call the parent __init explicitly.
- [ ] Store per-item data in a table and write one lookup function; expose only the changing values in the settings module.
- [ ] Clone definition data per instance and never write to the shared data table at runtime.
- [ ] Define every remote and packet in one shared module required by both sides.
- [ ] Use RemoteEvents to cross client-server and BindableEvents within one side.
- [ ] Before coding a feature, list its subsystems and the state machine, then write one set_state with early return on same-state.
- [ ] Reset state-specific flags inside set_state on every transition; nil-guard optional hooks.
- [ ] Gate actions with a state check at the top and return early.
- [ ] Connect GetInstanceAddedSignal before looping GetTagged, and pass each tagged instance into the handler.
- [ ] Name the tag after the module and use multiple tags (category plus specific) for grouping.
- [ ] On CharacterAdded, remove mode tags and re-add the default tag.
- [ ] Add Promises to a Trove with AddPromise and run cleanup in finally.
- [ ] Use Janitor :Add(obj, index) when you may need to remove one item early.
- [ ] Use a custom signal module when event deferral behaviour matters.
- [ ] Split any script over ~1000 lines and any section over ~100 lines.
- [ ] Order each script as services, modules, instances, variables; use PascalCase for classes, modules and types.
- [ ] Document preconditions, postconditions, return values, side effects and yields for each public function.
- [ ] Keep utility modules in a separate folder from game modules and reuse tested ones.
- [ ] Keep LocalScripts to input only; put logic in modules.
- [ ] Keep economy and purchase logic on the server Script.
- [ ] Use table.insert for arrays and table.remove(queue, 1) for a FIFO queue.
- [ ] Write new logic as functions and modules from the first version; do not copy-paste scripts.
- [ ] Wrap raw data-store access in a manager module with helpers such as GetData, GiveMoney and GetItems.
- [ ] Keep the data layer as a Modules folder in ServerScriptService (DataManager, Template, LeaderStats).
- [ ] For large static item catalogues, use one ModuleScript per item and a registry keyed by ID.
- [ ] When checking several downstream conditions, test the most restrictive one first and return early.
- [ ] Model permission checks as functions taking a Player and returning a boolean; chain them with one/all operators.
- [ ] Put each object's permission module beneath it and route checks through one central manager.
- [ ] Store common permission combinations as shared ReplicatedStorage modules.
- [ ] Define a typed Props table with defaults for every reusable UI component in ReplicatedStorage.
- [ ] Create UI state inside the component function so instances do not share it.
- [ ] Scope Fusion instances and state with fusion.scoped and alias repeated Fusion calls to locals.
- [ ] Check the installed Fusion version before choosing peek() versus :get().
- [ ] Keep shared player state in an atoms module; use effects to react instead of polling.
- [ ] Choose one zone interaction approach per system and create one observer per system.
- [ ] Return an exit function from zone observers and use metadata to identify the zone.
- [ ] Put accessory and other clone-only templates in a dedicated ServerStorage folder, never in Workspace.
- [ ] Clone template accessories at runtime from that folder instead of placing them in the world.
- [ ] Use a tested quaternion/rotation utility module for orientation problems instead of hand-written rotation math.
- [ ] Require grouped modules with ./ and ../ paths so the folder can move without path rewrites.
- [ ] Before standardising on string-based requires, confirm the exact syntax in the official require documentation.
- [ ] Route every item grant, clear and currency change through one API function in a single ModuleScript.
- [ ] When you have many entries of one type, store them in one table keyed by name and add new types by adding an entry.
- [ ] Name server scripts *.server.luau, client scripts *.client.luau, and ModuleScripts *.luau.
- [ ] Pick one variable naming convention and check it across all scripts.
- [ ] Place doc comments directly above each function with no blank line.
- [ ] Use an Observers-style helper for player, class and tag observation and add its cleanup to your Trove.
- [ ] Check a vetted utility set (e.g. RbxUtil) before writing common helpers yourself.
- [ ] Before scripting a new game, check whether an earlier game's framework already covers the needed system (data, state, UI, remotes, tags) and reuse it.
- [ ] When reusing an internal framework, confirm it has no game-specific logic left in it before copying it into a new project.
- [ ] Put effect code in a Changed handler on the state value, not in each trigger block.
- [ ] Wrap one world object's logic in a table module with setup and update, and require it from the main script.
- [ ] When a random pick breaks a rule, move selection into its own function and re-roll rather than nesting ifs.
- [ ] Join related rejection conditions with 'or' in one if block.

## Where creators agree
- Use ModuleScript classes with the __index/new/setmetatable pattern (DevForum, B Ricey, Crusherfire, official).
- Split code into single-responsibility modules; avoid giant scripts (DevForum, B Ricey, Crusherfire, official).
- Place shared code in ReplicatedStorage and server-only code in ServerScriptService or ServerStorage (B Ricey, Crusherfire, DevForum, official).
- Use CollectionService tags for behaviour attachment and add/remove signals for runtime changes (B Ricey, Crusherfire, official).
- Clean up every object's connections and instances via a single cleanup call (DevForum Maid, B Ricey Trove/Janitor, Crusherfire observers, official destroy()).
- Prefer composition over deep inheritance (B Ricey, DevForum 2020, official); Crusherfire agrees paradigms should match needs.
- Keep constants and tunables in one config module (B Ricey, Crusherfire, official).
- Use local variables, clear names, indentation and comments (DevForum, B Ricey, official).
- Put shared code in ModuleScripts in ReplicatedStorage, required by both client and server; keep server-only modules in ServerStorage or ServerScriptService.
- Use thin single entry-point scripts on each side that require modules (official 2026 docs and multiple indie creators).
- Use CollectionService tags rather than names or hierarchy to bind behaviour to instances.
- Prefer composition and small single-purpose modules over deep inheritance.
- Use BindableEvents for same-side coordination and RemoteEvents for crossing the boundary.
- Abstract reused code by moving the differing values into a data table.
- Use one cleanup path per object (Trove, Janitor, Maid or Destroy) and cancel pending Promises on destroy.
- Modular code from the start: Last Level Studios (T15906, T15766) and Amora (T16030) both argue for modules and separate structure early.
- Shared code belongs in ReplicatedStorage: Possible Panda's UI components and permission rule sets (T16302, T16329) match the existing shared-module rule.
- Cross-boundary communication uses RemoteEvents, not in-process signals: T16370 matches existing rules on BindableEvents and RemoteEvents.
- Scopes or cleanup of instances: T16296 (Fusion scope cleanup) matches the existing single-cleanup-path rule.
- GnomeCode (T18252) and SimTek Game Development (T18307) both prefer one lookup table keyed by name or material over per-part attributes or per-item storage.
- Emancyphur (T18000) and GnomeCode (T18328) both centralise item or currency writes in one ModuleScript API called from the server.

## Where creators disagree
- **Use a framework (Knit) or a module loader for structure**
  - B Ricey (2021) strongly recommends Knit as services and controllers, a lightweight copy-paste framework (T5372, Q904).
  - B Ricey (2022) warns Knit leans on singletons and suggests Matter ECS or simplest option (T5755).
  - Crusherfire (2025) uses a Module Loader and calls it a custom service system (T6279), but says you do not need a loader at all (Q995).
  - Official Creator Docs (2026) favour a single client and server entry point and singleton modules, without naming Knit (T9709, T9710).
- **Inheritance versus composition**
  - DevForum (2014-2022) teaches Parent.new and setmetatable(Child, Parent) inheritance (T4900, T5250, T5620).
  - DevForum (2020) warns against deep chains; B Ricey (2021) and the official docs prefer composition (T5334, T5451, T9711, Q911).
  - Duckable (2026, low-advice) uses inheritance for a base UI button class (T6685).
- **Where to keep tunable values**
  - Official docs (2026) say shared tuning values belong in a config ModuleScript, not attributes or value objects (T7224).
  - Official docs (2026) and Crusherfire (2025) say tunables can be attributes created in Studio (T9918, T9919, T6390).
- **Singletons versus instances**
  - Official docs recommend singleton ModuleScripts with no new() for global systems (T9710).
  - B Ricey (2022) cautions that Knit leans on singletons (T5755), while Crusherfire wraps modules as services with metatable inheritance (T6382).
- **Cleanup library choice**
  - DevForum (2019) uses a Maid class (T5112); B Ricey (2022) recommends Trove, with Janitor as most complete (T5741).
  - Official docs require destroy() to disconnect connections (T9712).
- **Use of general frameworks (Knit, Nevermore, Aero)**
  - Knit's Service/Controller split scales better and is recommended (T11234, T11236); Nevermore loader and libraries are useful (T10435); study Roact, Aero or Nevermore once comfortable with OOP (T10814).
  - Avoid general-purpose frameworks due to memory and lost typechecking/autofill (T10702, Q1154); prefer small single-purpose libraries (T10703) and plain module-to-module requires since frameworks invert coupling and weaken inference (T11885).
- **Inheritance for NPC or behaviour families**
  - Subclasses via metatables and a base module let NPC variants reuse shared behaviour (T12777, T12819).
  - Use composition over deep inheritance; give each component its own class and have entities hold them (T11282, T12578, N4784); use polymorphism only when behaviour differs (T12588).
- **ReplicatedFirst contents**
  - Keep ReplicatedFirst for the loading screen only; put assets in ReplicatedStorage subfolders (T11915).
  - Put shared logic in ReplicatedStorage and ReplicatedFirst since both replicate to clients (T15339).
- **Event deferral and signals**
  - Array and dictionary events need task.defer for safe mid-fire connect or disconnect (T12249); use BindableEvents and Deferred events for consistent handling (T14664, T14665).
  - task.defer masks problems and may not always be an option (Q1262); a custom signal module avoids breakage if deferral behaviour changes (T11759).
- **Static game data: one config module versus one ModuleScript per item**
  - Existing file rule: keep tuning values and IDs in one config or settings module, and use config modules for many objects.
  - Possible Panda (T16425, 2026-01, low-advice): store static items as one ModuleScript per item and load them through a registry keyed by ID.
- **Central manager versus centralised tables**
  - Possible Panda (T16328): use a central manager script to scale access control instead of per-object logic.
  - Last Level Studios (Q1490, 2020-08): describes their early centralised system where all signals were handled in one big table, which they treat as a messy pattern.
- **How to store many static items**
  - GnomeCode (T18252) and SimTek Game Development (T18307): store all item or block values in one table keyed by name, and avoid per-part attributes.
  - Existing knowledge file rule: store each static item as its own ModuleScript and load by ID.
  - Existing rule also says use attributes for per-object tunables created in Studio. Attributes still fit single tunables; the table approach fits large catalogues.

## Date context (what may be outdated)
- Older advice (2014-2020 DevForum) uses inheritance chains (T4900, T5620) and Maid cleanup. Later advice (2021 onward) supersedes the inheritance default with composition (T5451, T9711); treat inheritance as a niche tool.
- Knit was recommended in 2021 (T5372, Q904) and qualified in 2022 (T5755). Crusherfire moved to a module loader, observers and packages in 2025 (T6279, T6196, T6389). Newer advice tends to favour loaders over Knit, but the official 2026-10 batch does not mention Knit.
- Trove and Janitor (2022) replaced Maid in newer B Ricey advice (T5736, T5741); Crusherfire (2025) adds observers that return cleanup functions (T6196).
- Workspace.SignalBehavior (Default, Immediate, Deferred) was flagged in 2024-01 (T5871); check it in each project.
- Sera (2025, T6166) is a newer schema approach for serialization; Lemon Signal (2025, T6206) for variadic signal args. Verify these packages are still maintained before adopting.
- Official docs were all published 2026-10, so they are the most current source on mechanics. T9215 (Class.Player.User as identifier) and T7067 (HUD package locations) are version-specific and should be verified against current API docs.
- Low-advice videos (marked) are weaker evidence and may be superseded by the official batch.
- Nevermore loader and 2015-2020 framework advice (T10435, T10702, T10703) predates Promise, Trove and Observer patterns; newer sources (2023-2026) favour plain modules plus small single-purpose libraries.
- Knit advice spans 2021 (T11234, T11236) to 2023 (T11885, which warns it weakens inference); prefer the newer 2023 caution unless you need Knit's organisation.

## Instructions for an agent using this file
- If writing a new class, then use a ModuleScript with Class.__index = Class, a new() returning setmetatable, colon methods and a destroy() method.
- If an object owns connections or instances, then store a Trove (or Janitor/Maid) on it and call a single Destroy in destroy().
- If a feature needs to be shared by client and server, then place the module in ReplicatedStorage; if server-only, use ServerScriptService or ServerStorage.
- If a script grows past a few hundred lines or does more than one job, then split it into modules with one responsibility each.
- If you are tempted to inherit, then first check whether composition with has-a components works; use inheritance only for shallow families like UI buttons.
- If a system must apply behaviour to many instances, then use CollectionService tags with GetInstanceAddedSignal and GetInstanceRemovedSignal, not hardcoded names.
- If a yielding API (TweenService) must be cancellable, then wrap it in a Promise with onCancel and cancel it on Destroying.
- If a helper reads no external state, then make it a pure function in a shared module.
- If a value is tunable or appears in several scripts, then put it in one config ModuleScript, not hardcoded.
- If you need a framework, then choose Knit only when you want service/controller structure and accept singleton coupling; otherwise use a simple bootstrap or loader.
- If the project is small and the developer is new to OOP, use plain ModuleScript classes with one bootstrap per side and skip frameworks.
- If the same logic appears in several scripts with different values, abstract it into one function over a data table before adding more copies.
- If an object changes behaviour over time, route every change through one set_state, return early on same-state, and reset flags there.
- If two modules need each other, replace the require cycle with a signal exposed via a GetXSignal method.
- If a system creates connections or waits, register them in a Trove or Janitor and cancel Promises on destroy.
- If you use CollectionService, connect GetInstanceAddedSignal before looping GetTagged and pass the instance into the handler.
- If a name is referenced in several places (module, tag, ability, remote, UI part), grep every reference before renaming, because mismatches fail silently.
- If a module is required by both client and server, assume its tables are not shared across the boundary and replicate data with remotes.
- If you see Knit, Nevermore or Aero in a codebase, treat it as valid but note the inference trade-off and singleton behaviour.
- If a script is over ~1000 lines or a section is over ~100 lines, split it into modules by concept and keep dependencies one-way.
- If a request involves a large catalogue of static items, use one ModuleScript per item with an ID-keyed registry; keep global tunables in one config module.
- If a request involves access control, implement checks as predicate functions (Player -> boolean) and combine them with all/any helpers.
- If a request involves UI state, create state inside the component function, and use scope-based cleanup if using Fusion.
- If the Fusion version is unknown, check it before choosing peek() or :get().
- If a request involves shared player state read by UI and logic, put it in an atoms module and use effects to react.
- If a request involves zones, pick one interaction approach, create one observer per game system, and return exit functions.
- If a request involves many downstream conditions, check the most restrictive first and return early.
- Do not copy-paste code blocks between scripts; extract a function or module instead.
- Do not treat low-advice items as platform rules; present them as options.
- If a project has grouped module folders that may move, use ./ and ../ relative requires inside the group.
- If you are unsure of the exact string-require syntax, check the official docs rather than copying the source's example verbatim.
- If an orientation or rotation problem is present, reach for a tested quaternion utility module before writing custom math.
- If templates are needed at runtime, store them in a dedicated ServerStorage folder and clone them; do not leave them in Workspace.
- If a static catalogue has many entries of one type, use one table keyed by name; if each entry needs its own asset or script, use one ModuleScript per item.
- If code changes an item count or currency balance, call the single funnel function instead of writing to data directly.
- If you create a new file, apply the *.server.luau, *.client.luau or *.luau suffix based on where it runs.
- If you write a function that other developers will use, add a doc comment directly above it with no blank line.
- If you need player, class or tag observation, use an Observers-style helper and return its cleanup into the main Trove.
- If you need a common helper, check a vetted utility library first before writing your own.
- Treat HTML-tag formatting in doc comments as unverified and do not rely on it without testing in Studio.
- If the user's project resembles one they have already shipped, suggest reusing their earlier framework before writing new core systems.
- Treat the time-saving claim as an indie's self-report, not a benchmark.
- If an effect should run whenever a state value changes, attach a script to the value and react in its Changed handler.
- If a single world object needs setup and update logic, wrap it in a table module and require it from the main script.
- If a random selection breaks a rule, re-roll by calling the selection function again; add a retry limit yourself, since sources do not specify one.
- If several conditions all reject the same candidate, combine them with 'or' in one if block rather than separate checks.
