# Matchmaking And Teleport

_TeleportService, matchmaking, reserved/private servers, server browsers, cross-place travel, lobbies._

Evidence base: 187 extracted items from 58 videos by AlvinBlox, Crusherfire, Cumin, GnomeCode, LovJak, Mulch, PineappleDev, Roblox Creator Docs, Roblox DevForum, Roblox public API, Suphi Kaner, XTB7, janisjanis01, rasdev, studio rook. (2018-12-08 to 2026-11-01). Roblox changes quickly: check the date on each source and see Date context below.

## Overview
Official Roblox docs (2026-10) tighten teleport guidance around routing, failure handling and security. Teleports must run from server scripts; the client-side Teleport() is deprecated. Each TeleportOptions sets exactly one routing field: ReservedServerId for developer-created reserved servers, VipServerId for player-purchased VIP servers, or ServerInstanceId for friend joins. A VIP ID only works with places in the experience that owns it. Plain teleports can silently land on a VIP server. Reserved servers are identified on arrival by a non-empty PrivateServerId with PrivateServerOwnerId == 0. Teleport failures can surface after the call succeeds, so handle TeleportInitFailed. Lock down with Access Control for Places set to Secure once client calls are migrated.

## Rules and findings
- **Call TeleportAsync only from server scripts** (one-creator-repeated): Client-side Teleport() is deprecated and should not be used for new work. For legacy client teleports, move the logic to server scripts triggered via RemoteEvents, ProximityPrompts, ClickDetectors or Touched, then switch access control to Secure.
- **Wrap TeleportAsync in pcall with retries** (one-creator-repeated): Retry on failure, especially for reserved servers. Handle TeleportInitFailed for teleports that fail after a successful call. The docs' example SafeTeleport wrapper uses up to 5 attempts with a 1 second retry delay.
- **Branch on Enum.TeleportResult** (one-creator-repeated): On Flooded, wait about 15 seconds before retrying. On Failure, retry after about 1 second. Treat all other results as invalid teleports and do not retry them blindly.
- **Create reserved servers with a generated ID** (one-creator-repeated): Use HttpService:GenerateGUID(false) for ReservedServerId. The first teleport with a new ID creates the server; reusing that ID later routes players to the same server.
- **Know the default placement when no server is specified** (one-creator-repeated): Without a specified server, TeleportAsync places users in a public server matched on the first user in the list's information. Plan group teleports around that behaviour.
- **Test teleports only in a published game on the client** (one-creator-repeated): TeleportService does not work in Studio playtesting. Publish the game and test in the Roblox client.
- **Read teleport data on arrival** (one-creator-repeated): Use Player:GetJoinData().TeleportData on the server. Use TeleportService:GetLocalPlayerTeleportData() for client-only access.
- **Gate teleports with validators, seeking permissions and trust routing** (one-creator-repeated): Use setTeleportationValidator for custom pre-teleport checks (e.g. same Team only); return false to abort. Use setSeekingPermissions with placeIDs, userIDs and group minimum ranks so ordinary players cannot control event timing. Route by trust level with TeleportAsync from a casual to a ranked place, and set the callback in the ranked place too, since players can join there directly through friends. - **Pick signals that match the design goal** (multiple-creators): Raise Latency for responsive server-to-client replication (ping scores against a 100 ms max relevant delta). Raise Language for co-op or social games. Use the Age signal for voice-heavy games so players in the same age group can chat. Avoid over-weighting, since it makes matchmaking too restrictive. Sources: [Roblox DevForum 2025-11](https://devforum.roblox.com/t/custom-matchmaking-is-now-available-to-all-experiences-on-roblox/4051419), [Roblox DevForum 2025-11](https://devforum.roblox.com/t/custom-matchmaking-is-now-available-to-all-experiences-on-roblox/4051419), [Roblox DevForum 2026-03](https://devforum.roblox.com/t/voice-chat-is-now-supported-in-servers-of-up-to-100-users/4534031), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/matchmaking), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/matchmaking/attributes-and-signals). Newest source 2026-10-28.
- **Check voice chat is enabled before weighting voice signals** (single-mention): The Voice Chat signal's weight is automatically 0 if the place has voice chat disabled. Enable voice chat before expecting the voice signal to affect matches. Sources: [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/matchmaking/attributes-and-signals). Newest source 2026-10-28.
- **Adjust only a few signal weights, a little at a time** (one-creator-repeated): Prioritise a few signals and change them incrementally. Weights are relative across all signals, so raising many weights dilutes the important ones and can make matching too restrictive. Sources: [Roblox DevForum 2025-11](https://devforum.roblox.com/t/custom-matchmaking-is-now-available-to-all-experiences-on-roblox/4051419), [Roblox DevForum 2025-11](https://devforum.roblox.com/t/custom-matchmaking-is-now-available-to-all-experiences-on-roblox/4051419). Newest source 2025-11-06.
- **Use InitializeServerAttributesForStudio for Studio testing** (single-mention): Call MatchmakingService:InitializeServerAttributesForStudio to set up the server attribute schema so custom matchmaking can be tested in Studio. Sources: [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/matchmaking/attributes-and-signals). Newest source 2026-10-28.
- **Keep enough servers per region to keep population healthy** (one-creator-repeated): Cumin ran at most 2 servers per region; low population forced high-ping servers and empty lobbies that drove players away. Check regional population and ping before launch, not after. Sources: [Cumin 2025-06 3:15](https://youtu.be/Z1tj1OPOEZg?t=195), [Cumin 2025-06 3:15](https://youtu.be/Z1tj1OPOEZg?t=195). Newest source 2025-06-08.
- **Use per-mission queues for group PvE content** (single-mention): Give each mission its own queue or lobby instead of drop-in servers, so a run doesn't collapse when other players leave. Complements the existing duplicate-queue-rooms rule. Sources: [Cumin 2025-07 13:59](https://youtu.be/jXogdTgtlXE?t=839). Newest source 2025-07-31.
- **Let players create joinable rooms without requiring invites** (single-mention): Allow a player to create a room with a chosen dungeon and difficulty that others can join. Requiring invites makes multiplayer hard to start. This is in tension with the private-server/invite guidance; use invites for private content only. Sources: [Cumin 2025-12 22:08](https://youtu.be/hQpC_UHxJDU?t=1328). Newest source 2025-12-23.
- **Bracket lobbies by level or skill** (one-creator-repeated): Use level-bracketed lobbies (e.g. 1+, 30+, 60+) so players find similar-skill teammates instead of one mixed pool. Cumin reported current broad lobbies (100+ existing) as ineffective. Sources: [Cumin 2026-09 4:47](https://youtu.be/kjLtxvB_iyk?t=287), [Cumin 2026-09 4:47](https://youtu.be/kjLtxvB_iyk?t=287). Newest source 2026-09-13.
- **Stage groups in a bare queue server before teleporting** (single-mention): Send players to a bare queue server and teleport the whole group to the dungeon once enough players are gathered. Similar to grouping before a reserved-server teleport. Sources: [Cumin 2026-09 5:28](https://youtu.be/kjLtxvB_iyk?t=328). Newest source 2026-09-13.
- **Treat cross-server group search as significant work** (single-mention): Servers can message each other to search for groups (MessagingService or a library such as Muster). Cumin calls this significant work, so build simpler lobbies first. Sources: [Cumin 2026-09 5:28](https://youtu.be/kjLtxvB_iyk?t=328). Newest source 2026-09-13.
- **Size matchmaking and party logic to the game's configured server cap** (single-mention): Official platform figure: max players per server is 10, but the cap is set per game. Read the game's configured cap rather than hardcoding 10, and check that queue party sizes and reserved-server groups fit within it. Sources: [Roblox public API 2026-11](https://www.roblox.com/games/119958473240233/). Newest source 2026-11-01.
- **Use ReservedServerId for developer reserved servers, VipServerId for purchased VIP servers** (one-creator-repeated): Developer-created reserved servers use ReservedServerId; player-purchased VIP servers use VipServerId. Never set both on one TeleportOptions. Only one routing field per call (ReservedServerId, VipServerId, or ServerInstanceId), since setting more than one errors. Sources: [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport-private-servers), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport-private-servers). Newest source 2026-10-30.
- **Pass the same VipServerId on every teleport in a VIP session** (one-creator-repeated): Set the same VipServerId on each teleport so players stay in the same VIP server across places throughout gameplay. Carry the origin VIP ID into a reserved server via teleportData or a DataStore so you can return the player to that VIP server later. Sources: [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport-private-servers), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport-private-servers). Newest source 2026-10-30.
- **Match VIP server IDs to places in the owning experience** (single-mention): A VIP server ID only works with place IDs from the experience that owns the VIP server. Teleports to places in other experiences with that ID will not work. Sources: [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport-private-servers). Newest source 2026-10-30.
- **Set VipServerId explicitly to avoid silent VIP fallback** (single-mention): Plain teleports with no routing fields may land on a VIP server silently. VIP join failures fall back to public join unless VipServerId is explicitly set. Set it explicitly when the player must stay in a VIP server. Sources: [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport-private-servers). Newest source 2026-10-30.
- **Detect reserved servers on arrival via PrivateServerId and PrivateServerOwnerId** (single-mention): Identify a reserved server with game.PrivateServerId ~= "" and game.PrivateServerOwnerId == 0. PrivateServerId stays constant across instances of the reserved server, while JobId changes per instance, so use PrivateServerId for identity. Sources: [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport-private-servers). Newest source 2026-10-30.
- **Handle TeleportInitFailed for failures after a successful call** (one-creator-repeated): Teleports can fail silently after TeleportAsync succeeds. Listen to TeleportService.TeleportInitFailed, which fires with the original TeleportOptions so you can retry. Back off longer on Flooded results. Wrap the call in pcall with a small attempt limit and short delays. Sources: [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport-private-servers), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport). Newest source 2026-10-30.
- **Stop using the client-side Teleport() method** (single-mention): The client-side Teleport() method is deprecated and should not be used for new work. Teleport only from server scripts with TeleportService:TeleportAsync(). This supersedes any older client-side teleport guidance. Sources: [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport). Newest source 2026-10-30.
- **Set Access Control for Places to Secure after migrating client teleports** (one-creator-repeated): Once all client-side Teleport() calls are migrated, set Access Control for Places to Secure (or Secure within universe only) to block teleport-based exploits. Use Secure within universe only for games with strict progression gates, test places, or places that exclusively use reserved servers. Sources: [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport), [Roblox Creator Docs 2026-10](https://create.roblox.com/docs/projects/teleport). Newest source 2026-10-30.
- **Check crossplatform routing before mapping one reserved server ID to one server** (single-mention): With crossplatform play disabled, Xbox One players land in a different server, so a single reserved server ID can map to two physical servers. Enabling console access breaks the one-server assumption. Track player counts and state per platform group rather than per ID. Sources: [Suphi Kaner 2022-08 26:33](https://youtu.be/c4DymnlVuL0?t=1593). Newest source 2022-08-09.
- **Keep party lobbies joinable across servers** (single-mention): Avoid hidden level or host restrictions that silently block newcomers from joining. A lobby that looks open but rejects players will fail. This extends the existing joinable-rooms rule by naming hidden join conditions as the failure mode. Sources: [Cumin 2026-06 9:23](https://youtu.be/2IdxQNOGoqA?t=563). Newest source 2026-06-24.

## Checklist
- [ ] Put all TeleportAsync calls in server Scripts; remove any client Teleport() calls and migrate them via RemoteEvents or prompts.
- [ ] Wrap every TeleportAsync in pcall; retry up to 5 times with about 1 second delay on Failure.
- [ ] On Enum.TeleportResult.Flooded wait about 15 seconds before retrying.
- [ ] Handle TeleportInitFailed separately for teleports that fail after the call succeeded.
- [ ] Treat any other TeleportResult as invalid and abort instead of retrying.
- [ ] Generate reserved server IDs with HttpService:GenerateGUID(false) and store the ID to reroute players.
- [ ] Test teleports by publishing and running in the Roblox client, not Studio playtesting.
- [ ] Read join data with Player:GetJoinData().TeleportData on arrival.
- [ ] Add a setTeleportationValidator check for team or eligibility rules before teleporting.
- [ ] Set setSeekingPermissions so only allowed places, users or group ranks can trigger event timing.
- [ ] Set the callback in both the casual and ranked places when routing by trust level.
- [ ] Split the game into Lobby, Queue and Gameplay places and fill the _places table with each place ID.
- [ ] Keep the _places table identical in every place and paste it into Gameplay and Queue files before publishing.
- [ ] Start queue countdowns only after the minimum player count is reached (template: 3:00).
- [ ] Group players in five-player batches in a lobby, then teleport them once to a reserved server.
- [ ] Use priority queues so players who have waited longer are served first.
- [ ] Start custom matchmaking from default signals; change only weights first.
- [ ] Create custom attributes (max 5 server, 5 player) before creating custom signals (max 2).
- [ ] Check Preview with 3 mock servers and hover scores before applying a config to live places.
- [ ] Keep weights non-negative; use 0 to exclude a signal; tune by ratio.
- [ ] Confirm the Current Configuration for each place; no config means default matchmaking.
- [ ] Enable private servers for classes; rename them per group; use invite links or usernames (mobile must be invited directly).
- [ ] Set Permissions to Public in Experience Settings, since new games are private by default.
- [ ] Use MessagingService (not DataStore polling) for friend notifications and real-time server browsers (refresh about 1 minute, max 20 servers).
- [ ] Revoke public access to fully shut down a game after restarting servers.
- [ ] Elect one host server per game mode via a DataStore key before any queue confirms matches.
- [ ] Notify players to rejoin if the host server re-hosts, since the queue is lost.
- [ ] Use manual queue requests rather than auto-queuing players.
- [ ] Use Players:GetPlayerFromCharacter when you have a character and need its Player.
- [ ] Wrap ReserveServer and GetPlayerPlaceInstanceAsync in pcall, as well as TeleportAsync.
- [ ] Set exactly one of ShouldReserveServer, ReservedServerAccessCode or ServerInstanceId per TeleportOptions.
- [ ] Place the PlayerArrivedFromTeleport handler in a ReplicatedFirst script.
- [ ] Fire a RemoteEvent on touch to show a teleport GUI; use SetTeleportGui and GetArrivingTeleportGui on the client.
- [ ] Check a player is not already in the queue folder before adding them, and cap the queue at the player limit.
- [ ] Remove queued players on PlayerRemoving.
- [ ] Cancel the countdown coroutine and reset timer UI when the last player leaves.
- [ ] Confirm each queued player is still in the game before ReserveServer and TeleportToPrivateServer.
- [ ] Clear queue entries and reset billboard counters after each teleport.
- [ ] Set a queue time limit so the queue starts with the current count instead of waiting forever.
- [ ] Duplicate queue room folders and rename them to the player count; do not edit the Q folder.
- [ ] Create a separate public destination place, publish it, and paste its place ID into the teleport field.
- [ ] Reset the lobby between matches: return to the lobby spawn, clear the active players table, toggle the neutral spawn flag.
- [ ] Use same-place CFrame moves for travel inside one place; reserve TeleportService for big builds or matchmaking.
- [ ] Change signal weights a few at a time and prioritise only a few signals.
- [ ] Enable voice chat before expecting the Voice Chat signal to affect matchmaking.
- [ ] Use InitializeServerAttributesForStudio when testing custom matchmaking in Studio.
- [ ] Before launch, confirm enough servers and players per region to avoid high-ping, empty lobbies (T16179, N6384).
- [ ] For group PvE, create one queue or lobby per mission rather than drop-in servers (T16235).
- [ ] Allow players to create a joinable room with chosen dungeon and difficulty; avoid making invites the only way to start (T16396).
- [ ] Add level-bracketed lobbies (e.g. 1+, 30+, 60+) to find similar-skill teammates (T16646, N6658).
- [ ] Use a bare queue server to gather players, then teleport the group when the threshold is reached (T16647).
- [ ] Set group-content minimums explicitly; a 15-player campaign needs different queueing than a 4-player PvE group (N6407, N6554).
- [ ] Consider a cross-server group search only after the simpler lobby and queue designs fail; plan for significant work (T16648).
- [ ] Keep a re-entry cooldown after a completed round if players must wait before rejoining (N6511, low-advice).
- [ ] Before sizing a queue, party, or reserved-server group, confirm the game's configured max players per server (official reference figure: 10).
- [ ] Generate reserved-server IDs with HttpService:GenerateGUID(false) and reuse the same ID for every later teleport to that server.
- [ ] Wrap each TeleportAsync in pcall with a small attempt limit and short delays.
- [ ] Connect TeleportService.TeleportInitFailed and retry using the original TeleportOptions it provides.
- [ ] On Flooded results, back off longer before retrying.
- [ ] On arrival, check game.PrivateServerId ~= "" and game.PrivateServerOwnerId == 0 to detect a reserved server.
- [ ] Set VipServerId on every teleport in a VIP session, and set it explicitly when players must not fall back to public servers.
- [ ] Confirm each VIP-teleport target place belongs to the experience that owns the VIP server.
- [ ] Store the origin VIP server ID in teleportData or a DataStore before teleporting to a reserved server.
- [ ] Migrate every client-side Teleport() call to server TeleportAsync before setting Access Control to Secure.
- [ ] Set Access Control to Secure within universe only for progression-gated games, test places, or reserved-server-only places.
- [ ] Test teleport behavior in a published game; TeleportService does not work in Studio playtests.
- [ ] If the game supports console players, check the crossplatform setting before assuming a reserved server ID maps to a single server.
- [ ] Review lobby join conditions (level, host-only checks) and make them visible to players so newcomers are not silently blocked.
- [ ] When sizing party or lobby logic, confirm the per-server player cap (100 in the indie example) against the game's configured cap.

## Where creators disagree
- **Matchmaking speed versus filling a low-population lobby**
  - rasdev (T6450): make matchmaking instant; every second of waiting risks the player leaving.

  - Not a direct contradiction: rasdev targets speed, janisjanis01 targets population gaps. Roblox's countdown (T10092) waits for minimum players, which is a third trade-off.
- **Whether to use TeleportService at all for simple games**

## Instructions for an agent using this file
- If a TeleportAsync call is needed, then run it from a server Script; if the code is client-side, then move it to the server via RemoteEvent.
- If TeleportAsync throws or fails, then retry inside pcall up to 5 times with a 1 second delay; if TeleportResult is Flooded, then wait about 15 seconds first.
- If TeleportResult is any value other than Failure or Flooded, then treat the teleport as invalid and do not retry.
- If a reserved server is needed, then generate its ID with HttpService:GenerateGUID(false) and reuse that ID to route players to the same server.
- If you need to test teleports, then publish the game and test in the Roblox client; do not rely on Studio playtesting.
- If you are building custom matchmaking, then start from default signals, define player and server attributes first (max 5 each), and add at most 2 custom signals.
- If you change matchmaking weights, then preview with Preview and Test (3 mock servers) and inspect hover scores before applying to live places; use only non-negative weights and tune by ratio.
- If a lobby is underpopulated or players wait too long, then consider bots or fill logic, and raise priority for players who have waited longer.
- If a place shows no Current Configuration, then it uses default Roblox matchmaking (Friends weight 15 dominates).
- If you need access control or a server browser, then use private servers with invite links or usernames (mobile must be invited directly); for cross-server features, use MessagingService and a 1 minute refresh, not DataStore polling.
- If a game has multiple servers queuing players, elect one host per mode via a DataStore key before any teleport is confirmed.
- If a player asks to join a queue, use a manual request; do not auto-queue players.
- If the goal is to let friends join a player, call GetPlayerPlaceInstanceAsync and pass the job ID as ServerInstanceId; do not also set a reserved or access-code field.
- If the goal is an unjoinable matched group, use ReservedServerAccessCode or ReserveServer plus TeleportToPrivateServer, and check that each player is still in the game first.
- If a teleport is within one place, move the HumanoidRootPart CFrame instead of calling TeleportService.
- If a queue becomes empty, cancel the countdown coroutine and reset UI; if a player leaves, remove them from the queue.
- If tuning custom matchmaking, change only a few signal weights at a time, and expect a new custom signal to start at weight 0.
- If the Voice Chat signal is in use, confirm voice chat is enabled; otherwise its weight is 0.
- If an error occurs during teleport-related async calls, handle it with pcall and Enum.TeleportResult rather than only the TeleportInitFailed event.
- Prefer 2025 to 2026 official and DevForum guidance over 2019 to 2021 indie advice when they conflict.
- If a group PvE mode has a player minimum above a drop-in server's capacity, then use a per-mission queue or lobby, not a shared server pool, so one player leaving doesn't abandon the run (T16235).
- If a player asks to start a multiplayer room, then allow others to join a visible room with a chosen dungeon/difficulty rather than requiring invites first (T16396).
- If players report waiting in mixed-skill lobbies, then add level-bracketed lobbies (e.g. 1+, 30+, 60+) before adding matchmaking complexity (T16646, N6658).
- If a region has very few servers, then check ping and empty-lobby rates before launch; low population forces high-ping servers and drives players away (T16179, N6384).
- If a group needs to form before a teleport, then stage players in a bare queue server and teleport the whole group once the threshold is met (T16647).
- If cross-server group search is needed, then treat it as significant work; use MessagingService (existing rule) or a library such as Muster rather than building from scratch (T16648).
- If a design sets a large group size (e.g. 15-player campaigns), then size the queue, wait-time and fallback behaviour for that threshold; do not reuse 4-player PvE assumptions (N6407).
- If a server size cap is set, then remember it limits the teammate pool (e.g. 40 cap leaves 39 possible teammates) and balance it against population per region (N6655).
- If a task involves party size, queue capacity, or reserved-server grouping, check the game's configured server cap first; do not assume a fixed value.
- If code calls Teleport() on the client, migrate it to server-side TeleportService:TeleportAsync before changing Access Control.
- If a teleport targets a player-purchased VIP server, set VipServerId on every teleport in that session.
- If a teleport targets a developer reserved server, use ReservedServerId and never set a second routing field.
- If the player must not fall back to a public server, set VipServerId explicitly rather than relying on plain teleports.
- If a teleport fails after the call returned, handle TeleportService.TeleportInitFailed and retry with the original TeleportOptions.
- If the result is Flooded, increase the backoff before retrying.
- If you need to know a server is reserved on arrival, check PrivateServerId ~= "" and PrivateServerOwnerId == 0, not JobId.
- If the place is a test place, a progression-gated place, or reserved-server-only, prefer Secure within universe only.
- If a game has console players and crossplatform is off, do not assume one reserved server ID equals one server; track each platform group separately.
- If a lobby or party has level or host restrictions, surface the join conditions to players before they try to join, rather than failing silently.
- Treat the 100-player figure as a self-reported example, not a platform guarantee; check the game's configured cap.
- Do not treat the 2-player start, 50-second round cap, or 5-10 second intermission as matchmaking defaults; use them only as examples of round-based timing.
- If a request is about queue start thresholds, rely on the existing rule to start countdowns at minimum players and tune the threshold per game.

## Official docs update (chunk 16, 2026-11-01)

_Labels: OFFICIAL = Roblox Creator Docs (repo commit 2026-10-29), read this session. Older creator tutorials in this topic that use ReserveServer, ReserveServerAsync, TeleportToPrivateServer, ReservedServerAccessCode or ShouldReserveServer describe APIs now DEPRECATED (Release 743 ~2026-10-15; kept only for backward compatibility)._

- **Current pattern for private/reserved servers** (OFFICIAL, 2026-10-29): create `TeleportOptions`, set `ReservedServerId = HttpService:GenerateGUID(false)`, call `TeleportService:TeleportAsync(placeId, players, options)`. The first teleport with a new ID creates the server; the same ID returns to it. To let other servers join the same one, store the ID in a DataStore under a session key. For player-purchased VIP servers set `VipServerId` to the target's `DataModel.PrivateServerId` (scoped to the owning experience). Set only one of ReservedServerId, VipServerId, ReservedServerAccessCode, ShouldReserveServer, ServerInstanceId per call, or TeleportAsync errors. Sources: [Teleport between places](https://create.roblox.com/docs/projects/teleport), [Teleport to private servers](https://create.roblox.com/docs/projects/teleport-private-servers).
- **Identify servers on arrival** (OFFICIAL): `game.PrivateServerId ~= "" and game.PrivateServerOwnerId == 0` means reserved; a VIP server has a nonzero PrivateServerOwnerId. PrivateServerId equals the ReservedServerId you passed; JobId changes per running instance. TeleportAsyncResult.PrivateServerId gives the destination's ID. Source: [Teleport to private servers](https://create.roblox.com/docs/projects/teleport-private-servers).
