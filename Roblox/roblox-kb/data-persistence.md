# Data Persistence

_DataStores, ProfileStore/ProfileService, session locking, MemoryStore, MessagingService, saving/loading, migrations._

## Overview
Data-persistence advice centers on session-locked per-player profiles. ProfileService was the standard in 2023 (Amora). The newest indie advice (2025-12, Possible Panda) recommends ProfileStore for new projects. The core pattern: a template of typed defaults, Reconcile and AddUserId after load, release on PlayerRemoving, and kick when the session ends or the load fails. Gate every read and write on a loaded profile, and mirror profile data to leaderstats after changes. Expect the save system to be the largest and hardest part of the build, so build currency, unlocks and loadouts first. Enable Studio API access before testing. All sources here are indie and self-reported; no official Roblox docs are in this batch.

## Rules and findings
- **Wrap every DataStore call in pcall and check the result** (multiple-creators): Applies to GetAsync, SetAsync, UpdateAsync, IncrementAsync and MemoryStore Subscribe/Publish. Warn on failure with warn(err) so errors are visible. A failed write may still have succeeded on the backend, so verify with a fresh read (UseCache=false) before retrying. - **Store each player's data as one table under one key, keyed by UserId** (multiple-creators): One DataStore key per player means one write per player. Key by player.UserId, never username, since usernames can change. Keep a session table keyed by UserId. Use User.Id only within one game; for cross-domain identity store User:ToString() and restore with User.fromString(). - **Do not write to DataStores on every event** (multiple-creators): Keep values in a local table and save periodically or on leave. - **Use UpdateAsync, not GetAsync+SetAsync, for production writes** (multiple-creators): UpdateAsync re-runs your function on concurrent writes instead of overwriting them. Separate get and set calls produce about 2x the network errors. SetAsync is acceptable for demos or pure overwrites. Official docs say use UpdateAsync for values modified by multiple servers. - **Use a session lock (ProfileStore/ProfileService) for player data that can load on multiple servers** (multiple-creators): Without locking, stale saves cause data loss and item duplication via race conditions. Indie creators recommend ProfileService/ProfileStore over DataStore2 or a hand-rolled system unless you have unique needs. Official docs require session locking so data loads on one server at a time. - **If hand-rolling a session lock, store JobId, use os.time, and treat 30-minute-old sessions as dead** (one-creator-repeated): Store game.JobId as a session tag; load only if it is nil or matches your server. Release by setting it to nil only if it still matches your JobId. Compare os.time() values, not tick() or os.clock(). Treat sessions older than 30 min as dead. Retry locked loads after about 5 s. Queue load/save operations so a save finishes before a rapid rejoin load. ## Checklist
- [ ] Put all persistent player data in one table keyed by UserId under one DataStore key.
- [ ] Wrap every GetAsync, SetAsync, UpdateAsync and IncrementAsync in pcall; warn(err) on failure.
- [ ] Use UpdateAsync for production writes; reserve SetAsync for demos or pure overwrites.
- [ ] Pass a default template so new players start with defined values, not nil.
- [ ] Only overwrite session data when the load pcall succeeded and data exists.
- [ ] Mark a profile as errored on load failure so defaults never overwrite real saves; tell the player.
- [ ] Use a session lock (ProfileStore/ProfileService preferred) if the same player can load on more than one server.
- [ ] Save on PlayerRemoving and in game:BindToClose.
- [ ] In BindToClose, save all players in parallel and wait on a counter; budget is 30 s total.
- [ ] Decrement the shutdown counter on every early-return path, including when the player left mid-load.
- [ ] Run an autosave loop with an interval of 30 to 120 s and a random first offset per player.
- [ ] Keep values in a local table and avoid writing on every gameplay event.
- [ ] Convert Vector3 to X,Y,Z numbers and CFrame to GetComponents arrays before saving; do not pre-JSONEncode.
- [ ] Use OrderedDataStore for numeric leaderboards; page size up to 100.
- [ ] Use MemoryStore only for temporary data, and set expiration on every write (max 45 days).
- [ ] Use exponential backoff on retries (5 attempts, 2 s base, 32 s max).
- [ ] Treat throttle codes 301-306, KeyThrottled, DatastoreThrottled and HTTP 429 as back-off-and-retry.
- [ ] Verify failed writes with a fresh read (UseCache=false) before retrying.
- [ ] Snapshot the universe's data daily and before publishing data-logic changes.
- [ ] Keep data store names fixed; use key prefixes instead of scopes.
- [ ] Save the PurchaseId before granting items; revoke granted currency manually on refunds.
- [ ] Enable Studio Access to API Services before testing; verify final behavior in a published build.
- [ ] Keep economy logic and validation on the server; never call DataStoreService from clients.
- [ ] Sanitize client input and reject inf, -inf and nan before writing.
- [ ] Monitor DataStoreRequests by operation and status to catch throttling early.
- [ ] Use ProfileStore/ProfileService for any player data that can load on more than one server; do not hand-roll unless you need to.
- [ ] Convert UserId with tostring() for DataStore keys and tonumber() when reading ordered stores.
- [ ] Fix the production store/ProfileStore name before launch and never change it afterwards.
- [ ] Give test builds their own store index so they never share live storage.
- [ ] Define every default in ProfileTemplate and call Reconcile() after each load.
- [ ] Call AddUserId(player.UserId) on load and define RTBF deletion templates such as User_{UserId}.
- [ ] On PlayerRemoving call EndSession()/Release(); kick on OnSessionEnd and on a nil load.
- [ ] Load players already in the server at startup as well as on PlayerAdded.
- [ ] Save on three triggers: PlayerRemoving, an autosave loop, and BindToClose (typical autosave ~60 s).
- [ ] In BindToClose save all players in parallel within 30 s, then wait about 3 s before shutdown.
- [ ] Keep the autosave interval shorter than the session-lock expiry.
- [ ] Clear per-player tables and nil Instance references on PlayerRemoving.
- [ ] Use UpdateAsync for writes that depend on current data; SetAsync only for independent new values.
- [ ] Always pass metadata with SetAsync, IncrementAsync and UpdateAsync; use IncrementAsync for counters.
- [ ] Never yield inside an UpdateAsync callback; return nil to cancel a write.
- [ ] If you see 'data store request was added to queue', you are saving too often; reduce frequency and save only when data changed.
- [ ] Monitor request budget (about 60 requests/min plus 10 per player, self-reported) and DataStore:Usage().
- [ ] Measure save size with JSONEncode length before optimizing; compress only as a last resort.
- [ ] Store positions as integers (x1000, rounded) and flatten arrays before adding more encoding.
- [ ] Store binary data with Buffer:ToBase64(), not buffer.tostring output.
- [ ] Validate data on save and on load, and keep a wipe guard that holds saves when data collapses.
- [ ] Use migrations that fail closed; never stamp or save a half-migrated profile.
- [ ] Use ProfileStore:MessageAsync or queues for cross-server writes to a locked profile.
- [ ] Use GetOrderedDataStore for leaderboards and MemoryStore when cross-server updates must be real-time.
- [ ] Test DataStores in Studio with API access in a test version, then verify in a published build.
- [ ] For a new project with player data, install ProfileStore rather than ProfileService (verify the current package version first).
- [ ] Wrap each PlayerAdded load so handlers only run once the profile is loaded.
- [ ] At the top of every data-touching handler, return early if the profile is nil.
- [ ] After changing profile.Data, update matching leaderstats values in the same code path.
- [ ] Put every saved field (type, default, min/max) in one template module.
- [ ] Clamp integer fields to template bounds on load and cap array lengths.
- [ ] Build currency, unlocks and loadouts persistence before cosmetic or secondary systems.
- [ ] For stateful objects (e.g. plants), save position, growth stage, mutation and state, and test a server change.
- [ ] Before building a new save or session-lock layer, check whether Roblox's built-in transactions and session locking have shipped (targeted Early 2027).
- [ ] For leaderboard reads of several entries, use OrderedDataStore BatchGet (shipped) and check each returned entry.
- [ ] Do not write code against OrderedDataStore GetHistogramAsync until it appears in the official API reference (targeted Early 2027).
- [ ] If a feature moves players between servers by teleport, confirm that all secure data (currency, inventory, progress) is saved to a DataStore or MemoryStore before the teleport, and reloaded on arrival.
- [ ] Do not put currency or inventory into TeleportData as the source of truth.
- [ ] If you use reserved servers, write the reserved server ID to a DataStore keyed by session or party ID when it is created.
- [ ] When a player rejoins a reserved server, read the stored reserved server ID by session or party ID before teleporting them.
- [ ] Run a per-player autosave loop (task.spawn) at about 60 seconds in production to limit DataStore load (self-reported).
- [ ] Set the autosave interval to 3 seconds only for testing, and change it back before release.
- [ ] After adding each saved system, test by leaving and rejoining to confirm the data persists.
- [ ] Store CFrame as position and look-vector numbers, and rebuild with CFrame.new(pos, pos + look).
- [ ] Wait for CharacterAdded before moving a character to its loaded position.
- [ ] Test save behaviour with the autosave loop, because a Studio stop may skip PlayerRemoving.
- [ ] Use weak-keyed or weak-valued tables for caches that hold player references.
- [ ] Cap GetAsync calls at about 60 + 10 per player per minute, and cache loaded data in memory.
- [ ] Keep writes to any single key at least 6 s apart across servers; coalesce changes first.
- [ ] Deep-copy the defaults template per player before Reconcile.
- [ ] Use WaitForChild with about a 10 s timeout for folders created by other scripts.
- [ ] Detect reserved servers via a non-empty PrivateServerId and PrivateServerOwnerId == 0 before using DataStores.
- [ ] On reserved servers, key data by PrivateServerId, load once, cache, and save on BindToClose.
- [ ] In Studio test configs, set save interval to 0 and saveOnClose to false.
- [ ] Set a player attribute for connection state and show the warning only after about 5 s.
- [ ] Set session lock attempts to 3–5 and lock interval to 30–60 s.
- [ ] Keep the save interval below the lock expiry window.
- [ ] Pin DataStore module versions and review the changelog before major bumps.
- [ ] Change store names only for a deliberate wipe, after confirming with the user.
- [ ] Autosave every 1–2 minutes for larger games, in addition to save-on-leave and BindToClose.
- [ ] Enable Studio API access before testing DataStores in Studio.
- [ ] On Players.PlayerAdded, check ownership of each gamepass and grant its perks, because the purchase event will not fire for existing owners.
- [ ] Do not assume a purchase event means the perk is active on later joins; re-derive perks from saved or verified ownership at each join.
- [ ] Persist shop inventory and refresh timers on the server, and confirm they survive leaving and rejoining.
- [ ] Before deleting a pack or item, confirm its open or award action has completed successfully.
- [ ] Trace each shop or pack read to its authoritative data source when an item looks stuck refreshing.

## Where creators agree
- Wrap all DataStore calls in pcall and warn on failure (DevForum, B Ricey, Roblox Creator Docs).
- Save on PlayerRemoving and also on game:BindToClose; PlayerRemoving alone is unreliable at shutdown (DevForum, B Ricey, Roblox Creator Docs, janisjanis01 indirectly).
- Key data by player UserId, not username (DevForum, B Ricey, Roblox Creator Docs).
- Give new players defaults when no save exists (DevForum, B Ricey, Roblox Creator Docs).
- Enable Studio Access to API Services before DataStores work in Studio (DevForum, B Ricey, Roblox Creator Docs).
- Keep economy-relevant logic server-side and never let clients touch DataStores (DevForum, Roblox Creator Docs).
- Session locking is required to prevent duplication and data loss across servers; ProfileService/ProfileStore is the recommended route (DevForum, Roblox Creator Docs).
- Convert Vector3/CFrame and Instances to primitives before saving (DevForum, B Ricey, Roblox Creator Docs).
- Use UpdateAsync rather than GetAsync+SetAsync for concurrency-sensitive writes (DevForum, B Ricey, Roblox Creator Docs).
- Multi-server player data needs session locking (ProfileStore/ProfileService or equivalent): Q1157, T13527, T11749, T12367, Q1272 all say so, with item-dupe reasoning.
- Wrap every DataStore call in pcall and check results: T13963 (official), T14728 (official), T13514, T12751, T11517 all agree.
- Save on PlayerRemoving, a periodic loop, and BindToClose: T13522, T12754, T15578 (official), T13266 agree.
- Enable Studio Access to API Services before testing DataStores in Studio: T11175, T12749, T13264, T14751 (official) agree.
- Key data by UserId, not name: T11177, T12629, T15575 (official), T13528 agree.
- Kick the player instead of giving defaults when a load fails: T13520, T11519, T12751, T13885 agree.
- Prefer UpdateAsync when multiple servers may write the same key: T13526, T13964 (official), T15583 (official) agree.
- Do not call DataStores on every event; save on a timer and when data changes: T10715, T13524, T12750 agree.
- Autosave around 60 s is the common indie choice: T10895, T12750, T13515, T13522 agree (official example is 180 s).
- Possible Panda and Amora both recommend a session-locked profile library with a template of defaults, Reconcile after load, AddUserId, and release on leave.
- Amora and Possible Panda both kick the player when the profile is released or the session ends, to avoid playing unsaved.
- studio rook and LovJak (both low-advice) agree the save system is the biggest and longest part of the build.
- Possible Panda and Amora both say release or session end should save data; manual save calls are not needed when using the profile library.
- Wrap DataStore calls in pcall (T18115, T18177, T18022, T18040).
- Enable Studio API access before testing DataStores (T18114, T18174, T18327).
- Key data by UserId as a string (T18113, T18175).
- Save one table of persistent values on PlayerRemoving (T18176, T18326).
- Use ProfileStore-style session locking for per-player profiles (T18323, T18325).

## Where creators disagree
- **Write method: SetAsync vs UpdateAsync**
  - B Ricey (2021, T5563): SetAsync is fine for simple overwrite saves; UpdateAsync is optional.
  - B Ricey (2024, T5968): production saves should use UpdateAsync; SetAsync only for demos. Newer and preferred.
  - DevForum (2020-2021, T5341, T5521): use UpdateAsync only for session-locked saves.
  - Roblox Creator Docs (T8727): UpdateAsync for values modified by multiple servers.
  - Roblox Creator Docs (T9160, T9161): examples use GetAsync/SetAsync for simple cases, with pcall.
- **Load-failure handling: kick or continue with defaults**
  - DevForum ProfileStore example (2021, T5576): if LoadProfileAsync returns nil, kick the player with a rejoin message.
  - Roblox Creator Docs (2026, T9842): prefer letting the player play with default data plus a clear message over kicking. Newer; treat as authoritative.
  - Roblox Creator Docs (T9841): mark the profile errored so defaults never overwrite real data.
- **Serialization format for instances and positions**
  - DevForum (2018, T5019): object-space CFrame strings mapped to item names.
  - DevForum (2020, T5255-T5259): property-name dictionaries grouped by ClassName, with a Children key.
  - B Ricey (2024, T5964): CFrame:GetComponents number arrays.
  - Roblox Creator Docs (T9164, T9479): split Vector3 into X,Y,Z numbers. Official and most current.
- **Retry strategy**
  - DevForum (2019, T5179): fixed wait(7) between retries.
  - DevForum (2021, T5520): request-budget wait before each call.
  - Roblox Creator Docs (T9840): exponential backoff with 2 s base and 32 s max. Official; prefer it.
- **Autosave interval**
  - DevForum (2021, T5522, N2357): 60-second loop.
  - Roblox Creator Docs (T9163, N3674, N3886): 30 to 120 s recommended; sample 180 s. Prefer official.
  - B Ricey (T5287): autosave had mixed results; test before relying on it.
- **Data store limit scaling with player count**
  - Roblox Creator Docs (T6960): data store limits do not scale with player count, unlike Engine API limits.
  - Roblox Creator Docs (T8151, N3971-N3974): default budgets scale with CCU. Conflicts with T6960; T6960 may refer to legacy v1 fixed limits (see T6961).
  - Read budget differs: T8151 says 250 + CCU x 40; N3971 says 300 + CCU x 40. Verify in current docs.
- **Session lock implementation: hand-rolled vs library**
  - DevForum (2020-2021, T5341-T5349, T5524-T5525): hand-roll with JobId, os.time and 30-min lease.
  - DevForum (2021, T5517): hand-rolled version is less tested and may contain bugs; use DataStore2 or ProfileService.
  - DevForum (2021, T5573) and DevForum (2020, T5348): use ProfileService/ProfileStore unless you have unique needs.
  - DevForum (2018, T4980): DataStore2 recommended; dated, and maintenance status is unknown.
- **Studio behavior during saves**
  - B Ricey (2021, T5567): skip saving when RunService:IsStudio() during tests; verify in a published build.
  - DevForum (2021, T5523): under BindToClose, skip waiting when not in Studio.
  - Roblox Creator Docs (T5323, T9475): enable Studio API access so saves work in Studio.
- **Session lock versus waiting after join**
  - Q1157 (Roblox DevForum) and T13527 (Generalist Programmer) say session locking is essential for multi-server data.
  - T12483 and N4743 (Suphi Kaner, 2024-11) say waiting about 5 s after join before loading lets the previous server finish saving, instead of session locking; Q1286 calls it almost no-downside.
- **Hand-rolled lock expiry**
  - Existing file rule: use os.time and treat 30-minute-old sessions as dead (ProfileService uses 30 min per N4481).
  - T11753 and T11754 (Suphi Kaner, 2023-06) say os.time is unreliable across servers; store the lock in MemoryStore with expiration instead. Prefer the newer MemoryStore advice.
- **DataStore2 for player saves**
  - T10611 (2020) and T11444 (2022) say keep DataStore2 if it works.
  - T15577 (Roblox Creator Docs, official 2026-10) says do not use DataStore2 for new experiences and migrate with the official beta tool. Prefer the official guidance.
- **UpdateAsync always versus SetAsync for independent writes**
  - Existing file rule: use UpdateAsync, not GetAsync+SetAsync, for production writes.
  - T11750 (Suphi Kaner) and T15583 (official) say SetAsync is right for new keys or values independent of prior state; UpdateAsync with a fixed value gains nothing. T13964 (official) says prefer UpdateAsync when multiple servers write the same key.
- **MessagingService for cross-server work**
  - Existing file rule: do not use MessagingService for session handoff.
  - T12298 (Roblox DevForum) uses MessagingService to message the server holding data for GlobalUpdates; T15338 (official) recommends MessagingService for cross-server communication. T12372 prefers ProfileStore:MessageAsync for gifting. The rules apply to different jobs; keep handoff out of MessagingService.
- **Retry or kick when open or load fails**
  - T11717 (Suphi Kaner) says never kick on open failure; retry about every 6 s while the player remains in the server.
  - T11519 (GnomeCode), T12751 (SimTek) and T13885 (MonarchDev) kick after retries fail, with a try-again-later or progress-is-safe message.
- **Autosave interval**
  - 30 s: N4467 (Suphi), N5957 (official Gold Rush example), N4742 (demo).
  - ~60 s: T10895, T12750, T13515, T13522, N4854.
  - 180 s: N6067 (official example, must be shorter than lock expiry).
  - 300 s: N4693 (ProfileStore default), T13266 (ArTheDev), capped by T13581.
- **Queue processing order**
  - T11732 and T11734 (Suphi Kaner) describe a tradeoff: remove-then-save can lose coins on save failure; save-then-remove can double-grant. No single answer; choose by reward criticality.
- **Which profile library to use**
  - Amora (2023-08): use ProfileService; it handles session locking and scales well.
  - Possible Panda (2025-12): use ProfileStore for new projects; ProfileService users have little reason to switch.
  - Not a direct contradiction: the difference reflects the date. Treat ProfileStore as the current default for new work.
- **Whether manual saves are needed on leave**
  - Existing knowledge base rule: save on PlayerRemoving and in BindToClose.
  - Possible Panda (2025-12): the profile store autosaves, so manual saves on disconnect are not needed; end the session on leave as a backup.
  - Amora (2023-08): release the profile on PlayerRemoving to clear the lock and save. Both approaches end with a release on leave.
- **Failure handling: kick immediately or retry first**
  - Suphi Kaner (T18022, T18040, 2022-06): kick the player when GetAsync or SetAsync fails, so broken data is not used.
  - Existing KB rule (retry while the player is present; kick only after retries fail) is more recent and should be preferred. Both prevent overwriting data with defaults.
- **Whether store names should be changed to reset data**
  - AlvinBlox (T18111, 2024-05): incrementing the store name (e.g. version 2) effectively resets all player data.
  - Existing KB rule: treat store and key names as permanent after launch. Use a new name only for a deliberate, confirmed wipe.

## Instructions for an agent using this file
- If a DataStore call is written, then wrap it in pcall, check success, and warn(err) on failure.
- If the load pcall fails, then use defaults, mark the profile errored so it never saves over real data, and tell the player. Prefer this over kicking.
- If a player can be loaded on more than one server, then use a session lock, preferably ProfileStore/ProfileService, and store game.JobId with os.time timestamps.
- If you hand-roll a session lock, then treat sessions older than 30 minutes as dead, keep the lock during autosave, and release only on leave when the JobId matches.
- If writing production data that another server might change, then use UpdateAsync and not GetAsync+SetAsync. Use SetAsync only for demos.
- If the server is shutting down, then save all players in parallel inside BindToClose, using a counter, within the 30 s shared budget. Decrement the counter on every early return.
- If a player is leaving, then confirm data is loaded and the player is still in Players before saving.
- If progress updates every event, then keep it in a local table and save on an autosave timer (30-120 s with random offset) and on leave.
- If storing Vector3/CFrame/Instances, then convert to X,Y,Z numbers, number arrays, or property-name dictionaries. Never pre-JSONEncode before SetAsync.
- If data is temporary (queues, daily or monthly boards), then use MemoryStore with expiration; if it is permanent progress, then use DataStoreService. If it is a numeric leaderboard, then use OrderedDataStore.
- If the game needs player data across multiple servers, use ProfileStore; do not write raw GetAsync/SetAsync without a lock. If hand-rolling a lock, expire it with MemoryStore, not os.time.
- If a load still fails after retries, kick the player with a 'progress is safe' message; never save default data over real data.
- If a write depends on the current value, use UpdateAsync with a transform function; for new keys or independent values use SetAsync. Always pass metadata.
- If a save approaches the size limit, measure with HttpService:JSONEncode length first, then integer-scale, flatten and comma-join; compress only as a last resort.
- If migrating from DataStore2, use the official migration tool; do not start new experiences on DataStore2.
- If a write must reach a player locked on another server, use ProfileStore:MessageAsync or DataStore:Queue; do not write the locked store directly.
- If testing, use a separate test version and index; never enable Studio API access on the live experience.
- If user data must be deletable, define RTBF templates and use User_{UserId} keys before launch, then verify deletion end-to-end.
- If you need real-time cross-server leaderboards, use MemoryStore; use OrderedDataStore for stored leaderboards with a few seconds of lag.
- On shutdown, save all players in parallel within 30 s, then wait about 3 s before the server closes.
- If starting a new project with player data, use ProfileStore. For an existing ProfileService project, do not migrate for this reason alone.
- If a handler touches player data and the profile is nil, return early; do not create a new profile on the fly.
- If you change profile.Data that is shown in leaderstats, update the leaderstats value in the same code path.
- If you add a new saved field, add it to the template with a default and rely on Reconcile to fill it for existing players.
- If you define a saved integer, set its min and max in the template and clamp on load.
- If scoping a save system, prioritize currency, unlocks and loadouts before cosmetic or secondary systems.
- If a player's load fails, kick them rather than letting them play unsaved.
- If testing DataStores in Studio, confirm the Studio API access setting is on first.
- If built-in session locking ships, evaluate it against the ProfileStore and hand-rolled lock rules before changing them. Do not delete the existing lock rules until the official docs confirm the new behavior.
- If GetHistogramAsync is not in the API reference yet, do not generate code that calls it.
- For batched leaderboard reads, use OrderedDataStore BatchGet now and handle missing entries.
- When citing roadmap items, state the date you read them, because shipped items disappear after six months.
- If a task involves teleporting players between places or servers, check that secure state is persisted to a DataStore or MemoryStore and not held only in local or teleport data.
- If a task involves reserved servers, store the reserved server ID keyed by session or party ID so rejoin works across sessions.
- Treat these two items as official ground truth from the 2026-10 Creator Docs.
- If saving a CFrame, store position and look vector as numbers and rebuild it with CFrame.new(pos, pos + look).
- If testing saves in Studio, do not rely on PlayerRemoving alone. Verify with the autosave loop.
- If setting up production autosave, use about 60 seconds. Use 3 seconds only in test builds.
- If a player's character is moved to a saved position, do it after CharacterAdded.
- If a new saved system is added, verify persistence by leaving and rejoining before moving on.
- If a cache holds player objects, use a weak table (__mode 'k' or 'v') so entries can be collected.
- If a user cites a DataStore budget or throttle, confirm it against current official Roblox docs before using it as a constant.
- On a failed load or save, retry with capped backoff first and kick only after retries fail; do not follow the 2022 kick-immediately pattern.
- Before writing a key, check the ~6 s same-key cooldown and coalesce changes in memory.
- Detect reserved servers via PrivateServerId and PrivateServerOwnerId before running DataStore logic.
- Do not change a store name unless the user confirms a deliberate data wipe.
- For new projects, recommend ProfileStore over ProfileService or DataStore2.
- When debugging DataStore errors in Studio, first confirm Studio API access is enabled.
- When using a DataStore module, review its changelog before updating; treat major version bumps as breaking.
- Use WaitForChild with a timeout where a script depends on folders created by another script.
- If a task grants gamepass or purchase-based perks, add an ownership check in the PlayerAdded path in addition to the purchase handler.
- If a purchase rule and a perk-on-join rule conflict, keep the purchase handler for new purchases and the join check for existing ownership.
- If shop or pack state looks stale or stuck, first check which data source is authoritative, then check the order of refresh calls.
- If an item is destroyed or consumed, confirm its open or award action has finished first.
- Treat these shop and pack tips as single-source and self-reported; prefer official docs when they conflict.

- 2015-11-30 Roblox DevForum [page](https://devforum.roblox.com/t/stravants-bitbuffer-module-compact-storage-of-data-tutorial/20189): Write and read fields in the exact same order with the same bit widths; mismatched order is the hardest bug to find.

- 2015-11-30 Roblox DevForum [page](https://devforum.roblox.com/t/stravants-bitbuffer-module-compact-storage-of-data-tutorial/20189): Store the chosen bit width in a 6-bit header first, since 6 bits can represent widths up to 63.
